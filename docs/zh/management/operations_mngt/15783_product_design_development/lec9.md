# Lec 9 体验与服务设计（Experience and Service Design）

> 对应Spring 2026 Class 10。原始链接：[课程大纲](https://studylib.net/doc/28287998/syllabuspdd-spring-2026--1-)；核心阅读：[PDD第8版](https://www.mheducation.com/highered/product/Product-Design-and-Development-Ulrich.html)第17章。

## TL;DR

- 服务体验由用户行动、前台接触、后台活动、支持系统和有形证据共同产生，不能只靠修改界面或员工话术解决。
- 客户旅程描述用户经历，服务蓝图进一步把每个接触点连接到后台责任、依赖和失败恢复机制。
- 体验设计应围绕具体用户、任务与时间边界，既度量成功结果，也观察等待、交接、放弃和补救。

## 从旅程到交付系统

客户旅程按时间呈现用户为完成目标所经历的步骤、情绪与接触点。服务蓝图在其下方补上前台人员或界面、后台动作、支持流程和有形证据，并标出可见线与组织内部交接。

::: definition [服务蓝图]
服务蓝图是一种把用户体验与组织交付机制对齐的时序模型。它不仅画“用户看见什么”，还说明谁在后台做什么、依赖哪个系统，以及失败时由谁恢复。
:::

## 设计步骤

1. 固定一个用户、一个目标和清晰起止点。
2. 用真实研究材料写出用户行动，而不是公司部门流程。
3. 为每一步补上接触点、可见证据和期望状态。
4. 向下追踪后台动作、支持系统和责任角色。
5. 标记等待、交接、失配、放弃和补救路径。
6. 为关键节点定义时延、成功率、错误率或满意度等指标。

::: pitfall [把服务问题界面化]
若页面显示“可取货”而门店尚未完成拣货，根因是前后台事实不同步。重写按钮文案不会修复库存与履约流程。
:::

::: insight [服务原型要穿过可见线]
只测试用户面对的界面，可能验证了理想流程，却没有验证组织能否交付承诺。关键场景至少应走通一次前台、后台和异常恢复的完整链路。
:::
