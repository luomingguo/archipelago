# Lec 12 产品架构（Product Architecture）

> 对应Spring 2026 Class 14。原始链接：[课程大纲](https://studylib.net/doc/28287998/syllabuspdd-spring-2026--1-)；核心阅读：[PDD第8版](https://www.mheducation.com/highered/product/Product-Design-and-Development-Ulrich.html)第10章。

## TL;DR

- 产品架构规定功能元素如何映射到物理构件，以及构件之间通过哪些几何、能量、材料和信息接口协作。
- 模块化可以支持并行开发、升级、维修与产品族复用，但也可能增加体积、接口成本或性能损失；整体式架构则相反。
- 架构决策必须同时考虑功能耦合、用户可见变化、制造装配、供应链、团队边界和未来差异化需求。

## 功能、构件与接口

架构设计先列出功能元素，再决定哪些功能由同一构件承担、一个功能是否跨多个构件实现，以及构件之间需要交换什么。接口描述应足以让不同团队独立推进后仍能集成。

::: definition [产品架构]
产品架构是产品功能元素到物理构件的分配方案，以及构件接口的规范。模块不是任意分组，而是内部高关联、对外接口相对清晰的构件集合。
:::

## 模块化与整体式的权衡

| 关注点 | 模块化倾向 | 整体式倾向 |
| --- | --- | --- |
| 升级与替换 | 局部更改 | 牵动多个构件 |
| 并行开发 | 接口稳定后较容易 | 需要高频协同 |
| 性能与体积 | 可能有接口开销 | 更易联合优化 |
| 产品族 | 便于复用与组合 | 差异化可能需重设计 |

::: pitfall [模块越多越灵活]
每个模块都新增接口、容差、连接件和集成风险。模块化只有在变化隔离、复用、维修或组织并行的收益超过接口成本时才有价值。
:::

::: insight [团队结构会固化进架构]
若组织按既有部门直接切分产品，接口往往反映沟通边界而非用户价值。架构评审应同时问“哪些功能必须共同优化”和“哪些团队能够持续共同负责”。
:::
