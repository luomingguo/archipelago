# CLH 队列锁（CLH Queue Lock）

## 问题情境

在高并发共享内存系统中，当数十个线程同时使用传统 TAS 或 TTAS 自旋锁争抢临界区时，所有线程会在同一个全局共享锁变量上自旋。每次锁被释放，都会引发总线上的全量缓存失效风暴（Invalidation Storm），导致总线带宽被消耗殆尽，真正持有锁的线程甚至无法及时写入释放信号。此外，简单的自旋竞争不提供任何先来先服务（FIFO）顺序，容易导致部分线程长期无法获取锁而陷入饥饿。如何在保证严格 FIFO 公平性的前提下，将锁释放的总线广播开销降低为点对点单播通知？

## 概念界定

::: definition CLH 队列锁（CLH Lock）
CLH 锁（由 Travis Craig、Anders Landin 和 Erik Hagersten 提出）是一种基于隐式单向链表的自旋队列锁。每个请求锁的线程通过原子交换（Swap）接入队列尾部，并在其**直接前驱节点的锁定状态（`pred.locked`）**上进行自旋等待。锁释放时，持有者仅需更新自身节点状态即可单播唤醒唯一直系后继，具有 $O(1)$ 的释放总线通信开销与严格的 FIFO 公平性保证。
:::

## 解释与依据

CLH 锁的核心在于其隐式队列拓扑与硬件缓存一致性协议的配合：

1. **原子入队与前驱绑定**：
   系统维护一个全局原子尾指针 `tail`。当线程试图加锁时，将本地节点 `myNode` 的 `locked` 字段置为 `true`，并对 `tail` 执行原子交换指令（如 `tail.getAndSet(myNode)`）。这一操作不仅将自身原子化地设置为新的队尾，还获取了原队尾节点的引用 `pred`。
2. **前驱状态监听与本地缓存自旋**：
   线程不需要维护指向后继节点的指针，而是专一在获取到的前驱节点标志上循环自旋：`while (pred.locked) {}`。在具备硬件缓存一致性（如 MESI 协议）的多核系统中，前驱节点的 `locked` 状态会被加载到当前核心的私有缓存中；只要前驱持有锁，自旋轮询完全在本地缓存中命中，不会对共享总线产生任何网络通信。
3. **常数级单播唤醒**：
   持有锁的线程完成临界区后，只需执行 `myNode.locked = false`。该写入操作仅使直系后继核心中对应的只读缓存行失效，唯一直系后继感知到前驱释放并正式进入临界区，队列中其他排队线程的缓存行完全不受干扰。
4. **空间复用机制**：
   为了避免高频加锁解锁引发的频繁对象分配与 GC 压力，线程在释放锁后，可直接将前驱节点的引用赋值给自己的 `myNode`，在下一次加锁时作为自身节点复用。系统整体空间复杂度恒定为 $O(L + N)$（其中 $L$ 为锁数量，$N$ 为线程总数）。

::: insight CLH 的空间与通信权衡
CLH 锁以极其简练的原子交换完成了逻辑队列拓扑的构建，既不需要双向链表，也不需要维护显式后继指针。它将全局无序争抢转化为单向依赖链，把锁竞争从 $O(N^2)$ 的总线广播风暴精准规约为 $O(1)$ 的点对点失效通知。
:::

## 边界与辨析

- **适用条件**：
  具备硬件缓存一致性协议（cc-NUMA 或 SMP）的多核共享内存体系结构；临界区短、线程数较多的高吞吐场景。
- **NUMA 拓扑陷阱与反例**：
  在**缺乏缓存的 NUMA 体系结构**（Non-Cache-Coherent NUMA）或者跨节点缓存同步代价极高的非对称系统上，CLH 锁的性能会发生灾难性坍塌。原因在于前驱节点的内存物理分布在远程 NUMA 节点的物理内存中。当前核心反复读取 `pred.locked` 将导致持续不断的跨互连网络远程读取，迅速吃满互连总线带宽。
- **与 MCS 锁的辨析**：
  - CLH 锁监听前驱节点状态，链表指针隐式指向前驱；MCS 锁监听自身本地节点状态，链表指针显式指向后继。
  - CLH 锁在有缓存的 cc-NUMA 上表现极佳且实现极其简洁；MCS 锁在无缓存的 NUMA 上依然能保证严格的本地内存自旋（Local Spinning）。

## 提取与迁移

- **主动唤醒思考题**：
  1. *为什么 CLH 锁在释放锁后，线程必须执行 `myNode = pred` 回收前驱节点，而不能继续使用原来的 `myNode`？*
     - **参考答案**：如果直接复用原 `myNode`，而该线程紧接着再次申请同一把锁，它可能会将 `myNode` 重新加入队尾并置为 `true`。此时其后继线程还在观察该节点的旧状态，会立即发生状态混淆导致死锁或违背互斥性。将前驱节点回收作为本线程下一次加锁的新节点，能确保每个处于队列中的节点至多被一个后继线程监听。
  2. *在 Java `AbstractQueuedSynchronizer`（AQS）中，为什么采用了 CLH 锁的变体而非 MCS 锁？*
     - **参考答案**：Java 运行在现代强缓存一致性的 x86/ARM 多核硬件上，CLH 结构在 cc-NUMA 下通过缓存一致性即可实现本地自旋；更关键的是，AQS 需要支持线程中断（Interrupt）和超时放弃，在 CLH 变体中后继线程只需向前回溯探测未取消的前驱节点，比 MCS 动态重组后继单向链表更为容易。

## TL;DR

- CLH 锁通过原子交换将等待线程编排进隐式单向队列，实现先来先服务（FIFO）与无饥饿保证。
- 线程在前驱节点的锁定标志上自旋，锁释放时通过前驱节点单播通知后继，消除总线广播风暴。
- 依赖硬件缓存一致性协议实现本地自旋；在无缓存 NUMA 架构下会产生严重的远程内存轮询瓶颈。
