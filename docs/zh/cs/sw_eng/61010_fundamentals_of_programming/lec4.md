# Lec 4 图搜索与抽象路径规划（Graph Search）

> 参考资料：[Graph Search](https://py.mit.edu/fall26/readings/graph_search)

## TL;DR

- **状态空间的图抽象**：无论是地图导航、迷宫、15 拼图、推箱子还是单词接龙，只要能定义“状态（节点）”与“合法移动（边）”，皆可统一抽象为图。
- **调度策略决定搜索模式**：统一搜索骨架下，待办议程（Agenda）采用先进先出队列（FIFO，`pop(0)`）对应**广度优先搜索（BFS）**；采用后进先出栈（LIFO，`pop()`）对应**深度优先搜索（DFS）**。
- **BFS 最优性定理**：在边权均等的无权图中，BFS 首次触及目标节点时，所对应的路径必定是边数最少的最优最短路径。
- **环路防范与状态去重**：必须通过哈希集合 `visited` 追踪所有曾被扩展的状态，否则环路将导致无限死循环，且重复状态会导致计算量指数级爆炸。

## 什么是图：从物理网络到抽象状态空间

在计算机科学中，图（Graph）是用于表达事物之间关联关系的最强有力的数据抽象。无论是现实世界中错综复杂的物理网络，还是离散数学中抽象的因果推演，只要存在实体以及实体之间的某种转移可能，我们都可以将其纳入图论的统一视界。一个图在数学上被严格定义为由两个集合构成的二元组：
$$G = (V, E)$$
其中 $V$ 是非空的顶点集合（Vertices / Nodes），代表系统所能处于的所有离散状态或实体；$E$ 是连接两个顶点的边集合（Edges），代表实体之间的关联、通路或单步转移规则。如果顶点的度数（Degree）较小，即每个节点平均只与少数几个节点相连，我们称其为稀疏图（Sparse Graph）；反之，如果绝大多数节点之间都存在直接连接，则称为稠密图（Dense Graph）。在计算机程序设计中，绝大多数搜索问题面对的都是极其巨大的稀疏图空间。

```text
       [显式实体图: 地图与网络]               [隐式状态图: 15-Puzzle]
             (Boston)                         ┌───┬───┬───┐
            /        \                        │ 1 │ 2 │ 3 │
           /          \                       ├───┼───┼───┤
       (NYC) ──────── (Providence)            │ 4 │   │ 6 │  (状态节点)
           \          /                       ├───┼───┼───┤
            \        /                        │ 7 │ 5 │ 8 │
           (Philly)                           └───┴───┴───┘
                                                    │ 合法滑动 (边)
                                              ┌─────▼─────┐
                                              │ 1 │ 2 │ 3 │
                                              │ 4 │ 5 │ 6 │
                                              │ 7 │   │ 8 │
                                              └───┴───┴───┘
```

### 顶点、边与图的分类

- **有向图 vs 无向图**：边是否存在单向性。例如单行道或网页超链接是有向边，而双向畅通的公路或无阻碍相邻网格则是无向边。
- **带权图 vs 无权图**：边是否携带代价。例如无权图每一步代价均等为 1，而带权图的边可能代表距离、耗时或票价。
- **显式图（Explicit Graph）**：所有节点与连接关系提前完全存储在内存中（例如社交网络好友关系、全国航线图）。
- **隐式图（Implicit Graph）**：节点数量极其庞大甚至无限，无法预先全部枚举。我们仅知道初始状态，并在运行时通过“合法移动规则”动态生成当前节点的相邻后继状态（例如数独、魔方、国际象棋走子树）。

### 图在 Python 中的数据结构表示

在 Python 中，最地道的图表示方式是**邻接字典（Adjacency Dictionary）**，以节点作为键，与其相连的邻居集合或列表作为值：

```python
# 显式图：以字典表示图结构
flight_graph = {
    "Boston": ["NYC", "Providence"],
    "NYC": ["Boston", "Providence", "Philly"],
    "Providence": ["Boston", "NYC", "Philly"],
    "Philly": ["NYC", "Providence"],
}
```

对于隐式图，我们通常将其封装为一个**后继生成函数（Successor Function）** `get_neighbors(state)`，该函数接收当前状态对象，动态返回其所有一步可达的新状态列表。

## 抽象寻路算法框架（Agenda-based Pathfinding）

在抽象图上寻找从起点到目标的有效路径，可以沿用我们在洪水填充中建立的议程框架。所谓抽象路径，是指在图 $G$ 中由一组连续边依次衔接而成的节点序列 $(v_0, v_1, v_2, \dots, v_k)$，其中 $v_0$ 是指定的起始状态（Start Node），$v_k$ 是满足某种终止条件的目标状态（Goal Node），序列中的任意相邻两项 $(v_i, v_{i+1})$ 必须是图中的一条合法边。

算法的核心设计思想是维护一个动态的搜索前线（Frontier）。在每一次迭代推进中，算法根据明确的调度策略从前线取出一个候选探索路径，检视其末尾端点是否已经触碰到了预设的目标；若尚未达成，则向周围未曾涉足的邻居节点伸展触角，派生出更长的候选路径重新注入前线缓冲区。这一过程不断循环推进，直至找到通向目标的有效序列，或者当搜索前线彻底干涸为空时宣布无解。

寻路算法的正确性建立在清晰的循环不变量之上：在任意轮次循环开始前，所有已经探索完毕的节点都被收纳于已访问记录中，而所有已知且等待探索的边缘路径均整齐排列在议程前线。只要有限图内存在从起点可达的解路径，并且搜索算法采用系统性的前向推进策略，算法就必定能在有限步内终止并输出正确结果。在无解的情况下，随着连通分量内的所有节点逐渐全部被录入访问集合，议程必然耗尽变为空集，算法安全退出并返回 `None`。

```text
               ┌─────────────────────────────────────┐
               │         初始化 Agenda 与 Visited     │
               └──────────────────┬──────────────────┘
                                  │
                                  ▼
                     ┌────────────────────────┐
                     │ Agenda 中是否还有路径？ │◄─────────┐
                     └────────────┬───────────┘          │
                          是      │       否             │
                                  │   ┌──────────────┐   │
                                  │   │ 返回 None    │   │
                                  │   │ (目标不可达)  │   │
                                  │   └──────────────┘   │
                                  ▼                      │
                     ┌────────────────────────┐          │
                     │ 按调度规则弹出一跳路径  │          │
                     │ path, 提取末端 curr    │          │
                     └────────────┬───────────┘          │
                                  │                      │
                                  ▼                      │
                        curr == goal ?                   │
                       /              \                  │
                   是 /                \ 否              │
                     ▼                  ▼                │
             ┌──────────────┐   ┌────────────────────┐   │
             │ 返回 path    │   │ 遍历所有邻居 nxt   │   │
             │ (成功找到解) │   │ 若未访问则加入     │   │
             └──────────────┘   │ visited 并入队     │───┘
                                └────────────────────┘
```

### 议程与已访问记录的协同机制

在路径寻优与状态空间探索中，有两个基础性的工程考量直接决定了算法能否在实际机器上跑通：

1. **防止无限环路（Cycle Prevention）**：
   在几乎所有的现实图结构中，双向可达性是常态（例如无向图中如果存在边 $(u, v)$，则必然存在反向边 $(v, u)$；在棋盘推箱子或滑块拼图中，移动后通常也能原路退回）。如果算法只盲目将相邻邻居拓展入队，搜索程序就会在两个或多个节点之间陷入无休止的“乒乓震荡”。每次往返都会生成长度加 2 的新路径，瞬间制造数以百万计的无用候选分支，直接导致系统内存爆仓崩溃。

2. **状态去重与分支剪枝（Duplicate State Pruning）**：
   在复杂的网格图或状态图中，往往存在大量“条条大路通罗马”的重聚路径（Diamond Graphs）。例如从起点向右再向下到达 $(1, 1)$，与先向下再向右到达 $(1, 1)$，其达到的物理状态是完全相同的。在边权均等的寻路场景中，后抵达该状态的探索分支必然消耗了相同或更多的步数。因此，只要我们记录了“哪些状态已经被探索过”，后续所有试图再次进入该状态的分支都可以被直接物理剪枝抛弃。

通过将每个新发现的有效节点立即登记入 `visited` 集合，我们可以严格保证图中每一个顶点至多只被探索一次，将潜在的指数级爆炸路径空间强行压缩在多项式级别。

## 调度策略的决定性影响：BFS 与 DFS 对比

抽象寻路算法最精妙之处在于：**仅仅改变从 Agenda 中取出路径的顺序，就能彻底改变整个算法的遍历拓扑与时空特性**。

### 广度优先搜索（BFS）：先进先出队列

当我们在 Agenda 末尾追加新路径（`append`），而始终从 Agenda 头部弹出候选路径（`pop(0)`）时，这就是先进先出（FIFO）队列结构。

```text
BFS 探索波前：按离起点的距离（步数）分层逐圈向外辐射
Layer 0: 起点
Layer 1: 距离起点 1 步的所有节点
Layer 2: 距离起点 2 步的所有节点
...
```

- **最优性保证**：由于路径是按步数严格单调递增被检视的，当算法首次从队列中弹出一个包含目标节点的路径时，**该路径所包含的步数必然是全局最少的**！在计算最少操作步数（如迷宫最短路、六度空间理论）时，BFS 是无权图中的标准解法。
- **空间开销**：BFS 的主要缺点是空间膨胀。在分支因子为 $b$ 的图中，第 $d$ 层的节点数高达 $b^d$，队列必须同时驻留整层前线的所有候选路径，内存消耗随深度呈指数级上升。

### 深度优先搜索（DFS）：后进先出栈

当我们在 Agenda 末尾追加新路径（`append`），同时直接从末尾弹出最新路径（`pop()`）时，这就变成了后进先出（LIFO）栈结构。

```text
DFS 探索路径：一条道走到黑，撞墙后再逐步回溯
Path: A -> B -> D -> H (深入叶子)
回溯: A -> B -> D -> I
回溯: A -> B -> E ...
```

- **空间优势**：DFS 在任意时刻只需保留当前正在探索的一条单链分支，空间复杂度仅为 $O(d)$（$d$ 为最大探索深度），内存占用极小。
- **劣势与陷阱**：DFS **绝不保证找到最优最短路径**，它往往会绕一大圈迂回路线才碰巧到达终点；在存在无限深度分支或环路的隐式图中，未设置深度上限的 DFS 会在某一条歧路上彻底迷失。

## 通用寻路器在 Python 中的泛型实现

在软件工程中，优秀的架构追求高内聚与低耦合。如果为迷宫、拼图、网络路由和单词游戏分别编写一套专用的搜索循环，不仅会产生大量重复的样板代码，而且任何局部优化都无法跨业务复用。

我们可以将图搜索算法提炼为一个完全通用的**高阶泛型寻路函数（Generic Pathfinding Engine）**。该函数自身完全不关心具体的节点究竟是经纬度坐标、整数数组、棋盘字符串还是复杂的对象实例；它唯一依赖的是调用方以高阶函数形式传入的“后继生成器”（`get_neighbors_func`）与“目标判定谓词”（`is_goal_func`）。这种将算法骨架与具体领域状态转移解耦的设计，是构建专业算法库的标准模式。

在时间复杂度与空间复杂度分析层面：
- **时间复杂度**：假设图包含 $V$ 个可达顶点与 $E$ 条边，由于每个顶点在首次加入议程时便被永久记录进 `visited` 哈希集合，因此任何顶点至多只会被弹出扩展一次。在扩展该顶点时，算法会枚举其所有的出边邻居。整场搜索过程中所有邻居检查的累加次数恰好等于总边数 $E$。利用哈希集合进行常数时间 $O(1)$ 的存在性查询，该通用 BFS 寻路器的全局时间复杂度严格收敛于线性的 $O(V + E)$。
- **空间复杂度**：空间开销由两部分组成，即已访问集合 `visited` 与待办队列 `agenda`。最坏情况下需要记录所有可达节点，因此内存开销为 $O(V)$。

值得注意的是在目标判定位置的选择上：我们在生成新状态（`next_state`）的当下立即执行目标测试，而不是等到下一次从队列头部弹出该状态时才检测。这种“提前目标检测”（Early Goal Test）的小技巧，能使算法提前整整一层循环发现目标，避免将目标节点同一层级中成百上千个同级兄弟节点无意义地推入队列，在分支因子较大的搜索中能节省极可观的运行时间。

以下是完整的通用实现代码：

```python
def find_path(start, is_goal_func, get_neighbors_func):
    """
    通用广度优先搜索 (BFS) 路径规划器。

    参数:
        start: 初始状态对象 (必须是可哈希的，如元组或字符串)
        is_goal_func: 判断当前状态是否为目标的谓词函数 (state -> bool)
        get_neighbors_func: 获取相邻有效状态的函数 (state -> iterable of states)

    返回:
        从起点到目标的完整状态元组 (start, s1, s2, ..., goal)，若不可达则返回 None
    """
    # 边缘判定：若起点即为目标
    if is_goal_func(start):
        return (start,)

    # Agenda 保存全路径元组；Visited 保存已抵达的状态
    agenda = [(start,)]
    visited = {start}

    while agenda:
        # 核心：pop(0) 实现 FIFO 队列，确保按层搜索
        current_path = agenda.pop(0)
        current_state = current_path[-1]

        # 遍历后继生成器返回的每一个相邻状态
        for next_state in get_neighbors_func(current_state):
            # 目标检测提前：在生成阶段检测目标可少走一层循环
            if is_goal_func(next_state):
                return current_path + (next_state,)

            if next_state not in visited:
                visited.add(next_state)
                # 产生拓展一步的全新路径入队
                agenda.append(current_path + (next_state,))

    return None
```

### 经典实战：字梯游戏（Word Ladder）

字梯问题（Word Ladder，由《爱丽丝梦游仙境》作者刘易斯·卡罗尔于 1877 年发明）是一个极佳的隐式图建模案例。游戏规则如下：给定两个长度相等的英文单词（如从 `cold` 演变至 `warm`），每次只能更改其中一个字母，且每一次变换所产生的新词汇都必须存在于标准英语词典中。求解目标是找到步数最少的演变阶梯。

在这个问题中，如果我们试图预先将整个英文词典构建为显式的邻接表，词库可能包含上万甚至数十万个词汇，预计算两两之间的汉明距离将极其耗时且消耗大量常驻内存。相反，我们将其建模为一个**隐式状态图**：每一个单词是一个顶点，边存在于任意两个仅相差一个字符的合法词汇之间。

对于长度为 $L$ 的单词，其可能的单字符替换尝试只有 $25 	imes L$ 种可能（英语字母表共 26 个字母，排除自身）。我们只需在生成邻居时，枚举每个字符位置上的所有可能替换，并利用哈希集合以 $O(1)$ 复杂度判定该变形是否在有效词库集合 `WORDS` 中。

借助我们刚才编写的通用泛型 `find_path` 引擎，整个字梯问题的求解代码变得极其精简优雅：

```python
# 词库集合
WORDS = {"cold", "cord", "card", "ward", "warm", "bold", "bard"}

def get_word_neighbors(word):
    """生成只改变一个字符且在词库内的所有合法相邻单词。"""
    neighbors = []
    alphabet = "abcdefghijklmnopqrstuvwxyz"
    for i in range(len(word)):
        for char in alphabet:
            if char != word[i]:
                new_word = word[:i] + char + word[i+1:]
                if new_word in WORDS:
                    neighbors.append(new_word)
    return neighbors

# 寻找最优变换梯子
solution = find_path(
    start="cold",
    is_goal_func=lambda w: w == "warm",
    get_neighbors_func=get_word_neighbors
)
print("最优单词路径:", solution)
# 输出: ('cold', 'cord', 'card', 'ward', 'warm')
```

## 我的理解与工程洞察

::: insight 抽象建模的力量：将逻辑难题转化为图搜索
计算机科学最令人震撼的领悟之一，是发现浩瀚的现实工程问题本质上是同一个数学模型的投影。

在软件设计中应用图搜索时，需要牢记三条工程直觉：
1. **显式与隐式的决策权衡**：如果状态空间较小（如城市交通网、网络路由表），预先构建并常驻邻接字典能够实现最快的拓扑检索；而在大型游戏或组态搜索中，状态组合呈天文数字，**按需动态生成后继（Lazy Evaluation）**是唯一可行的路径；
2. **状态可哈希性（Hashability）**：`visited` 集合的高性能完全依赖于状态的哈希查找。因此，表示状态的对象必须是不可变对象（Immutable），例如用不可变元组代替列表，用冻结集合（`frozenset`）代替普通集合；
3. **空间瓶颈与双向搜索（Bidirectional Search）**：BFS 在深度增大时最容易因队列爆满而遭遇内存击穿（Out-Of-Memory）。在起点与终点皆明确且边可逆的场景下，从起点和终点同时发起向内辐射的双向 BFS，能将搜索分支规模从 $b^d$ 骤降至 $2 \cdot b^{d/2}$，带来数量级的性能跃迁。
:::
