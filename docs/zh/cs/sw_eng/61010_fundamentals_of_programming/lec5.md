# Lec 5 递归基石与递归环境模型（Recursive Patterns）

> 参考资料：[Recursive Patterns](https://py.mit.edu/fall26/readings/recursion)

## TL;DR

- **递归的两大支柱**：每个完备的递归函数必须拥有至少一个不发生递归调用的**基准情形（Base Case）**，以及若干将问题规模单调缩小向基准情形推进的**递归情形（Recursive Case）**。
- **环境模型与调用栈推演**：每一次递归调用都会在内存栈中开辟独立的局部帧；深层调用完成返回后，其局部帧被释放，计算结果逐级向上传递。
- **“信任跳跃”思考法**：编写递归分支时，切忌陷入逐层跟踪的人脑展开陷阱，应假设递归子调用已经正确返回了子问题的解，只需思考如何将其与当前第一项合并。
- **列表经典递归范式**：通过首元素（`x[0]`）与剩余切片（`x[1:]`）的分解，结合 `doctest` 进行边界测试与契约验证。

## 递归的本质：归约思维与结构分解

递归（Recursion）是计算机科学中最核心的计算思维之一。当一个过程在其内部直接或间接地调用自身来定义或求解时，便发生了递归。

初学者在接触递归时常常感到眩晕：**为什么一个尚未编写完成的函数，可以在自己的函数体内部直接调用自己？**

破解这一困惑的钥匙在于“归约”（Reduction）思维：我们并不是在无休止地自言自语，而是**将一个复杂的、宏观的大问题，归约为一个结构相同但规模更小或更简单的同构子问题**。

```text
计算 factorial(4):
  factorial(4) ── 等待 4 * factorial(3) ──► 4 * 6 = 24  (最终解)
    factorial(3) ── 等待 3 * factorial(2) ──► 3 * 2 = 6  ▲
      factorial(2) ── 等待 2 * factorial(1) ──► 2 * 1 = 2  │ 逐
        factorial(1) ── 等待 1 * factorial(0) ──► 1 * 1 = 1  │ 层
          factorial(0) ── 触发 Base Case ───────────────► 1  ┘ 回
                          (无需递归，直接返回 1)               传
```

### 递归定义的两大基本要素

任何正确且能成功终止的递归算法，必须且只能由以下两部分构成：

1. **基准情形（Base Cases）**：问题的最平凡、最小规模实例。在该情形下，答案显而易见，直接计算并返回结果，**严禁再次发起任何递归调用**。
2. **递归情形（Recursive Cases）**：将当前输入拆分为更小的数据片段，并在缩小的子输入上发起自调用。每次递推必须确保**子问题距离某个基准情形更近一步**。

以非负整数阶乘 $n!$ 为例，其严格的数学递归定义为：
$$
n! = \begin{cases} 
1 & \text{if } n = 0 \quad (\text{基准情形}) \\ 
n \times (n-1)! & \text{if } n > 0 \quad (\text{递归情形}) 
\end{cases}
$$

转化为 Python 实现：

```python
def factorial(n):
    """
    计算非负整数 n 的阶乘。
    
    >>> factorial(0)
    1
    >>> factorial(4)
    24
    """
    if n == 0:
        return 1
    else:
        return n * factorial(n - 1)
```

### “信任跳跃”（Leap of Faith）心智模型

编写递归代码时最容易出现的思维误区，是试图在脑海中一层层模拟所有嵌套调用。这种“人肉堆栈”展开会迅速耗尽大脑的工作记忆。

正确的工程策略是**信任跳跃（Leap of Faith）**：
1. 先写好并严格检查基准情形的正确性；
2. 在编写递归情形时，**先假设子问题调用 `factorial(n-1)` 已经完美、正确地计算出了结果**；
3. 集中全部精力思考：在拿到子问题的正确解后，我只需对当前输入 $n$ 执行什么计算，就能拼接拼装出当前 $n$ 的最终解？（在这里，只需简单地乘以 $n$）。

只要基准情形正确，且每次递归调用的参数都在向基准情形单调收敛，数学归纳法（Mathematical Induction）就能严格保证全流程的绝对正确。

## 递归在环境模型中的执行机理

很多程序员担心：递归调用会不会把之前的变量搞混？我们可以通过执行环境模型观察 Python 在底层的严格秩序。

### 调用栈帧的层叠生命周期

每当 Python 遇到一个函数调用时，都会在栈区分配一个全新的局部执行帧：
- 当调用 `factorial(3)` 时，创建帧 F1，其中局部变量 `n = 3`；
- 执行到 `return 3 * factorial(2)` 时，乘法无法立即完成，当前 F1 暂停等待。Python 为内层调用分配新帧 F2，其中局部变量 `n = 2`；
- 依此类推，栈上会依次叠放 F1、F2、F3 直至触发基准情形的 F4（`n = 0`）；
- F4 计算出结果 `1` 并返回，F4 帧随即弹出销毁；
- 控制权返回至 F3，F3 取得返回值后计算 `1 * 1 = 1` 并返回，F3 销毁；
- 结果一路沿着栈回溯，直至最初的 F1 计算出 `3 * 2 = 6`。

每一个帧内部的局部变量 `n` 都是各自物理独立的，彼此之间绝不会产生任何命名污染或覆盖。

### 递归深度与栈溢出防护

由于每个尚未返回的递归帧都会占据一定的栈内存，Python 为了防止死循环耗尽操作系统内存，设置了一个默认的最大递归深度保护（通常为 1000 层）：

```python
import sys
print(sys.getrecursionlimit())  # 默认输出 1000 左右
```

如果递归函数遗漏了基准情形，或者递推步没有让参数向基准情形收敛（例如误写成 `factorial(n)` 而非 `factorial(n-1)`），程序会不断开辟新帧，最终崩溃并抛出经典的异常：
`RecursionError: maximum recursion depth exceeded`

## 列表上的经典递归模式

除了处理数字，递归在处理序列与容器数据结构时展现出无与伦比的优雅。

### 列表求和：从空列表到首尾分解

考虑对一个数字列表求和的函数 `sum_list(x)`：
- **基准情形**：什么是最简单的列表？空列表 `[]`！其元素之和显然为 0。
- **递推策略**：对于非空列表，我们将其分解为第一个元素 `x[0]` 与剩余列表切片 `x[1:]`。如果递归调用能算出 `sum_list(x[1:])`，加上 `x[0]` 就是全列表的和！

```python
def sum_list(x):
    """
    递归计算列表 x 中所有数字的总和。

    >>> sum_list([])
    0
    >>> sum_list([3, 7, 2])
    12
    """
    if not x:
        # 基准情形：空列表
        return 0
    else:
        # 递归情形：首元素 + 剩余切片之和
        return x[0] + sum_list(x[1:])
```

### Doctest 驱动测试开发

注意上面代码注释中的 `>>>`。Python 内置的 `doctest` 模块能够自动提取文档注释中的交互式用例并执行断言验证：

```python
if __name__ == "__main__":
    import doctest
    doctest.testmod()
```

将测试用例直接写在函数的文档注释中，既充当了无可替代的可执行说明文档，又能在持续集成中防范回归，在递归算法开发中极其高效。

### 嵌套列表求和：迈向树形递归

在真实软件开发中，数据往往不会平铺直叙地排列成单一维度的扁平列表。考虑处理诸如 JSON 数据包、文件系统目录树或者由括号嵌套构成的算术表达式。这类数据的显著特征是具有不可预测的任意嵌套深度（例如 `[1, [2, [3, 4]], 5]`）。

面对这种结构，任何试图编写多层嵌套 `for` 循环的过程式方法都会彻底失效，因为你永远无法在编码期预知数据究竟嵌套了三层、五层还是一百层。而递归在这类结构面前展现出了近乎魔法般的优雅。

我们只需将当前问题拆分为三种清晰的互斥语义分支：
1. 列表为空：求和结果直接为 0；
2. 首元素本身依然是一个列表：这意味着遇到了内部的分支节点。我们分别对首元素子列表调用 `sum_nested(x[0])`，以及对剩余同级列表调用 `sum_nested(x[1:])`，并将两者的计算结果相加；
3. 首元素是普通数字：这对应着树的叶子节点。我们直接取得该数字，并与剩余列表的递归求和结果相加。

```python
def sum_nested(x):
    """
    递归计算任意嵌套深度的列表中所有数字之和。

    >>> sum_nested([1, [2, [3, 4]], 5])
    15
    >>> sum_nested([])
    0
    """
    if not x:
        return 0
    elif isinstance(x[0], list):
        # 首元素本身还是列表：双向递归深入
        return sum_nested(x[0]) + sum_nested(x[1:])
    else:
        # 首元素是普通数字
        return x[0] + sum_nested(x[1:])
```

在 `sum_nested` 中，我们第一次看到了在单次函数体内发起**多次分支递归调用**（Branching Recursion）。当遇到子列表时，函数同时向树的深处（深度展开）以及向同级的后续元素（广度推进）同时开辟新的栈帧。这种分形式的求解机制，正是下一讲深入探讨树与图等高维非线性数据结构的理论基石。

## 递归子问题的选择策略与分解范式

设计递归算法的关键艺术，在于如何为复杂对象挑选最合理的子问题分解方案。

### 首元素与剩余切片（Head & Tail）

这是线性序列最常用的分解方式，如上述的 `x[0]` 与 `x[1:]`。其直观性强，但在 Python 中，每次切片 `x[1:]` 都会在内存中浅拷贝一个长度减 1 的新列表，整个计算过程的总拷贝时间复杂度为 $O(N^2)$。在工业级优化中，我们可以通过传递索引下标 `sum_list_fast(x, index=0)` 消除切片复制，将时间复杂度降回线性的 $O(N)$。

### 二分分解（Divide and Conquer）

将序列从中间均分为两半：
```python
mid = len(x) // 2
return solve(x[:mid]) + solve(x[mid:])
```
这种分解模式将调用栈的最大深度从线性的 $O(N)$ 戏剧性地降低至对数级别的 $O(\log N)$，是归并排序（Merge Sort）与快速幂等高效算法的灵魂。

### 二叉选择树：子序列生成问题

在算法设计中，生成组合对象（如所有子集、排列组合、布尔可满足性真值指派）是经典的一类计算任务。考虑数学上的子集生成问题：给定一个序列，要求生成其所有的子序列（Subsequences）。一个包含 $n$ 个元素的序列，其所有子序列的总数恰好为 $2^n$（幂集的大小）。

如果用循环来编写这个过程，需要极其复杂的位运算掩码技巧。而如果转换到递归视角，整个问题便显现为一个清晰的**二叉决策树（Binary Decision Tree）**。

对于序列中的当前首元素 `first`，世间所有合法的子序列在逻辑上必然属于以下两类互斥情形之一：
- **不包含 `first` 的子序列**：这恰好等价于从剩余部分 `rest` 中提取出的所有可能子序列；
- **包含 `first` 的子序列**：这恰好是在“从剩余部分提取出的所有可能子序列”的基础之上，把 `first` 逐一追加到每一个候选者的开头！

只要我们递归求得 `rest` 的所有子序列集合 `subs_without_first`，就可以通过简单的列表推导式构造出第二部分，最后将两组列表直接拼接合并。

```python
def subsequences(seq):
    """
    生成序列 seq 的所有子序列列表。

    >>> sorted(subsequences("ab"))
    ['', 'a', 'ab', 'b']
    """
    if not seq:
        # 基准情形：空序列的唯一子序列是空字符串自身
        return [""]
    
    first = seq[0]
    rest = seq[1:]
    
    # 递归步骤 1: 假设已经完美求得不包含首元素的所有子序列
    subs_without_first = subsequences(rest)
    
    # 递归步骤 2: 将首元素拼接在每个子序列前面，生成包含首元素的一半宇宙
    subs_with_first = [first + s for s in subs_without_first]
    
    # 步骤 3: 归并两个分支的全部解并返回
    return subs_without_first + subs_with_first
```

每一次递归调用都分支为“选当前项”与“不选当前项”两条决策路径，这使得函数在执行过程中形成了一棵高为 $n$、叶子节点总数为 $2^n$ 的决策树。这不仅完美展示了递归在组合数学问题上的强大抽象表达力，更是后续第七讲回溯搜索（Backtracking）与剪枝算法的直接先导模型。

## 我的理解与工程洞察

::: insight 递归的本质是自相似性与数学归纳法
许多程序员抗拒递归，是因为我们习惯于“按时间轴一步步操作”的命令式时间思维。而递归是一种**空间与结构的结构性声明思维**。

深入理解递归，需要建立三层认知跃迁：
1. **递归与归纳法完全同构**：基准情形对应数学归纳法的基础步骤（$n=1$ 成立），递推情形对应归纳步骤（若 $n=k$ 成立，则可证明 $n=k+1$ 成立）。写递归时，必须在内心完成这一严谨的逻辑闭环；
2. **警惕隐性切片复制开销**：在高级语言中使用 `lst[1:]` 写递归极度舒适，但在处理大规模数据时，隐式内存拷贝会悄无声息地吞噬性能。若遇到长序列递归，应果断改用索引传参或迭代方案；
3. **分清线性递归与分支递归**：单次调用的线性递归（如单链表遍历）绝大多数都可以被无痛改写为 `while` 循环；而具有自相似树形结构的问题（如抽象语法树解析、XML/JSON 遍历、分治排序），递归才是最为纯粹、Bug 最少的天选之解。
:::
