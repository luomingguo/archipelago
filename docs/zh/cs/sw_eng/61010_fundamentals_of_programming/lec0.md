# Lec 0 设计程序指南与命令行工具（Designing Programs & Command Line）

> 参考资料：[Designing Programs](https://py.mit.edu/fall26/readings/design) · [Coding Style](https://py.mit.edu/fall26/readings/style) · [Command Line](https://py.mit.edu/fall26/readings/command_line)

## TL;DR

- **核心原则**：严禁在未形成清晰计划前盲目写代码。借鉴波利亚四步法（理解、计划、实施、回顾），将复杂问题分解为独立可测试的子单元。
- **自顶向下设计**：在编写具体逻辑前，先写函数契约（docstring）与伪代码注释，明确输入输出规范与前置后置条件。
- **现代化工具链**：利用 Python 虚拟环境（`venv`）隔离项目依赖，通过 `pytest` 进行测试驱动开发，利用 `ruff` 与交互式 REPL（`python -i`）实现毫秒级排错反馈。

## 程序设计通用方法论

经验丰富的工程师之所以能迅速写出优雅高效的程序，核心不在于死记语法，而在于掌握了一套将未知混乱问题条理化的心智框架。

```text
       ┌───────────────┐
       │ 1. 理解问题   │ 明确输入输出、边界条件与极端用例
       └───────┬───────┘
               │
       ┌───────▼───────┐
       │ 2. 制定计划   │ 分解子问题、设计数据表示、拟定纯函数
       └───────┬───────┘
               │
       ┌───────▼───────┐
       │ 3. 实施计划   │ 自顶向下填充伪代码、保持增量单测
       └───────┬───────┘
               │
       ┌───────▼───────┐
       │ 4. 回顾反思   │ 消除重复计算、优化复杂度、清理风格
       └───────────────┘
```

### 编程思维与波利亚四步法

乔治·波利亚在《How to Solve It》中提出的解题框架，是软件工程架构设计的基石。面对复杂软件需求，应遵循四阶段渐进推演：

#### 阶段一：透彻理解问题与边界

在敲下任何代码之前，必须彻底明确问题的规格说明：

- **输入与输出的数据表示**：输入是嵌套列表、字典还是元组？输出是原地修改还是返回全新对象？
- **构造极小用例**：用纸笔手动演算一到两组最简单的输入输出示例。
- **发现边缘条件**：空集合、负数、极大值、重复元素、边界越界等异常输入应如何应对？

#### 阶段二：制定解题计划与分解子任务

将主干流程分解为若干相互独立的子任务：

- **寻找输入与输出的转换算子**：需要哪些高级中间变换步骤？
- **确定必要的状态追踪**：除了原输入外，是否需要辅助哈希表（集合/字典）记录已访问状态？
- **评估已知模式**：当前问题是否与已知的图遍历、回溯、动态规划或贪心问题同构？

#### 阶段三：分步编码与增量验证

- 先实现基础的纯函数与辅助算子（helper functions）。
- 每完成一个辅助函数，立即用小用例验证其正确性，切忌将所有模块拼装在一起后才开始第一次运行。

#### 阶段四：回顾反思与代码重构

- **DRY 原则（Don't Repeat Yourself）**：是否有复制粘贴的重复计算？
- **时间与空间复杂度**：是否存在不必要的多层嵌套循环或高代价的列表切片拷贝？
- **命名与自解释性**：变量与函数命名是否精准表达了业务概念？

## 模块化与工程设计流程

在大型工程与复杂算法实现中，面对一个数十行甚至数百行规模的任务，直接从细节入手极易顾此失彼。业内推荐采用“文档字符串驱动”（Docstring-driven）与“注释骨架法”组织代码，将精力优先放在高层契约上。

### 伪代码与文档字符串驱动设计

编写代码的第一步是确定函数的类型签名、前置假设与后置保证。先为函数编写清晰的 docstring，定义好输入输出与异常情形，再用伪代码填充中间骨干。通过这种方式，可以在编码初期就彻底厘清函数的边界：

通过这种先定契约后写实现的模式，程序员可以强制自己在深入具体分支条件前理顺数据流。当需要与队友协作或后期重构时，完备的文档字符串和明确的步骤分解也能大幅减少理解成本。随后，我们可以针对其中的每一个子步骤独立编写小型辅助函数，使得整个系统的测试与调试都能够局限在最小故障半径之内。这种防御性设计策略在处理诸如迷宫搜索或大作业等大型逻辑时尤为有效。

## 现代命令行开发工具链

高效的开发体验依赖于顺手的现代命令行基础设施。

### 虚拟环境隔离（venv）

不同项目依赖的第三方库版本各异，必须使用独立的虚拟环境隔离 Python 环境：

```bash
# 创建虚拟环境
python3 -m venv .venv

# 激活虚拟环境 (macOS/Linux)
source .venv/bin/activate

# 导出与还原依赖
pip freeze > requirements.txt
pip install -r requirements.txt

# 退出虚拟环境
deactivate
```

### 静态代码检查与格式化（ruff 与 pylint）

使用静态分析工具在编码期捕捉语法错误、未定义变量及代码异味：

- **Ruff**：采用 Rust 编写的极速静态检查器，可毫秒级完成全项目扫描：
  ```bash
  # 快速静态扫描
  ruff check .

  # 自动修复符合规范的问题
  ruff check . --fix
  ```
- **Pylint**：更深度的语义分析工具，可生成规范评分：
  ```bash
  pylint my_module.py
  ```

### 自动化测试实践（pytest）

编写清晰的单元测试是保证代码长期稳健的核心习惯：

```bash
# 运行指定测试文件
pytest test.py

# 显示详细测试用例名称与耗时
pytest -v test.py

# 遇到第一个失败即终止（便于单点排错）
pytest -x test.py

# 打印代码中的 print 输出
pytest -s test.py

# 按名称模式过滤测试用例
pytest -k "test_edge_case" test.py
```

### 交互式调试技巧（REPL 与断点）

利用 Python 自带的交互式环境可以极快验证函数内部状态：

```bash
# 脚本执行完毕后直接进入交互式 REPL，保留当前所有全局变量与函数定义
python3 -i lab.py
```

在交互式环境中可直接调用 `f(test_val)` 检查输出，或在代码关键行插入 `breakpoint()` 启动 `pdb` 步进调试。

## 我的理解与工程洞察

::: insight 架构思维：控制状态是软件设计的终极议题
编程初学者常常急于写出第一行代码，往往陷入“改了这里坏了那里”的修补陷阱。软件工程中超过 80% 的难以定位的 Bug 源自不可控的可变状态与隐含边界。

优秀的程序设计应当追求**确定性**与**可测试性**：
1. **单一职责与纯函数优先**：若一个函数只依赖入参且无隐式副作用，它就可以被极其轻松地单测、复用与重构；
2. **提前收敛边界条件**：在函数开头通过断言（`assert`）或防御性守卫拦截非法输入，比在嵌套深处崩溃更容易维护；
3. **工具即心智放大器**：把 `pytest` 和 `ruff` 作为日常代码编写的伴随进程，形成“红灯-绿灯-重构”的敏捷正向循环。
:::
