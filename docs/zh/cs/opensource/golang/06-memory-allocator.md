# 内存管理与分配器实现

## TL;DR

- Go 内存分配器脱胎于 TCMalloc，构建了“`mcache`（P 本地无锁）$\to$ `mcentral`（按大小分级加锁）$\to$ `mheap`（全局大页锁）”的三级多层级缓存体系。
- 运行时将对象分为 67 种 size class，并区分是否包含指针衍生为 134 种 `spanClass`；标记为 `noscan` 的无指针对象在垃圾回收时直接跳过内部扫描。
- 编译期逃逸分析决定变量在栈还是堆上分配，返回值指针、接口装箱以及闭包跨栈捕获是触发逃逸的核心场景。
- Goroutine 栈采用连续栈模型，初始为 2KB，触发栈检查时通过全局双倍申请与全量指针重定位完成无缝扩栈。

## 分配器三级分层架构

在大规模多核高并发环境下，如果所有 Goroutine 在分配内存时均竞争全局堆锁，系统吞吐量将因锁争用而急剧崩塌。传统操作系统中通用的 `malloc` 实现通常需要维护全局自由内存链表，在成千上万并发线程竞争时会产生严重的 CPU 核心自旋风暴。

Go 借鉴了 Google TCMalloc（Thread-Caching Malloc）思想，以逻辑处理器 P 为隔离单元，构建了三级渐进缓存体系。其核心逻辑是：越靠近 CPU 执行现场的层级越快、越具备高并发亲和力，绝大多数小对象的分配请求都在无锁的 P 本地缓存中闭环消化。

这一设计同时兼顾了内存碎片整理与局部性：通过将内存划分为离散的页集合与预定规格的尺寸分类，分配器避免了传统基于伙伴系统或首次适应算法可能产生的外部碎片。同时，通过在本地线程缓存预留热点内存，显著提升了现代多核 CPU 的 L1/L2 缓存行命中率。

在整体设计目标上，Go 内存分配器追求以下三项核心指标：
- **极小化锁争用**：在多核扩展下，不同 P 上的分配操作必须互不阻塞，消除并发扩展的阿姆达尔定律瓶颈。
- **内存分配低延迟**：通过预先切分好的槽位链表和位图，使对象的物理分配降至数条汇编指令级别。
- **无缝协同 GC**：内存块元数据与三色标记位图严格对齐，清扫与分配紧密耦合，支持惰性并发回收。

在具体的分配路由设计中，三级架构展现出鲜明的分级回退特征：
- **第一级 mcache 极速无锁层**：运行在特定 P 上的 Goroutine 优先从绑定的本地 `mcache` 分配。由于同一物理时刻单个 P 仅由一个 M 承载，因此此过程无需任何互斥锁，指令周期可直接媲美栈分配。
- **第二级 mcentral 中心分级缓冲层**：当 `mcache` 的特定规格 span 耗尽槽位时，向对应的 `mcentral` 申请置换。由于锁粒度严格按 134 种 `spanClass` 进行细分，申请 16 字节对象的线程绝不会阻塞申请 64 字节对象的线程。
- **第三级 mheap 全局大页分配层**：当 `mcentral` 没有空闲页时，才会向全局唯一的 `mheap` 申请页面切割。`mheap` 作为物理内存与运行时的唯一中枢，持有全局互斥锁并在不足时调用 `mmap` 系统调用向 OS 扩张虚拟内存。

整个分层拓扑与执行流向如下所示：

```text
               +-----------------------------+
               |  Goroutine 对象分配请求      |
               +-----------------------------+
                              │
               ┌──────────────┴──────────────┐
         编译期逃逸分析                  逃逸至堆
         (栈上分配, 零 GC)              mallocgc()
                                             │
               ┌─────────────────────────────┼─────────────────────────────┐
               ▼                             ▼                             ▼
       Tiny 对象 (< 16B 且无指针)     Small 对象 (16B ~ 32KB)       Large 对象 (> 32KB)
       多对象合并打包分配             按 size class 规格路由        直通全局 mheap
               │                             │                             │
               └──────────────┬──────────────┘                             │
                              ▼                                            │
               +-----------------------------+                             │
               | mcache (P 本地缓存, 完全无锁) |                             │
               +-----------------------------+                             │
                              │ miss                                       │
                              ▼                                            │
               +-----------------------------+                             │
               | mcentral (中心缓存, 分级锁)  |                             │
               +-----------------------------+                             │
                              │ miss                                       │
                              ▼                                            │
               +-----------------------------------------------------------+
               |              mheap (全局页分配器, 全局大锁)                  |
               +-----------------------------------------------------------+
                              │ miss
                              ▼
               +-----------------------------+
               |     操作系统内核 (mmap/Arena)  |
               +-----------------------------+
```

每一级缓存不仅作为下一级的数据缓冲，还承担着隔离锁粒度的关键作用：
1. **本地分配路径（Fast Path）**：针对大部分 32KB 以下的对象，直接在当前线程绑定的 `mcache` 中命中。此时完全不涉及任何跨核心通信与原子 CAS 开销，整个内存分配流程高度内联。
2. **中心协调路径（Medium Path）**：当本地 span 被耗尽时，触发 `mcache.refill` 向对应 `mcentral` 申请换入新 span。此时只需争夺该规格独享的细粒度互斥锁，多核扩展性极佳。
3. **全局后备路径（Slow Path）**：当中心缓存也无法满足需求时，升级到 `mheap` 执行页级分配或向操作系统申请新的 Arena 虚拟空间。由于该路径触发频次被前两级缓存大幅摊薄，全局锁的争用在生产环境中被牢牢压制在极低水平。

## 核心数据结构

### 内存管理基元：mspan

`mspan` 是 Go 分配器管理堆内存的最基本物理单元。无论是微小对象还是跨页的大结构体，在物理内存上最终都落在一个或多个 `mspan` 之中。

一个 `mspan` 代表一段连续的虚拟内存区域，其尺寸严格以 **8KB 内存页（Page）**的整数倍递增。为了支持无碎片的高速分配，小对象所使用的 `mspan` 会在初始化时被均等切割为特定大小的固定槽位（Object Slot）。同时，span 内部维护了一个位图结构用于标记槽位的占用情况，寻找可用槽位等价于快速的位运算扫描：

```go
type mspan struct {
    next      *mspan     // 链表后继节点
    prev      *mspan     // 链表前驱节点
    startAddr uintptr    // 该 span 对应虚拟内存起始地址
    npages    uintptr    // 包含的 8KB 物理页数
    freeindex uintptr    // 下一个空闲槽位的索引
    nelems    uintptr    // 槽位（Object Slot）总数
    allocBits *gcBits    // 标记槽位是否已分配的位图
    spanclass spanClass  // 对应的大小规格与指针标记
}
```

每个 `mspan` 在生命周期中由垃圾回收器驱动其状态演进：在清扫（Sweep）阶段，未被标记为存活的槽位位图会被重置，从而无缝回归为可分配状态。

### size class 与 span class

为了最大程度降低内存外部碎片，Go 将 32KB 以内的小对象划分为 **67 个固定大小规格（size class）**（如 8B、16B、24B、32B 直至 32KB）。

每个 size class 针对垃圾回收机制派生出两种变体：
- **`scan`**：对象内部包含指针，GC 标记阶段必须对其内部引用的下游对象递归扫描。
- **`noscan`**：纯标量数据（如 `[]byte`、`string` 数据块、纯整数），GC 时无需向下递归，直接跳过扫描。

由此产生 $67 \times 2 = 134$ 种不同的 **`spanClass`**。

### mcache、mcentral 与 mheap

1. **`mcache`（P 本地独占）**：每个逻辑处理器 P 独占一份 `mcache`。它维护着一个包含 134 个 `*mspan` 的指针数组，每个 spanClass 对应一个当前活跃的物理 span。由于同一时刻只有一个 Goroutine 在 P 上执行分配，从 `mcache` 分配槽位**全程无锁**，速度与栈分配相当。
2. **`mcentral`（全局中心分类池）**：全局共存在 134 个 `mcentral` 实例。每个 `mcentral` 内部维持两组 span 集合（有空闲槽位的 `partial` 与满载的 `full`），并细分为已清扫和未清扫状态。**锁是细粒度按 `spanClass` 分离的**，申请不同规格内存的线程之间互不干扰。
3. **`mheap`（全局虚拟页管理器）**：统筹管理 Go 运行时的整个虚拟地址空间。当 `mcentral` 耗尽空闲 span 时，加全局锁向 `mheap` 索取连续空闲页；若 `mheap` 内存不足，则调用 `mmap` 向操作系统申请新的 64MB Arena 块。

## 三类对象的分配路径

分配入口统一汇聚于 `runtime.mallocgc`，依据目标内存尺寸分为三条执行流：

### 微对象分配：Tiny（< 16B 且无指针）

对于小于 16 字节且不含指针的小变量（如布尔值、单个数值），如果为每个对象单独开辟槽位将产生巨大的内部对齐碎片。
Tiny 分配器将多个微小对象**合并填充至同一个 16 字节的物理槽位中**，通过偏移量 `tinyoffset` 顺序推进放置。

### 小对象分配：Small（16B ~ 32KB）

这是 Go 程序绝大部分堆内存分配的主路径：
1. 计算大小并对齐至对应的 size class，确定 `spanClass`。
2. 检索当前 P 的 `mcache.alloc[spanClass]`，在当前 span 的 `allocBits` 位图中快速检索空闲槽位。**命中即返回，全程无锁**。
3. 若当前 span 已满，向所属规格的 `mcentral` 申请替换一个包含空闲槽位的 span（仅占用特定规格的细粒度锁）。
4. 若 `mcentral` 亦无空闲 span，向 `mheap` 申请空闲页重组构建 span。

### 大对象分配：Large（> 32KB）

大于 32KB 的超大内存块直接绕过 `mcache` 和 `mcentral`，通过大锁直接由全局 `mheap` 按需切分连续的 8KB 虚拟页进行供应。

::: insight
针对热路径上频繁创建的大对象（如批量读写的 64KB 网络 Buffer），直接触发 `mallocgc` 大对象路径会导致频繁争夺 `mheap` 全局锁并引发页表抖动。工程实践中应当使用 `sync.Pool` 予以长期复用，将大对象重分配频率压制至极低水平。
:::

## 编译期逃逸分析（Escape Analysis）

逃逸分析是 Go 编译器在静态编译阶段推导对象生命周期、决定其分配在栈还是堆的核心算法。编译器遵循“**逃逸则入堆，未逃逸则留栈**”的准则。

查看编译器逃逸决策：
```bash
go build -gcflags="-m -m" main.go
```

### 经典逃逸场景与触发机理

1. **向外返回局部变量指针**：
   ```go
   func CreateUser() *User {
       u := User{Name: "Alice"}
       return &u // u 的生命周期逃离了当前函数栈帧，必须在堆上分配
   }
   ```
2. **赋值给接口（装箱隐蔽逃逸）**：
   在向 `interface{}`（或 `any`）传参时，由于编译期无法确定具体实现类的物理内存体积，编译器通常将实体对象移至堆中，并将接口的 `data` 指针指向堆内存。常见陷阱即为频繁调用 `fmt.Println(val)` 导致的无意识逃逸。
3. **闭包变量捕获（跨作用域引用）**：
   当函数内部的闭包函数引用了外部环境变量，且该闭包本身的生命周期逃脱了外层函数时，被捕获的变量将被提升至堆中。
4. **编译期不可知长度或超大动态切片**：
   ```go
   s := make([]int, n) // n 为动态入参变量，编译期无法推算栈帧体积，强制逃逸到堆
   ```

## 动态连续栈机制

与 C/C++ 固定分配 2MB–8MB 线程栈不同，每个 Goroutine 初始仅分配 **2KB** 栈内存。

在早期（Go 1.3 之前），Go 采用“分段栈（Segmented Stack）”，通过链表连接不连续的栈片段。该方案存在致命的“热分裂（Hot Split）”缺陷：当循环恰好落在栈扩容的临界边界时，频繁的分配与释放会导致性能灾难性衰退。

Go 1.4+ 彻底切换为**连续栈（Contiguous Stack）**架构：
1. **栈边界检查**：函数执行前校验 `SP < stackguard0`。
2. **整体分配并倍增迁移**：触发扩容时，调用 `newstack` 在堆上分配一个**容量翻倍（2x）**的全新连续内存块。
3. **物理拷贝与指针修正**：将旧栈的所有数据按字节完整拷贝到新栈空间，并依据编译期生成的栈图（Stack Map），**逐个修正所有指向栈内存的内部指针地址**，确保指针全部指向新栈位置，随后安全回收旧栈。
