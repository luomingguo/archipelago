# Lec 21 安全性：拜占庭容错（BFT）

## TL;DR

- PBFT 在异步网络中实现了首个实用的拜占庭容错状态机复制，复杂度从指数级降至多项式级。
- 节点阈值约束：总节点数须满足 $3f+1$ 才能容忍最多 $f$ 个任意恶意或串通的拜占庭节点，法定多数 Quorum 大小为 $2f+1$。
- 三阶段协议流程：通过 Pre-prepare、Prepare 与 Commit 三阶段广播与消息认证码（MAC）证明，保证在视图变更中全局全序不被篡改。
- 安全性与活性权衡：在异步网络中始终保证安全性（Safety）；活性（Liveness）依赖弱同步假设（如指数退避视图超时）避免死锁。

## 一、背景：为什么需要 BFT？

此前的容错协议（Raft、Paxos 等）均假设**崩溃故障（Crash Fault / Fail-Stop）**：节点要么正常运行，要么完全停止响应。现实中还存在更危险的一类故障：

::: definition 拜占庭故障（Byzantine Fault）
节点在故障时可以产生任意行为：发送错误数据、向不同节点发送矛盾消息、假装正常但暗中破坏状态、选择性地不回复某些节点……故障节点不遵守任何协议规则。

典型来源：服务器被黑客攻陷（软件漏洞 / 密钥泄漏）、内部恶意节点、硬件计算错误。
:::

**拜占庭 vs 崩溃故障**：

| 维度 | 崩溃故障（Raft） | 拜占庭故障（PBFT） |
|------|---------------|-----------------|
| 故障节点行为 | 停止响应 | 可任意撒谎、发矛盾消息 |
| 最少节点数 | 2f+1 | **3f+1** |
| 消息复杂度 | O(n) | O(n²) |
| 延迟 | 低 | 高 |
| 应用场景 | 内部可信集群 | 开放/不可信环境 |

**历史上 BFT 为何少用**：实现复杂、消息量大、成本高。大多数系统依靠**预防**（防火墙、签名、隔离）和**检测**（入侵检测、审计日志）而非容忍拜占庭行为。

**近年复兴原因**：区块链重新引发对"恶意参与者共识"的需求。比特币用 PoW 解决了这个问题，但吞吐量极低、确认延迟高。PBFT 类协议在**许可制（Permissioned）**区块链中提供更快的共识（Hyperledger Fabric、Stellar、Tendermint、HotStuff）。

## 二、为什么需要 3f+1 个节点？

直觉推导：要容忍 f 个拜占庭节点，系统至少需要 **3f+1** 个节点。

**步骤一：为什么不够用 2f+1？**

考虑 2f+1 个节点，f 个是拜占庭恶意节点。客户端等待 f+1 个相同回复才接受：

```text
操作序列：
  Put("A")  →  f 个坏节点 + 1 个好节点 g1 回复 OK，g2 没看到
  Put("B")  →  f 个坏节点 + g1 回复 OK，g2 错过
  Get()     →  f 个坏节点（故意回 A）+ g2（确实没看到 B）→ 返回 "A"
```

f+1 个回复可以全部来自 f 个坏节点 + 1 个状态落后的好节点，打破线性一致性。

**步骤二：3f+1 如何解决？**

客户端等待 **2f+1** 个相同回复。任意两个 2f+1 的 quorum 集合，其交集至少有 **f+1** 个节点，其中至少有 1 个是诚实节点。

$$|Q_1 \cap Q_2| \geq (2f+1) + (2f+1) - (3f+1) = f+1$$

f 个坏节点不可能单独构造出 2f+1 个一致的虚假回复，因此 2f+1 个匹配回复中**必然包含至少 f+1 个诚实节点**。

::: insight 3f+1 的下界证明（直觉）
假设只有 3f 个节点，其中 f 个拜占庭。当 f 个节点崩溃（不响应）、f 个节点是拜占庭时，只剩 f 个诚实节点。系统需要在 f 个诚实节点和 f 个拜占庭节点中做决定，而拜占庭节点可以完美模拟 f 个崩溃节点——此时无法区分哪种情况，无法保证安全性。因此 3f+1 是理论最小值，不可放宽到 1/2 容错。
:::

## 三、设计演进：从简单投票到 PBFT

### 设计 1：等待全部 n 个回复一致

**问题**：1 个拜占庭节点可以发送不同回复，或完全不回复，导致客户端永远等待。

### 设计 2：2f+1 节点，等待 f+1 个一致回复

**问题**：f+1 个一致回复可以由 f 个坏节点 + 1 个状态落后好节点组成，客户端可能读到过期状态，违反线性一致性。

### 设计 3：3f+1 节点，等待 2f+1 个一致回复

解决了单客户端下的读一致性，但**多客户端并发**时出现新问题：

```text
客户端 A：Put("x", 1)
客户端 B：Put("x", 2)

若不同副本以不同顺序执行这两个操作，最终状态将不一致！
```

所有副本必须以**相同的全局顺序**处理请求。需要引入 **Primary（主节点）** 来排序。

### 设计 4（PBFT 雏形）：引入 Primary + 三阶段协议

坏主节点能做什么？

- 给不同副本分配不同操作（矛盾的 Pre-prepare）
- 忽略某些客户端请求
- 给自己发 Pre-prepare，但不通知其他副本

应对方案：引入 Prepare 和 Commit 两个阶段，让副本互相交叉确认，确保"即使 Primary 作恶，已提交的操作仍然一致"。

## 四、PBFT 正常操作流程

系统共 3f+1 个副本，其中一个是 Primary（主节点），其余是 Backup（备份节点）。视图号（view）决定当前 Primary：$p = v \bmod (3f+1)$。

### 三阶段协议

```text
Client ──REQUEST──► Primary
                      │
              ①  PRE-PREPARE
                      ▼
              所有 Backup 副本
                      │
              ②  PREPARE（互相广播）
                      ▼
              收集 2f+1 个 PREPARE
                      │
              ③  COMMIT（互相广播）
                      ▼
              收集 2f+1 个 COMMIT → 执行操作 → 回复 Client
```

**阶段一：PRE-PREPARE**

Primary 收到客户端请求 $m$ 后，广播：

$$\langle\text{PRE-PREPARE}, v, n, d\rangle_{\sigma_p}$$

- $v$：视图号
- $n$：操作序列号（全局单调递增）
- $d = D(m)$：请求的摘要（哈希）

副本接受 PRE-PREPARE 的条件：签名合法、视图号正确、同一 $n$ 没有接受过不同摘要的 PRE-PREPARE。

**阶段二：PREPARE**

每个接受 PRE-PREPARE 的副本，广播给所有其他副本：

$$\langle\text{PREPARE}, v, n, d, i\rangle_{\sigma_i}$$

副本收集到 **2f+1 个**（含自身）匹配的 PREPARE 消息后，称该操作"prepared"。

::: definition Prepared 状态
副本 i 对操作 (v, n, m) 达到 prepared 状态，意味着至少 f+1 个诚实副本已经看到了 PRE-PREPARE，且认可了该操作在序列号 n 的位置。这防止了 Primary 向不同副本发送不同操作。
:::

**阶段三：COMMIT**

每个 prepared 的副本广播：

$$\langle\text{COMMIT}, v, n, d, i\rangle_{\sigma_i}$$

副本收集到 **2f+1 个** COMMIT 后，执行操作，向客户端回复：

$$\langle\text{REPLY}, v, t, c, i, r\rangle_{\sigma_i}$$

客户端等待 **f+1 个**相同回复，接受结果。

::: insight 为什么需要三阶段？两阶段为何不够？
两阶段（仅 Pre-prepare + Prepare）无法保证：在 View Change 时，新 Primary 能正确重建哪些操作已经"committed"（被至少 f+1 个诚实节点执行）。Commit 阶段让副本"公告"自己已 prepared，新 Primary 通过 View-Change 消息中的 Prepare 证明，能安全推断出哪些序列号已不可撤销。
:::

## 五、View Change：处理 Primary 故障

当 Primary 超时无响应，备份节点触发 View Change：

**步骤**：

1. 副本 $i$ 广播：$\langle\text{VIEW-CHANGE}, v+1, n, C, P, i\rangle_{\sigma_i}$
   - $n$：最新稳定检查点的序列号
   - $C$：该检查点的 2f+1 个证明消息
   - $P$：序列号 $n$ 之后所有 prepared 操作的 Prepare 消息集合

2. 新 Primary（$p = (v+1) \bmod (3f+1)$）等待收到 **2f+1 个** VIEW-CHANGE 消息

3. 新 Primary 广播 $\langle\text{NEW-VIEW}, v+1, V, O\rangle$，其中：
   - $V$：收到的 2f+1 个 VIEW-CHANGE 消息证明
   - $O$：对上一 view 中所有 prepared 但未 committed 操作的重新 Pre-prepare（或 no-op）

::: insight View Change 的核心安全保证
若一个操作在视图 v 中已被 committed（2f+1 个 COMMIT），则在任何后续视图中，新 Primary 收集的 2f+1 个 VIEW-CHANGE 消息中，至少有 f+1 个来自诚实节点，这些节点的 P 集合会包含该操作的 Prepare 证明。因此新 Primary 必然能发现该操作并保留它，不会被遗忘或篡改。
:::

**序列号的处理**：
- 若上一 view 中某序列号已 prepared 但未 committed，新 Primary 保留该操作
- 若某序列号没有足够的 Prepare 证明，新 Primary 填入 no-op，确保序列号不空洞

## 六、性能代价：O(n²) 消息复杂度

PBFT 的三阶段协议中，每个阶段每个副本都需要向所有其他副本发消息：

- PRE-PREPARE：Primary → n 个副本：$O(n)$ 条
- PREPARE：每个副本 → 其余所有副本：$O(n^2)$ 条
- COMMIT：每个副本 → 其余所有副本：$O(n^2)$ 条

**总消息复杂度：$O(n^2)$**，随节点数平方增长，实际部署通常 $f \leq 1$（4 节点）或 $f \leq 3$（10 节点）。

**与 Raft 的对比**：

| 维度 | Raft | PBFT |
|------|------|------|
| 消息复杂度 | O(n) | O(n²) |
| 认证方式 | 无/TLS | MAC / 数字签名 |
| 延迟 | 1 RTT（正常） | 3 RTT（正常） |
| 故障假设 | 崩溃故障 | 拜占庭故障 |
| 最小节点数 | 2f+1 | 3f+1 |
| 主节点更换 | 选举 | 轮转（v mod n） |

## 七、实现细节

### 消息认证

原始论文：数字签名（RSA）——安全但慢。

优化：用**消息认证码（MAC）**替代大部分签名，仅在 View Change 等关键消息用签名。每对节点共享对称密钥，MAC 计算比 RSA 快 3 个数量级。

### 检查点（Checkpoint）

随着系统运行，日志会无限增长。PBFT 定期对当前状态生成**稳定检查点**：

- 当序列号 $n$ 是 100 的倍数时，触发检查点
- 副本广播 $\langle\text{CHECKPOINT}, n, d, i\rangle$（$d$ 是当前状态摘要）
- 收到 2f+1 个相同的 CHECKPOINT → 该检查点"稳定"
- 稳定检查点之前的日志可以安全清除

### 客户端超时与重试

若客户端超时未收到 f+1 个相同回复，重新向所有副本广播请求。非 Primary 的副本收到请求后，将其转发给 Primary（或触发 View Change 计时器）。

## 八、应用场景与现实局限

### 现实应用

- **Hyperledger Fabric**：企业联盟链，使用 PBFT 变体（PBFT + 身份权限管理）
- **Stellar**：联邦拜占庭协议（FBA），PBFT 思想的扩展
- **Tendermint / HotStuff**：现代 BFT 协议，优化了消息复杂度，应用于 Cosmos、Facebook Diem
- **BFT-SMaRt**：高性能 BFT 库，用于实验性分布式存储系统

### 为什么现实中 BFT 仍然少见？

::: insight BFT 的实际困境
1. **成本高**：需要 3f+1 个副本（vs Raft 的 2f+1），O(n²) 消息，延迟约 3 RTT。

2. **f 难以预测**：需要提前决定能容忍多少拜占庭节点，实际中难以判断。

3. **部署复杂**：不同副本需要运行不同实现（避免共模故障），N-version programming 成本极高。

4. **替代方案更实用**：预防（防火墙、权限隔离）+ 检测（审计日志、入侵检测）往往比容忍拜占庭故障更经济。

5. **适用场景有限**：仅在"参与者部分不可信"且"不可预防攻击"的场合才值得，如联盟链。
:::

## 九、常见问题解析

::: insight 为什么不能容忍 1/2 的拜占庭节点？比如用 2f+1 节点？
存在严格的理论下界证明（Lamport et al. 1982）：在异步网络中，若恶意节点数 ≥ 1/3，则无法区分"节点崩溃"和"节点拜占庭"，无法安全达成共识。3f+1 是绝对最小值，无法放宽。
:::

::: insight View Change 类似 Raft 选举吗？
类似但有关键区别：PBFT 的 Primary 是**预先确定**的（$v \bmod n$），不需要选举投票。新视图的 Primary 轮转，至多连续 f 个视图有 Primary 是坏的（因为坏节点最多 f 个）。Raft 则需要投票选出 Leader，依赖随机超时打破平局。
:::

::: insight PBFT 能保证活性（Liveness）吗？
在完全异步网络中，根据 FLP 不可能定理，无法同时保证安全性和活性。PBFT 的解决方式是假设**弱同步性**（消息延迟最终有界但不确定上界），在此假设下保证活性。安全性（Safety）在完全异步下仍然成立。
:::

::: insight 消息重传和乱序怎么处理？
PBFT 消息中包含足够的元信息（view 号、序列号、摘要）让接收方发现消息丢失或乱序。例如副本收到 PREPARE 但还没收到 PRE-PREPARE 时，会等待 PRE-PREPARE 到达后再处理。若等待超时，启动 View Change 计时器。
:::

## 十、PBFT 与比特币的关系

两者都解决"不可信参与者中的共识"问题，但路径截然不同：

| | 比特币（PoW） | PBFT |
|-|-------------|------|
| 参与者 | 开放、匿名、无许可 | 已知、有身份、许可制 |
| 拜占庭容忍方式 | 算力多数 | 节点数多数（3f+1） |
| 分叉 | 存在（最长链收敛） | 不存在（三阶段保证即时最终性） |
| 吞吐量 | ~7 TPS | 数千 TPS（小规模） |
| 确认延迟 | ~60 分钟 | 秒级 |
| 能耗 | 极高 | 低 |
| 典型应用 | 公链、价值存储 | 联盟链、企业区块链 |

::: insight 核心权衡总结
比特币用"算力证明"在开放网络中实现拜占庭容错，代价是低 TPS 和高延迟；PBFT 用"三阶段投票"在许可网络中实现拜占庭容错，代价是 O(n²) 消息和节点数限制。两者是"开放性"与"性能"之间的不同权衡点。现代系统（HotStuff、Tendermint）试图降低 PBFT 的消息复杂度，将其引入更大规模的场景。
:::

## 本讲小结

PBFT 是拜占庭容错领域的奠基性工作，核心贡献：

1. **3f+1 节点 + 2f+1 quorum**：给出了 BFT 的最小资源需求，并证明其充分性
2. **三阶段协议**（Pre-prepare → Prepare → Commit）：确保所有诚实副本以相同顺序执行操作，即使 Primary 作恶
3. **View Change 机制**：在 Primary 故障时安全切换领导者，保证已提交操作不丢失
4. **MAC 优化**：将数字签名替换为 MAC，使协议在实践中可用

局限在于：O(n²) 消息复杂度限制了可扩展性，实际部署通常 n ≤ 10；且需要已知的参与者集合，不适合开放网络。BFT 的真正复兴来自区块链时代，催生了 HotStuff、Tendermint 等更高效的后继协议。

## 论文阅读： 实用拜占庭容错

## 本讲导览

本文提出了一种新型的拜占庭容错复制算法。

## 1. 引言

该算法在不超过总数 1/3 的副本同时故障时，仍能保证活性与安全性。这意味着客户端最终能收到其请求的响应，且这些响应符合线性一致性要求。该算法适用于互联网等异步系统，并通过关键优化实现了高效运行。

为评估方案，我们开发了复制库并据此实现了真实服务：支持 NFS 协议的拜占庭容错分布式文件系统。

论文结构如下：第二章阐述系统模型与故障假设；第三章明确算法解决的问题及正确性条件；第四章详述算法设计；第五章介绍关键优化技术；第六章说明复制库的实现及拜占庭容错 NFS 的构建方法；第七章呈现实验结果；

## 2. 系统模型

我们假设一个异步分布式系统，其中节点通过网络连接。网络可能出现消息丢失、延迟、重复或乱序等问题。我们采用拜占庭故障模型，即故障节点可能产生任意行为。我们运用密码学技术来防范欺骗攻击和重放攻击，并检测损坏消息。消息中包含公钥签名、消息认证码以及抗碰撞哈希函数生成的消息摘要。节点签名的消息表示为${<m>}_{σ_i}$，消息 m 的摘要记为$D(m)$。我们遵循行业惯例，对消息摘要进行签名后惊奇附加至消息明文。所有副本节点军账务其他节点的公钥以验证签名。

我们假设存在能力极强的攻击者：可协调故障节点、延迟通信或阻滞正常节点，以期对复制服务造成最大损害。但基础假设是攻击者无法无限期阻滞正常节点，同时假定攻击者及其控制的故障节点受计算能力限制，因而（极大概率）无法破解上述密码学技术。例如，攻击者不能伪造正常节点的有效签名、无法从摘要反推原始信息、也不能找到具有相同摘要的两个不同消息。

## 3. 服务特性

我们的算法可用于实现任何具有状态和若干操作的确定性复制服务。

## 4. 容错算法

我们的算法属于状态机复制的一种形式：将服务建模为在分布式系统中多个节点间复制的状态机。每个状态机副本均维护服务状态并实现服务操作。我们用集合 R 表示所有副本，并为每个副本分配 0 到|R|-1 的整数标识。为简化起见，我们假设|R|=3f+1，其中 f 为可能发生故障的最大副本数；虽然可以配置超过 3f+1 个副本，但额外副本会降低性能（因为需要交换更多更庞大的消息），且无法提升容错能力。

副本通过一系列称为视图的配置进行状态演进。在每个视图中，一个副本担任主节点，其他副本作为备份节点。视图按连续整数编号。视图 v 的主节点为副本 p，满足  p = v mod |R|。当主节点疑是故障时，系统会执行视图切换。视图 v 的主节点为副本 p，满足 p = v mod |R|。当主节点疑似故障时，系统会执行视图切换。Viewstamped 复制[26]和 Paxos[18]也采用类似方法处理良性故障。

算法基本工作流程如下：

1. 客户端向主节点发送调用服务操作的请求
2. 主节点将请求组播至备份节点
3. 所有副本执行请求并向客户端返回响应
4. 客户端等待接收来自不同副本的 f+1 个相同结果，该结果即为操作最终结果

与所有状态机复制技术[34]相同，我们对副本提出两项要求：必须具有确定性（即在给定状态和参数下执行操作必须始终产生相同结果），且必须从相同初始状态启动。满足这两项要求后，本算法通过保证所有非故障副本就请求执行的全序达成共识，从而确保安全性特性。
