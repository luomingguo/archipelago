# Lec 19 Fork 一致性

## TL;DR

- SUNDR 研究在完全不可信（可能拜占庭恶意或被攻破）的中心化服务器上实现可验证的文件存储完整性。
- 核心局限与安全边界：无法阻止服务器隐瞒最新更新，但保证只要发生分叉（Fork 攻击），客户端间一旦通信必能立即检测。
- Fork 线性一致性（Fork Linearizability）：若服务器向两个客户端展示了不同历史，它们此后将永远无法看到彼此的后续写操作。
- 实现机制：客户端对操作记录（VSL/VSX）进行数字签名与版本向量链式哈希，使得任何重排序或内容篡改在密码学上不可伪造。

## 一、问题背景：不可信服务器上的可信存储

我们日常信任的存储服务——GitHub、Gmail、AFS、Dropbox——背后的服务器并非绝对可信：

- 软件或硬件存在漏洞，可能被利用；
- 攻击者可能窃取服务器管理员的账密并篡改软件；
- 云提供商内部人员可能存在腐败或操作疏漏。

**真实案例**：
- 2003年：Debian 服务器被攻破；
- 2011年：SourceForge（全球最大开源软件仓库）遭受攻击；
- 2019年：Canonical（Ubuntu 公司）被黑客攻陷。

如果攻击者控制了存储开源软件的服务器，就可以在数百万台机器运行的软件中植入微妙的后门。

::: insight 核心问题
能否从**不可信的服务器**上获得**可信的存储**？

注意：SUNDR 的目标是**完整性（Integrity）**，不是保密性（Confidentiality）。文件内容对恶意服务器是可见的，SUNDR 只防止服务器在用户不知情的情况下**篡改或遗漏**数据。
:::

SUNDR 的影响超出学术范畴：
- 类似思想出现在 **Git**（commit hash chain）和**区块链**中；
- **Keybase**（已被 Zoom 收购）直接受 SUNDR 影响。

## 二、密码学工具

### 2.1 加密哈希

```text
h = hash(data)
```

- `h` 很小（如 SHA-1 输出 160 位），`data` 可以很大；
- **安全性**：在计算上不可能找到两个不同输入具有相同哈希值（抗碰撞）；
- 用途：命名数据（内容寻址）或验证完整性。

**内容寻址存储（Content-Addressed Storage）**：

```text
写入：k = hash(v)；put(k, v)
读取：v = get(k)；assert hash(v) == k
```

如果服务器损坏了数据，客户端的哈希检查会失败。但这种存储是**不可变**的——键由内容决定，无法更新。

**局限**：内容哈希存储不能支持读/写文件系统，因为无法对已有键进行更新。

### 2.2 数字签名

数字签名允许**可变存储**：

```text
签名方（持有私钥 k_priv）：sig = sign(data, k_priv)
验证方（持有公钥 k_pub）：ok = verify(data, sig, k_pub)
```

- 写入：`put(k, v + sign(v, k_priv))`
- 读取：`v, sig = get(k)`；`verify(v, sig, k_pub)`

::: insight 数字签名的保证
只要服务器不知道用户的私钥，它就**无法伪造**签名。客户端接受的任何修改，必然是某个持有私钥的授权用户真正签署过的。

但这还不够——服务器虽然无法伪造内容，却可以**隐藏**某些用户的历史操作，向不同用户展示不同版本的文件系统。
:::

## 三、SUNDR 协议

### 3.1 总体架构

SUNDR 是一个网络文件系统，客户端应用的系统调用在内部被转换为两类操作：

- **Fetch（获取）**：检索文件内容，或验证本地缓存；
- **Modify（修改）**：将新的文件系统状态对其他用户可见。

每个用户（user）拥有一个**签名密钥对**（公钥/私钥）。文件系统超级用户通过 `.sundr.users` 和 `.sundr.groups` 文件管理账户与权限。每个用户各自拥有一张 **i-table**（inode 表），用自己的私钥签名，服务器无法伪造。

### 3.2 简单版本：虚拟文件系统（全量日志）

为理解核心思想，先考虑一个极度低效但正确的版本：

1. 服务器维护一个**有序的全局操作日志**，每条记录包含：
   - 操作类型（fetch/modify）；
   - 执行操作的用户的数字签名；
   - **签名范围覆盖该操作及之前的所有历史**。

2. 客户端执行操作时：
   - 获取全局锁；
   - 下载整个操作历史；
   - 验证每个用户最近一次签名，并确认自己上次操作在历史中；
   - 遍历历史，重建文件系统本地副本；
   - 将新操作附加到列表，签署新历史，发给服务器，释放锁。

**为什么 fetch 也要签名记录？**

::: insight 思考题：若只记录 modify，不记录 fetch，会发生什么？
若只有 modify 被签名记录，服务器可以向 B 隐藏 A 的某次修改，然后等 B 发出下一次修改后，再把 A 的修改"补进来"——因为 B 从未对 A 的修改处的状态签名，服务器可以无痕拼接历史。

fetch 签名的作用：B 的每次读取都记录了"我当时看到的是哪个状态"，服务器无法事后悄悄插入之前被隐藏的操作而不暴露矛盾。

结论：**fetch 签名是实现 Fork Consistency 的关键**，缺少它会破坏保证。
:::

### 3.3 i-handle：高效的文件系统状态摘要

全量日志方式带宽消耗过大。实际的 SUNDR 使用 **i-handle** 代替完整历史：

::: definition i-handle（索引句柄）
i-handle 是文件系统当前状态的紧凑摘要，包含：

① **i-table hash**：用户 i-table（inode 表）的哈希树根；

② **版本向量（Version Vector）**：记录该用户最后一次看到其他每个用户的哪个版本操作。

形如：`i-handle = (root_hash, version_vector)`

每次 fetch 或 modify 操作前后，客户端都要签署自己的 i-handle，并附上对服务器响应中其他用户 i-handle 的验证。
:::

**版本向量示例**：

```text
用户 A 的版本向量：{A: 3, B: 2}  → 表示"我(A)已执行了3次操作，且看到了B的前2次操作"
用户 B 的版本向量：{A: 2, B: 4}  → 表示"我(B)已执行了4次操作，且看到了A的前2次操作"
```

版本向量的作用：客户端可以通过比较版本向量，判断两个用户所见的历史是否一致，从而检测服务器是否发动了**分叉攻击**。

## 四、Fork 一致性

### 4.1 两种一致性保证

::: definition Fetch-Modify Consistency（获取-修改一致性）
服务器行为正确时的保证：每次 fetch 操作都能看到所有之前已授权的 modify 操作的结果。这是理想状态。
:::

::: definition Fork Consistency（分叉一致性）
服务器不诚实时能保证的最强性质：

若服务器向用户 A 隐藏了用户 B 的某次修改，则此后服务器**必须永远**向 A 隐藏 B 的所有后续修改（以及向 B 隐藏 A 的所有后续修改）。

换言之：**服务器只能让用户"分叉"，不能让历史消失后重新出现（不能"愈合"分叉）**。
:::

### 4.2 分叉攻击示意

```text
真实历史：A1 → B1 → A2 → B2 → A3

服务器向 A 展示：A1 → A2 → A3        （隐藏了 B1, B2）
服务器向 B 展示：A1 → B1 → B2        （隐藏了 A2, A3）

这就是"分叉"：A 和 B 看到了不同版本的文件系统。
```

**SUNDR 的保证**：一旦服务器对 A、B 进行了分叉，它就**无法**在不暴露矛盾的情况下，让 A 重新看到 B 的操作（或反之）。这是因为 i-handle 的版本向量会揭露逻辑矛盾。

**为什么？** 若服务器试图"愈合"分叉——让 A 在分叉之后又能看到 B 的操作——A 的版本向量会显示 B 的某个版本号"突然向前跳跃"（中间有跳过的操作），而 A 却未曾对跳过的那些操作签过名。这种跳跃构成密码学上可检测的矛盾。

### 4.3 与 Git 的类比

| 概念 | SUNDR | Git |
|------|-------|-----|
| 操作记录 | 带签名的 fetch/modify 日志 | commit |
| 历史摘要 | i-handle（hash + version vector）| commit hash（SHA） |
| 不可篡改性 | 哈希链 + 数字签名 | 哈希 DAG |
| 分叉 | 服务器强制分叉 | `git branch` / `git fork` |
| 合并 | 需要带外通信检测 | `git merge` |

::: insight Git 的类比
Git 的每个 commit 包含父 commit 的哈希，形成不可篡改的链（DAG）。这与 SUNDR 的 i-handle 链几乎同构：历史一旦签署，篡改必然被发现。这正是为什么"攻陷 Git 服务器的攻击者无法无声无息地修改历史"——用户 pull 时会发现 hash 不匹配。
:::

## 五、分叉检测与局限性

### 5.1 如何检测分叉

SUNDR 本身**不能自动检测分叉**，必须借助**带外通信（Out-of-Band Communication）**：

- 用户 A 通过邮件告诉 B："我更新了文件 X，请查看"，B 却看不到任何更新 → 说明服务器发动了分叉攻击（或 A 在撒谎）；
- 用户直接比较各自持有的最新 i-handle 签名，版本向量不一致即为分叉证据。

### 5.2 时间戳服务器（Timestamp Box）

论文提出用**可信时间戳服务器**来辅助检测分叉：

```text
时间戳服务器定期（如每分钟）对当前所有用户的 i-handle 进行签署，
并广播给所有客户端。
```

- 客户端可以验证自己的 i-handle 是否出现在时间戳服务器的广播中；
- 若服务器对 A 进行了分叉，A 的某个 i-handle 将与其他用户所见的版本不一致，时间戳服务器会暴露矛盾；
- **代价**：引入了一个新的可信第三方（时间戳服务器），与"不信任任何服务器"的初衷有所妥协。

### 5.3 分叉后如何处理

::: insight 检测到分叉后应该怎么做？
A：没有通用的技术答案。

① 立即停止信任该存储服务，更换提供商；

② 检查各分支历史，手动合并（或慎重丢弃）冲突写入——需要具体应用和文件格式的具体处理；

③ 评估分叉期间用户基于错误数据作出的所有决策的影响（最麻烦的部分）。
:::

## 六、SUNDR vs 比特币

::: insight SUNDR 和比特币如何分别处理分叉问题？

**SUNDR**：

- 服务器可以分叉，但无法愈合（密码学保证）；

- 检测分叉需要用户带外通信或可信时间戳服务器；

- 时间戳服务器是新的可信中心，存在单点失败风险。

**比特币**：

- 通过工作量证明（PoW）建立全局共识，自动处理分叉——最长链胜出；

- 无需可信第三方，任何节点都可以参与；

- 代价：大量计算资源消耗，且分叉在短时间内仍可能存在（需要等待足够多的确认块）。

本质区别：SUNDR 依赖**权威（可信时间戳）**解决分叉，比特币依赖**计算力（PoW）**解决分叉。
:::

## 七、核心定理与安全边界

### 7.1 SUNDR 能防什么

| 攻击类型 | 能否防御 | 原因 |
|---------|---------|------|
| 服务器伪造签名 | ✅ 能 | 服务器不知道用户私钥 |
| 服务器回滚历史（截断到旧版本） | ✅ 能 | i-handle 版本向量会检测到缺失操作 |
| 服务器替换文件内容 | ✅ 能 | 内容哈希验证失败 |
| 服务器向不同用户展示不同视图（分叉） | ⚠️ 有限防御 | 分叉可发生，但无法愈合（可最终检测） |
| 服务器彻底拒绝服务（不响应） | ❌ 不能 | 超出 SUNDR 范围 |

### 7.2 为何"分叉一致性是最强可达保证"

论文声称：**在没有在线可信第三方的情况下，分叉一致性是可实现的最强完整性保证**。

直觉原因：若只有一个客户端在线，或者客户端只能通过 SUNDR 服务器通信，则客户端无法区分"服务器正确返回了所有操作"和"服务器隐藏了某个其他用户的最新操作"——服务器完全可以声称"目前没有其他用户的新操作"。只要无法直接验证这一点，就无法做出更强的保证。

## 八、FAQ 精选

::: insight SUNDR 能加密文件内容对服务器保密吗？
A：不能。SUNDR 只提供完整性（integrity），不提供机密性（confidentiality）。服务器可以看到文件内容。用户可以在 SUNDR 层之上自行加密文件，但这不是 SUNDR 本身的功能。
:::

::: insight 计算 i-handle 的性能如何？
A：SHA-1 计算速度较快（约每字节 10 个时钟周期）。若只修改了一个数据块，只需对该块重新计算哈希，然后向上更新到根哈希，无需全量重算。真正慢的是**签名步骤**（公钥密码学运算）。

优化：i-handle 可以存储哈希值 + 最近操作变更的简短日志，避免多次操作中重复计算整棵哈希树。已验证过最近版本的客户端只需应用日志中的少数几条操作即可完成验证。
:::

::: insight 为什么说"分叉虽然不理想，但分叉一致性是好的"？
A：确实，分叉不是理想状态。但在普通假设下，无法完全阻止恶意服务器向客户端分叉内容。SUNDR 的做法是**限制**服务器的自由度：只能分叉，不能合并。一旦分叉，后果（合作用户不再看到彼此的更新）往往很快就会被察觉，用户就会停止信任该服务。这是在实际约束下能达到的最优解。
:::

::: insight SUNDR 目前有哪些实际应用？
A：SUNDR 本身没有被广泛直接部署。但其核心思想渗透到了：

① **Git**：commit hash chain，内容哈希保证历史不可篡改；

② **区块链/账本系统**：操作日志 + 签名的分布式版本；

③ **Keybase**（已被 Zoom 收购）：直接受 SUNDR 影响的商业系统，提供基于密钥的身份与文件完整性验证。
:::

## 本讲小结

| 核心概念 | 说明 |
|---------|------|
| 威胁模型 | 服务器可撒谎、回滚、选择性展示历史，但不知道用户私钥 |
| 密码学工具 | 内容哈希（防篡改）+ 数字签名（防伪造）|
| i-handle | hash tree root + version vector，紧凑表示文件系统状态及用户所见历史 |
| Fetch-Modify 一致性 | 诚实服务器的保证：fetch 总能看到所有已授权的 modify |
| Fork 一致性 | 不诚实服务器的最强约束：只能分叉，不能愈合 |
| 分叉检测 | 需要带外通信或可信时间戳服务器 |
| 局限性 | 无法阻止分叉本身发生；无法提供机密性 |

::: insight 核心洞见
SUNDR 的根本贡献是厘清了"不可信服务器上可信存储"的**可能性边界**：通过哈希链 + 签名，可以将服务器的欺骗空间从"任意篡改"压缩到"只能分叉且无法愈合"。这一思想比 SUNDR 本身更长寿——它成为 Git、区块链等现代系统的理论基础。
:::

## 思考题

在简单的设想方案中，`fetch`和 `modify`操作都被记录在日志中并进行签名。假设一种替代设计，其中只有``modify``操作被签名并记录在日志中。这样设计是否允许恶意服务器破坏 `fetch-modify consistency`（获取-修改一致性）或 `fork consistency`（分叉一致性）？为什么或为什么不？

## 本讲导览

SUNDR 是一种网络文件系统，设计用于在不受信任的服务器上安全存储数据。SUNDR 允许客户端检测恶意服务器操作员或用户对文件的任何未授权修改尝试。SUNDR 协议实现了一种称为“**分叉一致性**”的特性，该特性保证只要客户端能够看到彼此的文件修改，就能检测到任何完整性或一致性方面的故障。描述的实现性能与 NFS 相当（有时更好，有时稍逊），但提供了显著更强的安全性

## 1. 引言

SUNDR 是一种网络文件系统，旨在解决数据完整性和可访问性之间的长期矛盾。保护数据通常被视为在存储服务器周围建立更高“围栏”的问题——限制访问人数、禁用可能会被远程利用的不必要软件，并保持最新的安全补丁。然而，这种方法有两个缺点。首先，经验表明，人们常常没有建立足够高的围栏（或者有时将围栏交由不完全可信的管理员负责）。其次，更重要的是，高围栏会带来不便；它们限制了人们访问、更新和管理数据的方式。

这一矛盾在自由软件源代码库中尤为明显。自由软件项目通常涉及地理分散的开发人员从互联网各地提交源代码更改，使得用防火墙来阻止攻击者的方案不切实际。更糟糕的是，许多项目依赖第三方托管服务。通过攻陷 SourceForge，攻击者可以在可能运行于成千上万甚至数百万台机器的软件中植入微妙的漏洞。并且攻击事件并不仅限于学术探讨。

我们并不指望服务器绝对安全，而是开发了 SUNDR 这一网络文件系统，以减少对存储服务器的信任需求。SUNDR 使用加密方法保护所有文件系统内容，使客户端可以检测任何对文件的未授权更改。与以前的拜占庭容错文件系统 [6, 27] 通过分布信任但假定一部分服务器诚实不同，SUNDR 将文件写权限完全赋予用户的公钥。即便是获得完全管理权限的恶意用户，也无法让客户端接受他无写权限的文件内容修改。

凭借其安全特性，SUNDR 还为数据管理提供了新的选择。使用 SUNDR，组织可以将存储管理外包而不必担心服务器操作员篡改数据。SUNDR 还提供了新的数据备份和恢复选项：在发生灾难后，SUNDR 服务器可以从不受信任的客户端文件缓存中恢复文件系统数据。由于客户端始终加密验证文件系统的状态，它们不在意数据是从不受信任的客户端恢复的，还是始终保存在不受信任的服务器上。

本文详细介绍了 SUNDR 文件系统的设计和实现。我们首先描述了 SUNDR 的安全协议，接着介绍了一个原型实现，该实现的性能在软件开发工作负载和微基准测试下通常与流行的 NFS 文件系统相当。我们的结果表明，像 CVS 这样的应用程序可以在享受 SUNDR 强大安全保障的同时，承受较低的性能损耗。

## 2. 设置

SUNDR 提供了一个远程存储的文件系统接口，类似于 NFS [29] 和其他网络文件系统。例如，为了保护源代码库，项目成员可以将远程 SUNDR 文件系统挂载到目录 /sundr，并使用 /sundr/cvsroot 作为 CVS 仓库。所有的检出和提交操作都通过 SUNDR 进行，从而确保用户能够检测到托管站点对仓库内容的任何篡改企图。

图 1 展示了 SUNDR 的基本架构。当应用程序访问文件系统时，客户端软件会在内部将它们的系统调用转换为一系列获取和修改操作，其中获取指的是检索文件内容或验证本地缓存的副本，修改指的是使新的文件系统状态对其他用户可见。获取和修改操作分别通过 SUNDR 协议的 RPC 调用实现。协议在第 3 节中说明，服务器设计在第 5 节中描述。

要设置 SUNDR 服务器，需要在一台联网的机器上运行服务器软件，并使用专用的 SUNDR 磁盘或分区。服务器可以托管一个或多个文件系统。创建文件系统时，需要生成一个公钥/私钥超级用户签名密钥对，将公钥提供给服务器，并保密保存私钥。私钥提供对文件系统根目录的独占写权限，同时直接或间接地允许访问根目录下的所有文件。然而，这些权限仅限于单个文件系统。因此，当一个 SUNDR 服务器托管多个由不同超级用户管理的文件系统时，没有任何单一人员可以拥有所有文件的写访问权限。

SUNDR 文件系统的每个用户（user）也拥有一个签名密钥。建立账户（account）时，用户与超级用户（superuser）交换公钥。超级用户通过根目录下的两个由其拥有的文件来管理账户：

1. .sundr.users 列出用户的公钥和数值 ID，
   - 每个用户都有一个唯一的公钥，用来证明其身份，以及一个数值 ID，作为用户在系统中的标识
2. sundr.group 指定组及其成员
   - 这个文件定义了不同的用户组及其成员关系。它指明了哪些用户属于哪些组，以便于权限管理

要挂载文件系统，必须将超级用户的公钥作为客户端的命令行参数，还必须让客户端能够访问私钥。（SUNDR 也可以使用更灵活的证书方案来管理密钥和组；系统只需要一种方法来验证用户彼此的密钥和组成员身份。）

在本文中，我们使用“用户”一词来表示拥有映射到 .sundr.users 文件中某个用户 ID 的签名密钥的实体。根据上下文，这可能是持有私钥的个人，或者是代表用户操作的客户端。然而，SUNDR 假设用户知道自己上次执行的操作。在实现中，客户端会记住它代表每个用户执行的最后操作。要在不同客户端之间切换，用户需要同时携带其私钥和其最后一次操作的记录（以版本号简明表示）。另外，用户还可以为不同客户端分配多个用户 ID（可能使用相同的公钥），并将所有文件权限赋予一个个人组。

SUNDR 的架构在服务器管理和文件系统管理之间划分了明确的界限。管理服务器无需任何超级用户私钥。**为了最佳的安全性，密钥对应在单独的、受信任的机器上生成，且私钥不应保留在服务器上**，即使是内存中也不应有。重要的密钥，如超级用户密钥，应在不使用时离线存储（例如存储在软盘上并用密码短语加密）。

## 3. SUNDR 协议

SUNDR 协议允许客户端检测未经授权的文件修改尝试，即便攻击者完全控制了服务器。当服务器行为正确时，获取操作完全反映了此前所发生的授权修改。我们称这一特性为**“获取-修改一致性（fetch-modify consistency）”**。如果服务器不诚实，客户端则强制执行一种稍微弱一些的特性，称为“**分叉一致性（fork consistency）**”。直观地说，在分叉一致性下，一个不诚实的服务器可能导致用户 A 的获取操作错过用户 B 的修改。但是，任何一方用户在看到对方的后续操作时都能检测到攻击。因此，为了维持欺骗，服务器必须分叉两个用户的文件系统视图。换句话说，如果 A 的客户端接受了 B 的某次修改，那么至少在 B 进行该次修改之前，两个用户都拥有一致的、获取-修改一致的文件系统视图。

我们已经正式定义了分叉一致性【16】，并在假设数字签名和抗碰撞哈希函数的基础上，证明了 SUNDR 协议能够实现分叉一致性【17】。因此，违反分叉一致性可能意味着底层加密技术被破坏，或实现偏离了协议，或者我们将高级 Unix 系统调用映射到底层获取和修改操作的方式存在缺陷。

为了讨论分叉一致性的含义并描述 SUNDR 系统，我们从一个简单的虚拟文件系统开始，该系统通过极大的低效性实现分叉一致性（第 3.1 节）。然后我们提出一个改进的系统——带有更合理带宽需求的“序列化 SUNDR”（第 3.3 节）。最后我们放宽了序列化要求，得到“并发 SUNDR”，即我们构建的系统（第 3.4 节）。

### 3.1 简单的虚拟文件系统

在 SUNDR 的粗略近似版本中，虚拟文件系统避免任何并发操作，允许系统消耗不合理的带宽和计算资源。服务器在文件系统上维护一个单一的、不可信的全局锁。要获取或修改文件，用户首先获得该锁，然后执行所需操作，再释放锁。只要服务器诚实，操作是完全有序的，每个操作在下一个操作开始之前完成。

接着，客户端遍历操作历史，以构建文件系统的本地副本。对于每次遇到的修改操作，客户端还进一步检查该操作是否确实被允许，使用用户和群组文件来验证签名用户是否与文件的所有者或群组匹配。如果所有检查均成功，客户端将新操作附加到列表中，签署新的历史，将其发送至服务器，并释放锁。如果操作是修改操作，附加的记录包含了一个或多个文件或目录的新内容。
