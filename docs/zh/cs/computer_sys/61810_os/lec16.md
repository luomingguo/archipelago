## 问题背景：微秒时代与数据中心尾延迟危机

在上一节课中，我们探讨了以太网硬件驱动与接收活锁（Livelock）。今天我们要研读的这篇论文——发表在网络与系统顶会 NSDI 2019 上的 **Shenango**，代表了当今系统结构领域非常前沿的研究方向。

在过去的十年里，数据中心硬件发生了一场翻天覆地的物理革命：

- 存储介质从毫秒级的旋转机械硬盘，跃升到了纳秒/微秒级的 NVMe SSD 与非易失性内存；
- 网络互联从千兆以太网，飙升到了 100Gbps / 400Gbps 乃至超低延迟的 RDMA 网络；
- 在分布式内存键值存储（如 Memcached、Redis）或微服务 RPC 中，处理一次网络请求纯粹的计算时间往往只有 1 到 2 微秒（1~2 μs）！

然而，当我们把这种微秒级服务部署到传统 Linux 操作系统上时，一场令人绝望的“抽象倒挂”出现了：  网卡把数据包注入内存只需要 1 微秒，但 Linux 内核光是处理一次中断、唤醒线程并完成上下文切换，就要耗费 10 到 30 微秒！操作系统内核自身，已经彻底沦为了整个数据中心最沉重的性能枷锁！

## 长尾难题

在评估微秒级网络系统时，业内不再仅仅关注“平均延迟（Average Latency）”，而是将聚光灯打在了一个决定大型互联网公司生死存亡的指标上——**长尾延迟（Tail Latency / 99th Percentile Latency）**。

Google 传奇首席架构师 Jeff Dean 在其名篇《*The Tail at Scale*》中揭示了一个极具破坏性的数学模型——**请求扇出效应（Fan-out Effect）**：

```text
+--------------------------------------------------------------+
|                     微服务扇出与长尾放大效应                  |
|                                                              |
|                     [ 用户端手机发起搜索请求 ]                |
|                                |                             |
|                                v                             |
|                     [ API 网关聚合接入层 ]                   |
|                                |                             |
|           +--------------------+--------------------+        |
|           | 一次用户请求并发扇出到 100 台后端微服务服务器!    |
|           v                    v                    v        |
|     [ 广告索引推荐 ]     [ 用户画像画像 ]     [ 知识图谱数据库] ...
|           |                    |                    |        |
|           +--------------------+--------------------+        |
|                                | (等待全部 100 台返回后组装) |
|                                v                             |
|                     [ 用户终于看到渲染页面 ]                 |
+--------------------------------------------------------------+
```

### 尾延迟的概率诅咒

假设单台后端服务器的性能表现极佳：99% 的请求在 1 毫秒内完成，只有 1% 的长尾请求因为各种偶发抖动耗时 1 秒（99% 尾延迟 = 1 秒）。  
在单机时代，这意味着只有 1% 的用户会遇到慢响应。  
但是，在微服务架构下，一个前端请求需要并发扇出向 100 台机器索要数据，前端必须等待**最慢的那一台机器返回**才能生成结果：

$$P(\text{请求遇到 1 秒慢响应}) = 1 - (1 - 0.01)^{100} = 1 - 0.99^{100} \approx \mathbf{63.4\%}！$$

灾难发生了！ 虽然每一台单机都宣称自己拥有 99% 的极速响应，**但高达 63.4% 的真实终端用户在屏幕前遭遇了整整 1 秒的卡顿**！长尾延迟被网络扇出呈指数级无情放大！


传统 Linux 内核为何必然崩塌？我们站在底层硬件的角度算一笔冷酷的算术账：

```text
+--------------------------------------------------------------+
|                 100Gbps 物理网络下的 CPU 算力配额             |
|                                                              |
|   1. 100Gbps 线速以太网:                                     |
|      - 每秒最多传输 1.48 亿个小数据包 (148 Mpps)             |
|                                                              |
|   2. 现代单核 CPU 时钟频率: 2.4 GHz (每秒 24 亿时钟周期)      |
|                                                              |
|   3. 单个 CPU 核心处理一个数据包的理论极限配额:               |
|      2,400,000,000 / 148,000,000 ≈ 仅 16 个时钟周期 !!       |
|      (即使配置 8 颗专用核心，每包配额也只有区区 128 个周期!)   |
|                                                              |
|   4. 传统 Linux 内核的固定开销:                               |
|      - 响应一次 PLIC 硬件中断: ~1000 周期                    |
|      - 一次跨特权级系统调用: ~200 周期                       |
|      - 一次线程上下文切换与 TLB 冲刷: ~2000 周期              |
|      - 内核套接字锁争用与跨核 Cache 抖动: 数千周期            |
+--------------------------------------------------------------+
```

**结论无可辩驳**：面对微秒级的网络流量，传统内核以中断和线程为核心的设计，在数学上就注定了崩溃的宿命。


## 内核旁路技术（Bypass）的崛起与利用率死结


## 4. 内核旁路技术（Kernel-Bypass）的崛起与“利用率死结”

为了跨越操作系统内核的泥潭，系统界在过去几年广泛采用了**内核旁路技术（Kernel-Bypass Networking）**（以 Intel DPDK 为代表）：

```text
+--------------------------------------------------------------+
|                    传统 Linux vs 内核旁路 (DPDK)              |
|                                                              |
| [ 传统 Linux 架构: 层层排队与特权跨越 ]                      |
|   网卡 DMA -> 硬件中断 -> 内核驱动 -> TCP 协议栈 -> Socket 队列|
|   -> 唤醒线程 -> 上下文切换 -> 用户进程读取                   |
|                                                              |
| [ 内核旁路架构 (Kernel-Bypass / DPDK): 零拷贝直通 ]           |
|   1. 绕过整个 Linux 内核！网卡 DMA 描述符环直接通过页表映射   |
|      到用户态进程的虚拟内存空间;                             |
|   2. 用户态嵌入极简 TCP 栈 (LibOS);                          |
|   3. 专核专用 (Core Pinning): 独占 4 颗 CPU 核心，在死循环中  |
|      全速轮询 (Polling) 网卡环形队列，彻底消灭所有中断与切换! |
+--------------------------------------------------------------+
```

### 

纯内核旁路系统（如 ZygOS）确实取得了惊人的微秒级超低尾延迟。然而，它在工业界数据中心遭遇了巨大的商业阻力：**利用率（CPU Utilization）极其低下！**

- 为了防止突发流量冲垮系统，数据中心不得不为这些微秒服务永久绑定死 8 颗或 16 颗专属 CPU 核心，让它们日夜不停地高速死循环轮询网卡；
- 但在互联网现实中，日间与夜间的访问流量有着数十倍的潮汐差距。在绝大部分低负载时刻，这些被独占的核心在疯狂空转，根本无法被出借给其他有需要的计算任务（如批处理、机器学习离线训练、视频转码）；
- 在数百万台服务器的超算中心里，常年维持 20% 以下的 CPU 利用率，意味着每年白白蒸发数十亿美元的机房电费与采购成本！

**核心技术鸿沟**：我们能否既拥有内核旁路的微秒级超低尾延迟，又拥有传统分时多任务操作系统的高 CPU 利用率？


## Shenango 架构突破：5 微秒级敏捷核心调度

NSDI '19 经典论文 **Shenango** 创造性地打破了这一双重僵局！

Shenango 的核心洞察是：**以往的操作系统调度粒度是以毫秒（10~100 ms）为尺度的；如果在微秒尺度（5 μs）上动态借调

Shenango 的核心洞察是：**以往的操作系统调度粒度是以毫秒（10~100 ms）为尺度的；如果在微秒尺度（5 μs）上动态借调与抢占核心，就能在尾延迟爆发前瞬间平抑拥塞！**

```text
+--------------------------------------------------------------+
|                     Shenango 系统架构组织全景                 |
|                                                              |
| [ 独立特权 I/O 内核 (I/O Kernel - 独占 1 颗专用核心) ]        |
|   1. 利用 DPDK 直接接管物理网卡，全速轮询外部所有网络报文;   |
|   2. 每隔 5 微秒 扫描一次所有业务应用的输入队列与线程状态;    |
|   3. 【敏捷大脑】: 探测到计算拥塞 -> 瞬间为该应用动态分配核心; |
|                                                              |
| ===================[ 共享内存无锁单生产者单消费者队列 ]====== |
|                                                              |
| [ 延迟敏感型应用 (如 Memcached) ]      [ 批处理应用 (如 编译) ]|
|   - 平时仅维持 1 颗核心保底运行        - 在空闲时吞噬所有余量核心|
|   - 一旦流量洪峰在 5μs 内被检测到:       全速计算;              |
|     I/O 内核瞬间从批处理应用手中       - 一旦洪峰到达，核心在 5μs|
|     强行夺回核心交还给 Memcached!       内被无情剥夺让位!      |
+--------------------------------------------------------------+
```

---

### 5.1 计算拥塞探测算法（Algorithm 1）

I/O 内核如何知道一个应用即将撑不住了？它不能等到延迟飙升后才反应。I/O 内核每隔 **5 微秒** 执行一次极其精密的健康体检：

::: definition Shenango 计算拥塞（Compute Congestion）判定准则
在第 $T$ 个 5 微秒周期扫描时，如果发现以下两项之一成立，立即判定发生计算拥塞：

1. **网络输入队列堆积**：在上一个周期写入该应用核心输入队列的数据包，在本次周期检查时**依然没有被消费**；
2. **轻量级用户线程排队**：应用内部的用户态待运行线程队列（`uthread queue`）非空，且有任务在排队等待 CPU。
   :::

一旦检测到计算拥塞，I/O 内核在 **下一微秒内** 启动核心再分配！

---

### 5.2 敏捷核心分配与借调算法（Algorithm 2）

当 I/O 内核决定为 Memcached 扩容核心时，它按照以下严苛的**亲和性优先级**挑选并唤醒核心：

```text
+--------------------------------------------------------------+
|                   Shenango 核心遴选四级优先级                 |
|                                                              |
|   优先级 1: 共享同一物理物理核的超线程兄弟 (Sibling Hyperthread)|
|            - L1/L2 缓存与 TLB 命中率最高，冷启动惩罚为 0!    |
|                                                              |
|   优先级 2: 该应用最近刚刚让出的核心 (Most Recently Yielded)  |
|            - CPU 缓存行（Cache Lines）尚未完全被驱逐         |
|                                                              |
|   优先级 3: 系统全局空闲的核心 (Idle Core)                   |
|                                                              |
|   优先级 4: 从吞吐型批处理应用手中强行抢占核心 (Preemption)   |
|            - 发送跨核处理器间中断 (IPI)，迫使其瞬间归还核心!  |
+--------------------------------------------------------------+
```

## 6. 用户态轻量级线程运行时（Uthreads & Work Stealing）

进入到应用进程内部，Shenango 彻底抛弃了重量级的 POSIX `pthread`（因为内核线程创建与调度需要跨越特权级）。它在应用内部内嵌了一个**完全运行在 U-mode 的极速协程运行时（Uthreads）**：

- **每个网络请求对应一个轻量级 Uthread**：开销仅有几百字节；
- **无锁工作窃取（Lock-Free Work Stealing）**：每个核心维护本地的就绪队列；空闲的核心通过原子指令偷取其他过载核心的任务，彻底消除了全局任务锁竞争；
- **主动让出（Cooperative Yield）**：一旦处理完当前 RPC，如果本地队列为空，核心在微秒之内主动向 I/O 内核发出“我还空闲，可被借调”的信号。

## 7. 实验评估与基准对比（NSDI '19 真实表现）

在论文的评测章节中，作者将 Shenango 与标准 Linux 内核、纯内核旁路系统（ZygOS）在 Memcached 高负载下进行了严酷的对比测试：

```text
+--------------------------------------------------------------+
|                 Memcached 延迟与吞吐性能对比曲线              |
|                                                              |
| 尾延迟 (99% Tail)                                            |
|   400 μs |                        Linux (在 80 万 QPS 时崩溃) |
|          |                         /                         |
|   100 μs |                        /                          |
|          |                       /                           |
|    10 μs |----------------------+----+                       |
|          |                     /     |   Shenango & ZygOS    |
|     5 μs +--------------------+------+---------------------+ |
|          0                 80万     160万        300万 QPS   |
|                                                              |
| 核心利用率 (低负载 20 万 QPS 阶段):                          |
| - ZygOS: 100% 独占核心自旋，利用率无法释放给其他任务 (浪费 80%)|

```

**测试数据震撼业界**：

- 在 80 万 QPS 时，传统 Linux 的 99% 尾延迟飙升到了 **300~400 微秒**，并迅速由于队列溢出丢包瘫痪；
- Shenango 与 ZygOS 将尾延迟死死压制在 **5 微秒之内**，吞吐量突破 **300 万 QPS**（提升近 4 倍）；
- 更关键的是：在低流量时，Shenango 能在不伤及 5 微秒尾延迟的前提下，将集群平均 CPU 利用率拉升到接近 100%！

## 8. 课堂精选 Q&A 研讨

**Q1：为什么 I/O 内核自己不直接通过重新配置网卡硬件（RSS 流哈希）来分流报文，而要在软件层面调度？**  
**Robert 教授**：  这是硬件体系结构的深刻限制。现代网卡的 RSS（Receive Side Scaling）流哈希分发是硬编码在固件里的。如果通过 PCIe 总线向网卡芯片重新配置哈希转向表，**硬件总线往返需要消耗数百微秒（100s μs）**！在微秒级世界里，几百微秒相当于“永恒的停顿”。软件在 CPU 核心之间传递指针只需要纳秒，因此在软件 I/O 内核中完成重定向比直接修改硬件快了两个数量级！

**Q2：Shenango 是一个能够直接替代通用 Linux 的完整操作系统吗？**  
**Robert 教授**：  
并不是。Shenango 是一篇前沿的研究型学术论文（Research Paper）。它是一个高度定制的特化系统（运行在 Linux 基础之上），专为无阻塞内存 RPC 服务优化。如果你想在它上面运行一个带有重型磁盘文件系统交互、或者需要通用权限沙箱隔离的传统 Unix 应用，它并没有提供通用的抽象。但它所展示的微秒级调度哲学，正在深刻重塑新一代云原生内核与数据中心架构。

## 五、与 xv6 网络实验的关系（思考题解答）

::: example
**Q：在 xv6 里应用能直接把包写进 NIC 队列吗？xv6 net 实验有几个 NIC 队列？**
:::

- **应用不能直接碰 NIC**。xv6 走的是**传统内核中介**模型：用户进程通过系统调用（socket/read/write）进内核，由内核里的 **E1000 驱动**（`e1000.c` 的 `e1000_transmit` / `e1000_recv`）去操作网卡的发送/接收环。应用碰不到 NIC 的 DMA 环——这正是 Figure 2 里「传统系统应用无法访问 NIC 硬件队列」的对照。
- **xv6 net 实验只有一对队列**：**一个 TX 环 + 一个 RX 环**（各 16 个描述符），单核处理、靠中断收包。
- **Shenango 则相反**：每个核一个队列（实验里 16 个 NIC 队列），应用 runtime 在用户态**直接轮询**属于自己的共享内存包队列，IOKernel 用软件把包按核分发——是 kernel-bypass + 多队列 + 轮询的路子。

| | xv6 net 实验 | Shenango |
| --- | --- | --- |
| 应用能否直接访问 NIC 队列 | ❌ 必须经内核 E1000 驱动 | ✅ 用户态 runtime 直接轮询 |
| NIC 队列数 | 1 个 RX + 1 个 TX | 多个（每核一个，实验 16 个）|
| 收包方式 | 中断 | 轮询（专属核）|
| 协议栈 | 内核里 | 用户态 runtime |

## 六、论文重点图

> 按整理惯例，论文部分只记录图中最重点的内容。

**Figure 2：整体架构**

- Shenango 把数据面拆成**特权的 IOKernel**（独占核）和**非特权的每应用 runtime**。
- 包从 NIC 进来 → IOKernel 解复用 → 分发到**共享内存队列** → 应用 runtime 直接轮询取走，全程绕过传统内核网络栈。
- 与常规系统形成鲜明对比：常规系统里应用**根本访问不到 NIC 硬件队列**。

**拥塞检测机制图/算法**

- IOKernel 约每 **5µs** 检查一次系统状态，同时盯**包队列**（NIC 积压）和**应用 runqueue**（待处理工作）。
- 队列深度上升 = CPU 不够 → 把核从批处理任务收回给网络应用。这个基于轮询的反馈环实现了亚毫秒级的负载响应。

**核 steering / RSS**

- IOKernel 用 **RSS** 把流量导向特定核——不是均匀摊开，而是按流 steer 到应用核，减少缓存失效与协调开销。

**性能结果（Pareto 前沿与利用率）**

- **延迟**：请求-响应负载下尾延迟低至**个位数微秒**（Linux/IX 是毫秒级）。
- **CPU 效率**：网络低负载时能**腾出 10–15 个核**给批处理计算。
- **延迟-吞吐折中**：比 Arachne、IX、ZygOS 好约 **10×** 的 Pareto 前沿；在 memcached、RocksDB 等真实负载上全面优于 Linux/IX/ZygOS。
- 注意 Shenango 的延迟曲线比 ZygOS **更早开始上升**——因为它在动态共享核：负载升高、预留核占满后需要抢占批处理、重分配核，这一步引入了额外延迟（但换来了高利用率）。
