# Lec 16 分布式事务与两阶段提交

## TL;DR

- 分布式事务解决跨多个物理数据分片的原子提交（Atomic Commit），任何单一分片发生异常均要求全局回滚。
- 两阶段提交协议（2PC）通过准备（Prepare）与提交（Commit）两轮网络协商保证原子性，但存在协调者宕机引发的无限持锁阻塞缺陷。
- 经典三阶段提交（3PC）在现实不可靠网络分区下存在严重脑裂风险，工业界普遍放弃使用。
- 现代 NewSQL 核心架构采用“2PC 协调跨分片原子性 + Paxos/Raft 解决分片内多副本高可用”的融合范式，终结了协调者单点阻塞。

## 架构演进与核心洞察

::: insight 2PC 与 Paxos 的黄金组合
许多人容易混淆两阶段提交（2PC）与 Paxos 共识协议的职责边界。2PC 解决的是“原子提交（Atomic Commit）”——各个参与者节点管理着互不相同的数据分区，只要有一个节点违反完整性约束，所有节点必须集体回滚；而 Paxos/Raft 解决的是“复制共识（Consensus）”——各个节点保存同一份数据的冗余副本，只要多数派存活即可达成共识并持续对外服务。现代工业级分布式数据库（如 Google Spanner、CockroachDB、TiDB）的最佳实践是：底层多副本用 Paxos/Raft 保障单分片高可用与无阻塞选举，上层跨分片事务用 2PC 保证分布式全局原子性。
:::

## 1. 跨节点分布式事务与原子性危机

在单机数据库中，事务提交由一条写入本地预写日志文件的 `<COMMIT>` 记录瞬间决定。而在无共享（Shared-Nothing）集群中，数据被水平切分存放在不同物理节点中。一个跨分片转账事务同时修改了节点 A 的扣款账户和节点 B 的入账账户：

```text
                  分布式转账事务: 从节点 A 扣款 100，向节点 B 入账 100
                                 |
        +------------------------+------------------------+
        | (网络传输)                                      | (网络传输)
        v                                                 v
  [ 参与者节点 A (Shard 1) ]                       [ 参与者节点 B (Shard 2) ]
  执行: UPDATE Account A...                        执行: UPDATE Account B...
  扣款成功，准备提交!                              突发断电宕机 / 磁盘爆满报错!
```

- **核心矛盾**：没有任何单一物理节点拥有全知视角。若节点 A 单方面提交，而节点 B 故障中止，数据一致性将被彻底破坏；若节点 A 无限期等待节点 B 的网络回音，其持有的行锁将长期阻塞其他并发业务。
- **系统目标**：设计分布式原子提交协议（Atomic Commit Protocol），确保所有参与节点在面对任意网络延迟、消息丢包与单机断电重启时，达成绝对一致的提交或中止决议。

### 1.1 经典草稿方案的演进与破灭（MIT 课堂推演）

MIT 6.5830 课件深入剖析了实现分布式提交的三次思维演进：

1. **草稿方案 1（独立 ARIES，直接提交）**：
   - 设想：各个工作节点分别在本地跑自己的 ARIES 恢复引擎。当某一个工作节点在本地刷盘提交后，广播通知其他节点“我已提交，大家跟进”；
   - **致命缺陷**：若某节点因约束冲突本地执行了 `ABORT`，而其他节点已持久化提交，直接导致事务原子性瓦解。
2. **草稿方案 2（单轮协调者询问，无准备阶段）**：
   - 设想：引入一个中央协调者（Coordinator）。协调者直接向各个节点发送提交请求，节点收到后本地执行提交；
   - **致命缺陷**：节点 1 提交成功，但网络瞬间发生断网，发给节点 2 的提交指令丢失，节点 2 因超时选择回滚，系统再次陷入不一致。
3. **方案 3（两阶段提交原型）**：
   - **核心思想**：提交必须分为两个阶段——先询问“大家能否提交？”，所有节点在本地将所有修改强制落盘锁定后投赞成票；只有全员同意，协调者才发出真正的提交指令。这便是经典的 **两阶段提交协议（Two-Phase Commit, 2PC）**。

## 2. 分布式理论边界：从双将军问题到 FLP 不可能性定理

在探讨分布式提交协议之前，必须确立不可逾越的理论物理边界：

### 2.1 双将军问题（Two Generals Problem, Jim Gray 1978）
Jim Gray 证明了：在**不可靠的通信信道（可能丢包、延迟）**中，两台计算机试图通过消息传递对同一行动达成绝对确定的共识，在数学上是**不可能完成的任务**（最后发送确认的一方永远无法得知确认消息是否被对方接收到）。

### 2.2 FLP 不可能性定理（Fischer, Lynch, Paterson, 1985）
::: theorem FLP 不可能性定理
在纯粹的**异步网络系统（Asynchronous Network）**中，只要有哪怕**一台节点可能发生停机故障（Fail-Stop Crash）**，没有任何确定性共识算法能够同时保证安全性（Safety）与终止性（Liveness）。
:::
- **工程启示**：所有真实世界的分布式提交协议必须引入**超时机制（Timeout）**与**网络弱同步假设（Partial Synchrony）**，在可用性与一致性之间做出权衡。

## 3. 两阶段提交协议（Two-Phase Commit / 2PC）机制

两阶段提交协议由 Jim Gray 于 1978 年提出，是工业级关系数据库跨分片事务处理的基石。

### 3.1 协议角色分工
- **协调者（Coordinator）**：负责全局统筹推进提交流程的中心节点（通常为客户端直接连接的网关节点）；
- **参与者（Participants / Cohorts）**：实际存储了受该事务影响的数据分片物理节点。

### 3.2 2PC 完整执行流程与状态机

```text
       协调者 (Coordinator)                                 参与者 (Participants)
                |                                                     |
                | ------------- 1. PREPARE (准备请求) --------------> |
                |                                                     | (检查本地完整性、
                |                                                     |  预留资源并强刷 WAL)
                | <------------ 2. VOTE_COMMIT / VOTE_ABORT --------- |
                |                                                     |
[ 收集全部投票 ]|                                                     |
[ 若全为 YES 则提交;                                                  |
  若有 NO 或超时则回滚 ]                                              |
[ 强刷 COMMIT/ABORT 日志 ]                                            |
                |                                                     |
                | ---------- 3. GLOBAL_COMMIT / GLOBAL_ABORT --------> |
                |                                                     | (正式执行本地提交/回滚，
                |                                                     |  释放锁资源，强刷日志)
                | <----------------- 4. ACK 应答 -------------------- |
                |                                                     |
[ 收到全部 ACK ]|                                                     |
[ 强刷 DONE 日志 ]                                                    |
```

#### 阶段一：准备阶段（Prepare / Voting Phase）
1. 协调者向所有参与者发送 `PREPARE` 消息；
2. 每一个参与者收到 `PREPARE` 后，在本地进行严格校验：
   - 检查所有约束（唯一性、外键、余额充足性）是否满足；
   - **将该事务所有的更新物理改动（Redo 日志）与撤销凭证（Undo 日志）强制刷写至稳定外存（Force-WAL）**；
   - 保持所有相关的排他行锁（X 锁）继续锁定；
3. 参与者投出决定性选票并落盘：
   - **同意（VOTE_COMMIT / YES）**：在本地日志强制写入 `<PREPARED>` 记录，回复 `YES`。
     ::: important 参与者的不可撤销承诺
     参与者一旦投出 `YES` 并将 `<PREPARED>` 刷盘，便对全世界作出了绝对保证：无论后续发生宕机断电还是硬件重启，该节点都有绝对能力在任意时刻完成提交！参与者在此刻彻底放弃了单方面回滚事务的权利。
     :::
   - **拒绝（VOTE_ABORT / NO）**：在本地写入 `<ABORT>` 记录，向协调者回复 `NO`，并可安全释放本地资源。

#### 阶段二：提交阶段（Commit Phase）
1. 协调者统计所有选票：
   - **全票通过（All Vote YES）**：
     协调者向本地磁盘**强制刷写一条 `<COMMIT>` 日志**。**此瞬间是该分布式事务在逻辑上正式提交的法定时刻（Atomic Decision Point）！** 随后向所有参与者广播 `GLOBAL_COMMIT`；
   - **一票否决（Any Vote NO）或等待超时**：
     协调者在本地强刷一条 `<ABORT>` 日志，随后向所有参与者广播 `GLOBAL_ABORT`；
2. 参与者执行最终决议：
   - 收到 `GLOBAL_COMMIT`：执行本地提交，在日志追加提交记录，**释放持有的所有行锁**，向协调者回复 `ACK`；
   - 收到 `GLOBAL_ABORT`：利用本地 Undo 日志回滚数据，释放行锁，向协调者回复 `ACK`；
3. 协调者收到所有参与者的 `ACK` 后，向本地日志写入一条 `<DONE>` 记录，事务上下文安全回收。

## 4. 2PC 与 ARIES 协同故障恢复（Crash Recovery）

2PC 的正确性完全依赖于各节点在系统重启恢复期间，严格依据各自本地的预写日志（WAL）重建事务状态。协调者必须在向网络发送任何决定性指令前将决策强刷落盘，参与者也必须在投出赞成票前将自身的未决修改持久化。

### 4.1 五大典型崩溃场景与恢复行为矩阵

| 节点角色 | 崩溃发生的关键物理时序 | 重启恢复后的确定性处理逻辑 |
| :--- | :--- | :--- |
| **协调者** | 发送 `PREPARE` 之前突发崩溃 | 本地日志中无任何决策记录。恢复子系统直接在本地追加一条 `ABORT` 记录，向客户端与参与者通报中止 |
| **参与者** | 收到 `PREPARE` 前后发生崩溃 | 参与者未投出赞成票或投出 `NO`。协调者在等待超时后主动判定全局中止，通知所有活跃参与者回滚 |
| **参与者** | 投出 `YES` 并落盘后发生崩溃 | 重启后恢复引擎扫描本地日志，发现事务处于 `PREPARED` 挂起状态。必须主动向协调者发送询问（`Status Query`），收到决策前严格持锁等待 |
| **协调者** | 决策刷盘后、收到全量 ACK 前崩溃 | 重启后扫描日志发现存在 `COMMIT` 但缺失 `DONE` 记录。协调者依据外存决策重新向未确认的参与者补发通知，收齐后写入 `DONE` |
| **参与者** | 本地提交落盘后、发送 ACK 前崩溃 | 重启后恢复引擎重演历史（Redo）完成本地提交，重新向协调者补发 `ACK` 确认报文 |

### 4.2 协调者与参与者状态机收敛证明
- **协调者的垃圾回收与 DONE 标记**：若协调者收到全部参与者的 ACK 后不记录 `DONE`，其必须永久在内存维护该事务状态以防参与者重复询问。写入 `DONE` 标志着分布式生命周期的终结，后续若收到重复询问可安全回退至已提交状态。
- **参与者单向防线**：在 `PREPARED` 状态下的参与者绝对不能擅自根据本地超时回滚事务，因为协调者可能已经做出提交决议并完成持久化。

## 5. 2PC 的致命死穴：无限持锁阻塞（The Blocking Problem）

尽管 2PC 确保了原子性，但它在分布式理论中拥有一个致命缺陷：**两阶段提交是一个强阻塞式协议（Blocking Protocol）！**

```text
时序场景:
  1. 协调者广播 PREPARE;
  2. 所有参与者本地准备完毕，强刷 WAL，全部回复 VOTE_COMMIT (YES);
  3. 协调者收到全票 YES;
  4. 协调者尚未把 COMMIT 刷盘，物理服务器电源突发烧毁，彻底断电宕机!
```

### 5.1 参与者的“不确定窗口（In-Doubt Window）”
此时所有参与者均处于已投出 `YES`、等待最终指令的悬空状态：
- **参与者能否单方面决定回滚？**  
  **绝对不能！** 协调者可能在断电前一瞬间已经将 `COMMIT` 刷盘，单方面回滚将导致数据产生致命分裂。
- **参与者能否单方面决定提交？**  
  **绝对不能！** 协调者可能因某个参与者网络断开而选择了全局回滚。
- **灾难后果**：  
  所有参与者必须**无限期挂起等待协调者被物理抢修并重启**！在此期间，所有涉及的数据行锁**全部被死死锁定，无法释放**，后续并发事务全部排队堵塞，引发全集群级联雪崩。

### 5.2 三阶段提交（3PC）的理论尝试与现实破灭
Dale Skeen 于 1981 年提出了**三阶段提交协议（Three-Phase Commit, 3PC）**，在准备与提交之间插入了缓冲的 `Pre-Commit` 阶段，试图通过超时推导实现无阻塞推进。
::: pitfall 现实网络环境下的 3PC 幻灭
3PC 的数学无阻塞证明依赖于一个完全脱离现实的假设——**网络永不发生网络分区（No Network Partition）**！而在真实生产环境中，网络丢包、交换机抖动与跨机房断网是常态。一旦遭遇网络分区，3PC 会因分区局部超时导致不同子集群分别做出提交与回滚的相反决议，引发灾难性的**数据脑裂（Split-Brain）**。因此现代工业界一致放弃了 3PC。
:::

## 6. 高可用数据副本拓扑与 K-Safety

为了防止单机硬件损毁造成数据永久丢失，数据库管理系统（DBMS）跨冗余节点维护多份数据副本。

![分布式副本复制拓扑对比图：主从复制读写分离架构与多主复制并发写入架构](https://tc-1258979383.cos.ap-guangzhou.myqcloud.com/image-20250903165719737.png)

1. **主从复制模式（Primary-Replica）**：
   - 所有写入操作统一路由至指定的主节点（Primary），主节点在本地处理并持久化后将日志传播至从副本；
   - 从副本（Replicas）承担只读查询，分担主库压力；当主库发生故障时，系统通过选举机制晋升新主库；
2. **多主复制模式（Multi-Primary / Active-Active）**：
   - 事务可以在任意副本节点并发更新数据对象，节点之间必须依赖分布式冲突仲裁或原子提交协议保证一致性；
3. **K-Safety 容灾指标**：
   - 系统容忍至多 $K$ 个节点同时发生永久性物理损坏依然保持可用与数据零丢失，每个数据对象的物理副本总数必须至少达到 $K + 1$。

## 7. 现代 NewSQL 终极破局：2PC + Paxos / Raft 共识集成

现代工业级分布式数据库（以 **Google Spanner**、**CockroachDB**、**TiDB** 为代表）彻底终结 2PC 单点阻塞的方案不是废弃 2PC，而是**使用 Paxos / Raft 复制状态机对 2PC 进行全武装**：

```text
                  分布式事务协调者 (Transaction Coordinator)
                  (本身不是单机，而是一个高可用 Paxos Group!)
                  +-----------------------------------------+
                  |  [Leader] <---> [Follower] <---> [Follower]
                  +-----------------------------------------+
                                       |
                   (运行 2PC 原子提交协议，调度各个分片)
                                       |
        +------------------------------+------------------------------+
        |                                                             |
        v                                                             v
分片 1 (Shard 1 参与者):                                    分片 2 (Shard 2 参与者):
+-----------------------------------+                       +-----------------------------------+
| 一个独立的 Paxos / Raft Group:    |                       | 一个独立的 Paxos / Raft Group:    |
|   [Leader]                        |                       |   [Leader]                        |
|    /    \                         |                       |    /    \                         |
| [Foll]  [Foll]                    |                       | [Foll]  [Foll]                    |
+-----------------------------------+                       +-----------------------------------+
```

### 7.1 分层架构与责任解耦
1. **分片内部（Intra-Shard Replication）**：每一个数据分片以及协调者本身，都是一个独立的由 3 或 5 个物理副本组成的 **Paxos / Raft 复制组**；
   - 组内任意单机物理宕机，Paxos 多数派在百毫秒内自动选出新 Leader 继续服务，**单点故障在物理层被彻底消除**；
2. **跨分片事务（Cross-Shard Atomicity）**：各分片 Leader 之间依然运行标准的 2PC 协议；
   - **破解 2PC 阻塞**：若协调者 Leader 所在物理机宕机，其背后的 Paxos 复制组会立即选举出新 Leader。新 Leader 继承先前已同步的决策日志，平滑继续推进 2PC，**参与者绝不会无限期被卡死在 Prepared 状态**！

### 7.2 Google Spanner 与 TrueTime 外部一致性
Google Spanner（OSDI 2012）在全球部署中落地了 2PC 与 Paxos 的结合，并引入基于 GPS 与原子钟硬件的 **TrueTime API**：
- `TrueTime.now()` 返回确定性的时间置信区间 $[t.earliest, t.latest]$，最大不确定度界限为 $\epsilon$（通常 $\le 7\text{ms}$）；
- **提交等待规则（Commit Wait）**：事务分配提交时间戳 $s$，并在向客户端返回成功前强制睡眠等待 $2\epsilon$，确保绝对的外部一致性（External Consistency / Linearizability）与无锁只读快照扫描。

## 8. CAP 定理与 PACELC 模型权衡

在分布式系统设计中，一致性与可用性受制于经典理论约束：

1. **CAP 定理（Eric Brewer, 2000）**：
   在存在网络分区（Partition Tolerance, P）的现实环境下，系统只能在一致性（Consistency, C，等价于单副本严格线性一致性）与可用性（Availability, A，非故障节点必定成功响应）之间二选一：
   - **CP 系统**：发生网络分区时拒绝写入，优先保证强一致性（如 HBase、ZooKeeper、Spanner）；
   - **AP 系统**：发生网络分区时继续接受写入，保证可用性但牺牲实时一致性（如 Cassandra、DynamoDB）。
2. **PACELC 定理（Daniel Abadi, 2012）**：
   CAP 仅关注出现网络故障时的抉择，而 PACELC 补全了系统正常运行时的常态权衡：
   - **如果存在网络分区（If there is Partition, P）**：系统在可用性（Availability, A）与一致性（Consistency, C）之间权衡；
   - **否则在正常运行时（Else, E）**：系统在延迟（Latency, L）与一致性（Consistency, C）之间权衡（追求极低读写延迟必须牺牲严格一致性）。

## 9. 经典文献研读与学术思辨（Literature Review）

### 9.1 必读奠基论文

1. **Jim Gray (1978)**  
   *`Notes on Data Base Operating Systems`*. IBM Research Report / Operating Systems, LNCS 60.  
   **核心贡献**：首次系统阐明了双将军问题，形式化推导了两阶段提交（2PC）的协议流程与 WAL 故障恢复机制，奠定了事务型分布式系统的理论大厦。
2. **Fischer, Lynch, Paterson (1985)**  
   *`Impossibility of Distributed Consensus with One Faulty Process`*. Journal of the ACM (JACM).  
   **核心贡献**：证明了计算机科学史上著名的 FLP 不可能性定理，确立了异步分布式共识算法的理论边界，推动了后续工程系统对弱同步假设与超时的广泛采用。
3. **James C. Corbett et al. (Google, 2012)**  
   *`Spanner: Google’s Globally-Distributed Database`*. USENIX OSDI 2012.  
   **核心贡献**：展示了全球分布式数据库的工业巅峰，创新性地将 2PC、Multi-Paxos 与 TrueTime 硬件原子钟深度结合，在地理级分布式集群上达成了强一致性与线性事务隔离。

### 9.2 学术深度思辨题

::: insight 研读思考题 1：两阶段提交（2PC）的阻塞缺陷与网络分区下的可用性抉择
**问题**：为什么在两阶段提交协议中，处于 Prepared 状态的参与者在与协调者失联后，即便与其他参与者相互通信，也无法在所有场景下自主决定提交或中止？  
**深度解答**：  
设系统包含协调者 $C$ 与参与者 $P_1, P_2$。若 $P_1$ 与 $P_2$ 均已投出 YES 处于 Prepared 状态，随后 $C$ 宕机断联。  
- 若 $P_1$ 与 $P_2$ 能相互通信，发现对方都投了 YES，它们依然**不能贸然决定全局提交**！因为可能存在第三个参与者 $P_3$，在崩溃前向 $C$ 投了 NO，或者 $C$ 在断电前已在本地强刷了 ABORT。  
- 反之，它们也**不能贸然决定全局中止**！因为协调者 $C$ 可能在宕机前的那一纳秒，刚刚将 COMMIT 写入本地日志外存并已向客户端返回了成功确认。  
若参与者单方面做出任何假设，一旦协调者重启恢复，数据必定产生灾难性的状态分裂。因此，只要参与者无法与协调者取得确定性法定决策，就必须无限期处于持锁阻塞的炼狱状态。2PC 是一个典型的 CP 协议，在面对协调者崩溃时毫不犹豫地牺牲了系统的可用性（Availability）。
:::

::: insight 研读思考题 2：Spanner TrueTime Commit Wait 与物理不确定性边界 $\epsilon$ 的延迟约束
**问题**：Google Spanner 中的事务为何必须故意睡眠等待 $2\epsilon$ 毫秒？若全球原子钟硬件故障导致时钟漂移不确定度 $\epsilon$ 突然膨胀至 1 秒，系统会发生数据不一致还是性能剧烈衰退？  
**深度解答**：  
Spanner 分配事务提交时间戳 $s = \text{now}().\text{latest}$。为了满足外部一致性（若 $T_2$ 在现实世界时间晚于 $T_1$ 提交，则必有 $s_2 > s_1$），系统必须确保当 $T_1$ 的提交结果对外界可见时，现实世界中的绝对真实时间 $t_{\text{absolute}}$ 已经严格超过了时间戳 $s$。  
由于 $\text{now}()$ 的误差范围为 $[t - \epsilon, t + \epsilon]$，从分配 $s = t_0 + \epsilon$ 到真实时间越过 $s$，所需的最坏现实物理时间间隔正好是 $2\epsilon$。因此，Spanner 强制调用 `Commit Wait` 挂起当前线程等待 $2\epsilon$ 之后才向客户端回复确认。  
若原子钟同步失效导致 $\epsilon$ 骤增至 1 秒：Spanner 的**安全性（Safety）绝对不会破坏**，外部一致性依然得到百分之百数学保障；但由于每个写事务提交时都必须强行睡眠等待长达 2 秒，系统的写延迟将从数毫秒暴增至数秒，事务吞吐量将发生灾难性的剧烈衰退。
:::

::: insight 研读思考题 3：2PC 与 Paxos 的层级协作模型：为什么不直接用 Paxos 替代 2PC？
**问题**：既然 Paxos 具有强大多项式级的无阻塞容灾能力，为什么现代分布式数据库不能直接完全使用 Paxos 处理跨分片事务，而依然需要保留“臭名昭著”的 2PC 框架？  
**深度解答**：  
这源于“状态机复制”与“原子提交”在分布式语义上的本质正交性：  
1. **Paxos 是多数派裁决（Majority Voting）**：其语义是只要 $\lfloor N/2 \rfloor + 1$ 个副本同意，某个提议即可通过生效；少数派节点的拒绝或宕机被安全忽略。  
2. **分布式事务是全票通过（Unanimous Agreement）**：跨分片事务中的每一个分片管理着互不重叠的数据集。如果 Shard 1 的银行账户扣款成功，而 Shard 2 发现用户不存在或透支超额投出拒绝，系统**绝对不能**依靠多数派“2 票赞成对 1 票反对”强制提交事务！任何一个分片的拒绝都代表着业务完整性的破坏，必须有一票否决权。  
因此，Paxos 的多数派模型天然无法表达跨分片事务的一票否决语义。现代系统的破局之道是**分层治理**：分片内部用 Paxos 追求“多数派存活即可用”的高可用复制，跨分片之间用 2PC 严格捍卫“全员同意才可提交”的原子性底线。
:::
