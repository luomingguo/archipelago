# Lec 5 索引机制与访问路径

## TL;DR

- 访问路径（Access Methods）决定引擎在全表堆扫描与索引查找间的物理抉择；受 SSD 随机寻道与顺序带宽差异影响，选择度低于约 0.1% 时全表扫描反而显著优于索引随机回表。
- B+ 树凭借高分支因子、半满不变量与叶节点双向兄弟链表，构成单维标量点查与范围检索无可争议的标准架构。
- 面对高维空间与地理数据，一维 B+ 树的字典序投影导致局部性撕裂；R*-树通过联合优化重叠度、边框周长、面积与强制重新插入（Forced Reinsert），彻底解决了多维剪枝发散难题。
- 通用搜索树（GiST）将平衡树的并发加锁与 ARIES 崩溃恢复同自定义谓词解耦，为 PostGIS 等工业级空间引擎提供基石。
- 面对 AI 大模型高维向量（维度 $d \ge 50$），“维数灾难”致使树形 MBR 剪枝全盘失效，现代系统全面转向 HNSW 与 IVF-PQ 等近似最近邻（ANN）索引。

## 架构演进与核心洞察

::: insight 为什么优化器有时会“弃用”你精心建立的索引？
当你发现数据库查询没有走索引时，不要急着责怪优化器。优化器掌握着底层硬件的物理代价模型与数据分布直方图。如果选择度（Selectivity）过低，大量的随机 I/O 回表会导致极度严重的磁盘寻道震荡；此时将磁盘整块连续拉进内存做顺序流式过滤，性能反而高出几个数量级！
:::

## 核心访问路径与物理代价模型

在关系代数和 SQL 编译完成之后，执行引擎面临的第一个物理抉择是：**通过何种具体物理途径从外存中获取满足条件的元组？**

在典型的单表扫描场景中，表数据在磁盘上通常是以一系列无序的数据页（Data Pages）组成的堆文件（Heap File）形式持久化的。当用户提交一条包含范围谓词的过滤查询时：

```sql
SELECT * FROM Employees WHERE salary BETWEEN 50000 AND 80000;
```

DBMS 查询优化器必须在两条性质截然不同的**访问路径（Access Methods）**之间做出权衡：

1. **全表堆扫描（Heap Scan）**：
   执行引擎从堆文件的第一个物理数据块开始，依次顺序读取后续每一个页。对于每个读入缓冲池的物理页，遍历其内部的插槽目录（Slot Directory）和每条元组，逐行计算 `WHERE salary BETWEEN 50000 AND 80000` 表达式的布尔真值。
   - **系统级优势**：由于页面在物理存储设备或外存逻辑块上大多是连续存放的，全表扫描能够充分触发现代操作系统和底层存储控制器的流式预取（Read-Ahead Pre-fetching）机制，最大化饱和顺序 I/O 带宽，消除寻道延迟。
   - **根本性缺陷**：如果整张表包含 1000 万条记录（数百 GB），哪怕最终仅有 1 条记录满足薪资过滤条件，执行引擎也必须将所有数据页从磁盘完整搬运进内存，时间复杂度为严格的线性增长 $O(N)$。

2. **索引访问路径（Index Scan）**：
   若该表在 `salary` 属性上事先构建了辅助索引（如 B+ 树），执行引擎则将过滤谓词下推到索引树中。首先从常驻内存的根节点出发，经过对数级高度（通常仅需 2~3 次内部路由比较）直接定位到目标数据所在的叶子节点物理槽位。
   - **系统级优势**：对于高选择度（即仅命中少量元组）的精准点查与小范围检索，将检索复杂度从全表线性扫描降至极速的对数级 $O(\log N)$，大幅削减 CPU 过滤开销。
   - **维护与性能代价**：构建和维护索引并非零成本。任何写操作（`INSERT`、`UPDATE`、`DELETE`）都需要同步更新索引树；若更新导致节点分裂，还会引入额外的写放大；更为致命的是，非聚簇二级索引在获取元组物理标识符（RID）后，必须回表进行二次随机寻道。

```text
+--------------------------------------------------------------+
|                     两大基本访问路径对比                     |
|                                                              |
|   [ 全表堆扫描 Heap Scan ]                                   |
|   磁盘块 1 -> 磁盘块 2 -> 磁盘块 3 -> ... -> 磁盘块 100,000  |
|   (优点: 顺序 I/O、流式预取; 缺点: 随表规模膨胀开销线性增加) |
|                                                              |
|   [ 索引访问路径 Index Scan ]                                |
|   根节点 -> 内部路由节点 -> 叶子节点 (仅 3 次 I/O!) -> 取元组|
|   (优点: O(log N) 极速点查与范围扫; 缺点: 写入维护代价高昂)  |
+--------------------------------------------------------------+
```

### 覆盖索引与复合索引最左前缀

从数据组织的本质来看，数据库索引是一个物理上与堆文件并存的辅助键值映射表：$\text{Key} \to \text{RID (PageID, SlotID)}$ 或 $\text{Key} \to \text{Tuple}$。根据物理存储的组织形态，索引主要划分为聚簇索引、二级辅助索引和覆盖索引三大类：

聚簇索引决定了表数据的绝对物理排布顺序，因而在物理上每张数据表至多只能有一个聚簇索引；而二级非聚簇索引则允许数据库面向不同业务维度建立多个查询入口，但其代价在于查询常常需要通过 RID 回表访问底层堆文件。

```text
+-----------------------------------------------------------------------------+
|                         关系数据库三大核心索引形态                          |
|                                                                             |
|   索引类型          物理组织特征                           性能优势          |
|  +----------------+--------------------------------------+----------------+ |
|  | 聚簇索引       | 表数据的物理存储顺序与索引键的排序顺序| 范围查询极致性能|
|  | (Clustered)    | 严格一致。一张表物理上**至多有 1 个**!| (磁盘连续读取) |
|  | 非聚簇二级索引 | 索引叶子节点仅存储 `Key -> RID`，     | 加速多维度点查 |
|  | (Secondary)    | 真实元组仍在堆文件中乱序存放。        | (需回表查找)   |
|  | 覆盖索引       | 索引键包含查询所需的**全部列**字段   | **零回表 I/O!** |
|  | (Covering)     | (无需访问底层堆文件，Index-Only Scan)| 吞吐量暴涨十倍 |
|  +----------------+--------------------------------------+----------------+ |
+-----------------------------------------------------------------------------+
```

#### 覆盖索引（Covering Index / Index-Only Scan）
在传统非聚簇二级索引的访问中，“回表”是限制吞吐量的最主要瓶颈。当引擎在叶节点中找到一条满足过滤谓词的记录时，它拿到的是形如 `(PageID=1024, SlotID=12)` 的物理行标识符。为了获取查询目标列（例如员工薪资或姓名），执行引擎必须向缓冲池申请拉取 Page 1024。如果不同匹配项的 RID 散落在整个堆文件的各个物理页中，就会引发高频的随机小块 I/O 读取。

覆盖索引彻底颠覆了这一流程。考虑如下查询与联合索引定义：

```sql
-- 建立复合索引
CREATE INDEX idx_emp_dept ON Employees (dept_id, salary);

-- 执行查询
SELECT salary FROM Employees WHERE dept_id = 10;
```

在火山模型执行器初始化阶段，优化器对比查询所请求的列投影集合与索引树包含的键集合，发现 `WHERE` 需要的 `dept_id` 以及 `SELECT` 需要返回的 `salary`，均已被完整容纳在该索引的复合键物理结构中。执行引擎直接在索引叶子节点中完成元组抽取与结果集组装，**完全无需向底层堆文件发起任何换页请求**，使原本受制于磁盘寻道的 I/O 开销直接下降 50%~90%。

```text
+--------------------------------------------------------------+
|            普通索引回表 vs 覆盖索引 (Index-Only Scan)        |
|                                                              |
|   [ 方案 A: 普通非聚簇索引 (需回表) ]                        |
|   查 B+ 树叶节点 -> 拿到 RID (Page 5, Slot 2)                |
|                  -> 额外触发一次随机 I/O 读取 Page 5 拿字段!  |
|                                                              |
|   [ 方案 B: 覆盖索引 Covering Index (零回表!) ]              |
|   查 B+ 树叶节点 -> 索引自身已包含 salary 列 -> 直接返回!     |
|   (完全无需触碰物理堆文件，I/O 开销削减 50% 以上!)           |
+--------------------------------------------------------------+
```

#### 复合索引的最左匹配前缀规则（Prefix Matching）
对于联合索引 `CREATE INDEX idx_abc ON Table (a, b, c)`：
- `WHERE a = 1 AND b = 2 AND c = 3`：完全命中索引树遍历；
- `WHERE a = 1 AND b = 2`：完全命中（最左前缀匹配）；
- `WHERE b = 2 AND c = 3`：**完全无法使用该索引树的二分路由**！因为 B+ 树的第一级排序基准是 `a`，在 `a` 未知的情况下，`b` 和 `c` 在全局范围内是无序乱跳的。

### 基于 SSD 物理延迟的代价模型推导

许多初级开发者在进行数据库调优时往往持有一种盲目的教条：“只要有过滤查询，无脑加索引一定能加速”。这在复杂的工业级数据库内核中是一个严重的认知误区。数据库内核的成本模型（Cost Model）建立在真实的底层硬件延迟之上，优化器在决定是否使用非聚簇索引时，必须严密权衡“随机 I/O 寻道成本”与“顺序 I/O 流式传输吞吐”的物理临界点。

#### 物理延迟推演实战：
考虑一块典型的现代企业级 NVMe SSD，其物理技术参数如下：
- **随机寻道与小块读取延迟**：每次随机抽取一个 4KB 物理页平均耗时约为 $100\ \mu\text{s}$（即 $0.0001\text{ 秒}$，受限于控制器中断和闪存单元寻址）；
- **连续顺序传输带宽**：顺序读取时凭借闪存并发通道与内部流水线，带宽可稳定维持在 $1\text{ GB/s}$；
- **数据表规模**：假设整张数据表总大小 $T = 10\text{ GB}$，每条数据元组平均长度 $R = 100\text{ 字节}$，因此表内总记录数为 $10^8$ 条；
- **查询目标**：用户的 `WHERE` 谓词要求从表中筛选并读取 $B$ 字节的数据。

#### 代价公式对比：
1. **全表顺序扫描总耗时（Seq Scan）**：
   在全表扫描模式下，磁盘驱动器不需要在物理空间内频繁跳跃寻道。预取控制器以最大总线吞吐将所有块拉入缓冲池，总耗时仅取决于硬件带宽与表尺寸，与满足条件的元组数量 $B$ 完全解耦：
   $$\text{Time}_{\text{scan}} = \frac{T}{\text{Bandwidth}} = \frac{10\text{ GB}}{1\text{ GB/s}} = 10\text{ 秒}$$
   （不论命中 1 条记录还是全部命中，耗时恒定为 10 秒！）

2. **非聚簇二级索引随机点查总耗时（Index Lookup）**：
   在二级索引扫描模式下，索引树的遍历开销极低（树高为 3 时仅需 3 次缓存访问），但每一个命中的元组在获取其 RID 之后，由于数据在堆文件中是乱序插入的，每次回表都会在磁盘的不同闪存块位置触发一次昂贵的随机小页读取：
   $$\text{Time}_{\text{index}} = \left( \frac{B}{R} \times 100\ \mu\text{s} \right) + \frac{B}{1\text{ GB/s}}$$
   公式左侧第一项为回表触发的离散随机寻道耗时（元组数 $\times$ 寻道延迟），第二项为实际有效数据的网络/总线传输耗时。

#### 计算临界平衡点：
优化器需要求解的核心方程是：何时“二级索引回表的随机延迟总和”会反超“从头到尾读完整张 10GB 大表”？
$$\text{Time}_{\text{index}} > \text{Time}_{\text{scan}}$$
$$\frac{B}{100} \times 100 \times 10^{-6} + \frac{B}{10^9} > 10$$
$$10^{-6} B + 10^{-9} B > 10 \implies B \cdot (10^{-6} + 10^{-9}) > 10$$
$$B \gt \frac{10}{1.001 \times 10^{-6}} \approx 9.99\text{ MB}$$

当命中的数据量 $B$ 超过 9.99 MB 时，随机点查累积的寻道时间就已经吃光了全部时间预算。换算成选择度（Selectivity）：
$$\text{Selectivity} = \frac{9.99\text{ MB}}{10\text{ GB}} \approx 0.1\%$$

```text
+--------------------------------------------------------------+
|            全表扫描 vs 索引随机点查的代价转折点              |
|                                                              |
|   耗时 (秒)                                                  |
|     ^                                                        |
|     |                         / (索引随机点查耗时: 斜率极大) |
|     |                        /                               |
|     |                       /                                |
|  10 |----------------------*---------------- (全表扫描: 恒定)|
|     |                     /|                                 |
|     |                    / |                                 |
|   0 +-------------------/--+---------------------------->    |
|       0              10MB  10GB              读取数据量 (B)  |
|                                                              |
|   【结论震惊业界】：                                         |
|   在 10GB 的大表里，若查询结果超过仅仅 10MB（选择度 > 0.1%），|
|   优化器选择【全表扫描】的速度将远远甩开【索引查找】！       |
+--------------------------------------------------------------+
```

## 哈希表与动态外存哈希

哈希表（Hash Table）是一种实现关联数组的抽象数据类型，提供平均 $O(1)$ 的点查与更新复杂度。在数据库系统中，哈希结构广泛用于缓冲池页表管理、内存连接算子（Hash Join）以及哈希物理索引。

### 哈希函数选择与冲突解决
在内核工程中，数据库与密码学系统的关注点截然不同。密码学哈希（如 SHA-256、SM3）追求不可逆性与雪崩效应，计算指令极其复杂；而 DBMS 仅在引擎内部映射键值，无安全泄露风险，因而关注的绝对核心是：**计算速度（吞吐量）与碰撞均匀度**。
- **Facebook XXHash3 / MurmurHash3**：现代数据库内核的绝对事实标准，充分利用现代 CPU 的 SIMD 向量化指令集，处理每字节数据仅需零点几个时钟周期，且哈希离散度极高。

在冲突解决机制上，内存哈希通常采用**线性探测（Linear Probing）**或**罗宾汉哈希（Robin Hood Hashing）**以获得极致的 CPU 缓存行命中率；然而在外存场景中，静态哈希一旦填满就需要对全量磁盘文件做两倍扩容并重新计算哈希值，这将导致持续数小时的 I/O 阻塞。

### 可扩展哈希（Extendible Hashing）
为了彻底解决外存哈希的扩容痛点，Ronald Fagin 等人提出了**可扩展哈希（Extendible Hashing）**。其核心机制是将哈希表拆分为两级结构：常驻内存的小型**目录数组（Directory）**与实际存放数据的**外存数据桶页（Bucket Pages）**，并引入**全局深度（Global Depth: $G$）**与**局部深度（Local Depth: $L$）**：

- **全局深度 $G$**：表示目录索引使用的二进制哈希前缀位数，目录共有 $2^G$ 个插槽；
- **局部深度 $L$**：表示当前物理数据桶所依据的哈希前缀位数。当多个目录指针指向同一个桶时，必定有 $L < G$。

```text
+--------------------------------------------------------------+
|                       可扩展哈希 (Extendible Hashing)        |
|                                                              |
|   全局目录 (Global Depth = 2)        数据桶页 (Local Depth)  |
|   目录条目 (2 位二进制)                                      |
|   [ 00 ] --------------------------> [ 桶 A (Local Depth = 2)]|
|   [ 01 ] --------------------------> [ 桶 B (Local Depth = 2)]|
|   [ 10 ] --------------------------> [ 桶 C (Local Depth = 1)]|
|   [ 11 ] -----------------------------^                      |
|                                                              |
|   【分裂规则】：                                             |
|   若桶 A 溢出且 L == G：全局目录翻倍 (G 变为 3)，重新分配指针;|
|   若桶 C 溢出且 L < G：目录无需翻倍，仅分裂桶 C (L 变为 2)!  |
+--------------------------------------------------------------+
```

当向某个物理桶插入新键发生溢出时：
1. 若该桶的局部深度 $L < G$（如上述桶 C）：表明有多个目录插槽共享此桶。此时**全局目录无需做任何扩容**，只需新分配一个物理桶页，将原桶深度增至 $L+1$，并根据第 $L+1$ 位的二进制值（0 或 1）将数据在两个桶之间重新划分，随后调整目录对应的指针；
2. 若该桶的局部深度 $L = G$（如上述桶 A）：表明当前目录精度已无法区分溢出数据。此时触发**目录翻倍**：全局深度提升为 $G+1$，目录条目由 $2^G$ 增至 $2^{G+1}$，随后再执行桶分裂。由于翻倍的仅是极小的内存目录指针数组，底层所有其他数据桶完全无需做任何数据搬迁！

## 树形索引王者：B+ 树物理架构与动态维护

虽然学术界提出了 B-Tree、B*Tree、Blink-Tree、Bw-Tree 等诸多变体，但 **B+ 树（B+ Tree）** 依然是工业界五十年不动摇的绝对霸主。

```text
+-----------------------------------------------------------------------------+
|                             B+ 树经典多路平衡物理拓扑                       |
|                                                                             |
|                           [ 根节点 (Root): Key 35 ]                          |
|                                 /           \                               |
|             [ < 35 路由指针 ]  /             \  [ >= 35 路由指针 ]           |
|                               v               v                             |
|              [ 内部节点: Key 10, 20 ]       [ 内部节点: Key 50, 70 ]        |
|                /       |       \              /       |       \             |
|               v        v        v            v        v        v            |
|   叶子节点: [1..9] <-> [10..19] <-> [20..34] <-> [35..49] <-> [50..69] ... |
|   (双向链表)   |          |           |           |           |             |
|               v          v           v           v           v             |
|   物理数据: 真实元组 或 RID 指针 (直接支持极速顺序范围扫描!)                 |
+-----------------------------------------------------------------------------+
```

### B+ 树四大数学不变量
1. **严格多路自平衡（Perfect Balance）**：所有叶子节点严格位于完全相同的物理深度；
2. **极高分支因子（High Fanout: $m$）**：每个节点通常占用一个整页（如 4KB 或 8KB），能容纳数百个键（$m \approx 200 \sim 500$），因此数千万行数据的树高仅需 3~4 层；
3. **半满约束（Half-Full Rule）**：除根节点外，每个节点至少半满，所容纳的键数量满足：
   $$\lceil m / 2 \rceil - 1 \le \text{NumKeys} \le m - 1$$
4. **叶节点兄弟指针（Sibling Pointers）**：所有叶子节点之间通过双向链表首尾相连。执行范围查询（`BETWEEN 10 AND 50`）时，只需通过树根找到起点 `10`，后续顺着链表物理扫描即可，**完全无需回溯父节点**。

## 高维空间索引：从一维退化到 R*-Tree 的几何演进

虽然 B+ 树在一维标量数据（整数、时间戳、单字段字符串）上表现完美，但在地理空间数据（经纬度坐标）、CAD 几何体、多维点集检索中，一维索引彻底失效。

### 为什么一维 B+ 树在高维/空间多维查询中失效？

考虑一个典型的二维空间范围查询：

```sql
-- 查找位于某矩形区域内的所有商户点
SELECT * FROM Points 
WHERE x BETWEEN 10 AND 20 
  AND y BETWEEN 100 AND 200;
```

假设我们在 `(x, y)` 上建立了一个复合 B+ 树索引（Composite Index）：
1. **字典序排序约束**：B+ 树只能按照单轴字典序排列元组：$(x_1, y_1) < (x_2, y_2) \iff (x_1 < x_2) \lor (x_1 = x_2 \land y_1 < y_2)$。
2. **一维投影撕裂二维局部性**：在物理存储上，只要 $x$ 坐标稍有不同（例如 $x=10$ 与 $x=11$），哪怕两者的 $y$ 坐标非常接近（如 $y=150$），它们在 B+ 树中也会被隔得极远！
3. **退化为海量跳读或全表扫描**：树只能在 $x \in [10, 20]$ 上进行初步定位；对于这个范围内的所有数据，必须全量扫描叶节点比对 $y$。若查询仅过滤 $y$，复合索引彻底瘫痪。

### 空间划分 vs 数据划分路线对决

在地理信息系统（GIS）、地图导航、自动驾驶雷达点云以及高维多特征检索等现实应用中，待索引的数据对象往往超越了一维数值的范畴。为了对多维几何空间中的点、线、多边形以及高维向量提供高效的范围剪枝与最近邻检索，学术界与工业界探索出两条截然不同的体系架构路线：**空间划分（Space Partitioning）**与**数据划分（Data Partitioning）**。

空间划分路线立足于“坐标空间本身的无重叠网格化切分”，认为只要将无限连续的几何空间划分为互不相交的局部区间，就能实现无歧义的点定位；而数据划分路线则立足于“围绕具体数据实体的动态聚类包络”，认为空间中无数据的空白区域无需建索引，应由多路平衡树动态调整包围盒以适配外存分页。

```text
+-----------------------------------------------------------------------------------+
|                        高维多维空间索引两大阵营技术对照表                         |
|                                                                                   |
|   对比维度          空间划分 (Space Partitioning)    数据划分 (Data Partitioning) |
|  +----------------+--------------------------------+----------------------------+ |
|  | 代表结构       | KD-Tree、Grid Files、Quad-Tree | R-Tree、R*-Tree、SS-Tree   |
|  | 划分依据       | 固定的空间坐标切割 (轴平行超平面)| 根据数据对象的分布动态聚类 |
|  | 空间重叠       | **零重叠**（空间互斥，每个点唯一）| **允许重叠** (MBR 间可交叠)|
|  | 树平衡性       | 数据倾斜时极易退化，难保证严格平衡| 保持类似 B+ 树的**严格平衡**|
|  | 外存适配性     | 较差（节点大小不规则，分裂难控）| **极佳**（节点严格对齐磁盘页)|
|  | 对象类型支持   | 主要适用于点（Points）         | 天然支持点、多边形与矩形   |
|  +----------------+--------------------------------+----------------------------+ |
+-----------------------------------------------------------------------------------+
```

在空间划分阵营中，最具代表性的是**网格文件（Grid Files）**、**k-d 树（k-d Tree）**与**四叉树（Quad-Tree）**。以四叉树为例：

#### 四叉树（Quad-Tree）
四叉树是一种将二维空间递归等分为四个正方象限（西北 NW、东北 NE、西南 SW、东南 SE）的树状数据结构。每个内部节点具有恰好四个子指针，分别对应四个互不相交的空间子区域。当某个象限内容纳的点数量超过单页容量上限时，该象限进一步递归四分。四叉树对于空间点数据的单点定位与均匀分布检索非常高效，但其致命缺陷在于：现实世界中的人口、车辆或地理 POI 呈现极度严重的向心聚集倾向（例如纽约曼哈顿中心的数据密度可能是撒哈拉沙漠的数百万倍）。这种极端倾斜会导致四叉树局部子树层级过深，树拓扑严重失衡，在磁盘页分页存储和高并发节点加锁时带来极大的系统工程开销。

### R-Tree（Guttman 1984）物理拓扑与查询剪枝

为了克服空间划分结构在外存对齐与平衡性上的固有缺陷，1984 年，加州大学伯克利分校的 Antonin Guttman 在 SIGMOD 会议上正式提出了 **R 树（R-Tree: A Dynamic Index Structure for Spatial Searching）**。R 树完全打破了“空间区域必须互不重叠”的思维桎梏，采用**数据驱动的最小外接矩形（MBR: Minimum Bounding Rectangle）**进行层次化动态包络，首次将 B 树经典的多路平衡、高外存利用率与对数级高保证度引入了多维空间。

#### 核心物理结构：
- **叶节点（Leaf Node）**：叶节点直接存放在数据磁盘页中，每个条目格式为 `(MBR, RID)`。其中 MBR 是紧紧包围该空间几何对象（点、折线或复杂多边形）的 $n$ 维闭区间轴平行超矩形：
  $$\text{MBR} = [x_{\min}, x_{\max}] \times [y_{\min}, y_{\max}]$$
- **内部节点（Internal Node）**：内部节点负责空间导航与多路剪枝，每个条目格式为 `(MBR, child_ptr)`。这里的 MBR 是能够完全覆盖该子节点所包含的所有下层子 MBR 的几何并集超矩形。

![R 树空间包围盒 MBR 分层嵌套几何拓扑](https://tc-1258979383.cos.ap-guangzhou.myqcloud.com/66bef0caa1652.png)

![R 树多层内部节点与叶子节点树状检索路径](https://tc-1258979383.cos.ap-guangzhou.myqcloud.com/66bef0e1be7f4.png)

::: pitfall 为什么原版 R 树的查询性能极易劣化？
Guttman 原版 R 树在节点分裂与插入时，仅依赖单一启发式——**最小化 MBR 面积增加量（Area Enlargement）**。这容易产生狭长且高度重叠（Overlap）的 MBR。当查询矩形落在重叠区时，执行引擎必须同时遍历多个分支，导致剪枝失效并引发大量随机 I/O！
:::

### 经典文献精读：R*-Tree（Beckmann et al. 1990）的四大几何优化

针对 Guttman 原版 R 树因盲目追求面积最小化而导致重叠恶化、分支剪枝失效的严重缺陷，1990 年，慕尼黑大学的 Norbert Beckmann、Hans-Peter Kriegel、Ralf Schneider 与 Bernhard Seeger 发表了划时代论文：  
> **“The R*-tree: An Efficient and Robust Access Method for Points and Rectangles”** (ACM SIGMOD 1990)

这篇论文不仅彻底奠定了现代空间索引的工业级标准，其严密的实验方法论与精妙的动态自组织算法，至今仍是数据库内核领域的典范之作。

#### 1. 四大联合优化几何准则
Beckmann 等人通过广泛的真实地理数据集（如不列颠哥伦比亚省地图水系、道路网）测试发现，仅仅衡量 MBR 面积覆盖是极度片面的。两棵总覆盖面积完全相同的空间树，在实际查询中的 I/O 次数可能相差数倍之巨。R*-Tree 首次系统性地确立了优秀多维索引树必须协同优化的四大几何目标：

1. **最小化兄弟节点 MBR 之间的重叠面积（Minimize Overlap Area）**：这是决定剪枝效率的生死线。重叠越小，给定一个查询窗口 $Q$，其同时与多个内部节点 MBR 相交的概率就越低，引擎就能更早地将搜索收敛为单路径向下，避免多分支搜索雪崩；
2. **最小化节点包围盒的覆盖总面积（Minimize Area Coverage）**：各个节点的 MBR 应该如同紧身衣一般仅仅贴合内部真实数据，包含的“空白死区（Dead Space）”越少，在面对随机点查和范围查询时产生“假阳性相交（False-positive Intersection）”的概率就越低；
3. **最小化外边框周长和（Minimize Margins / Perimeters）**：在面积固定的几何约束下，一个正方形的周长严格小于任何狭长扁平的长方形（即周长与形状的各向同性密切相关）。外框更接近正方形的 MBR 在面对各种不同长宽比的查询窗口时，表现出极高且稳健的平均相交概率，杜绝了由于极端扁平包围盒带来的异常相交；
4. **最大化物理存储利用率（Maximize Storage Utilization）**：通过优化每个磁盘块中条目的装填因子，使得整棵树能够以更少的磁盘页面总数容纳海量空间实体，直接降低树的物理高度，从根本上削减点查与范围遍历的基准 I/O 次数。

```text
+--------------------------------------------------------------+
|            R 树（仅面积优化） vs R*-树（综合多维优化）       |
|                                                              |
|   [ Guttman R-Tree: 产生狭长且重叠的 MBR ]                  |
|   +-------------------------+                                |
|   | MBR A                   |                                |
|   |         +---------------+--------------------+           |
|   |         | 重叠区 (Overlap): 触发双倍 I/O 搜索!|           |
|   +---------+---------------+                    |           |
|             | MBR B                              |           |
|             +------------------------------------+           |
|                                                              |
|   [ R*-Tree: 追求正方紧凑、零重叠或极低重叠 ]                |
|   +---------------+      +---------------+                   |
|   | MBR A (正方)  |      | MBR B (正方)  |  (零交集!         |
|   | (低周长/紧致) |      | (低周长/紧致) |   查询精准剪枝!)  |
|   +---------------+      +---------------+                   |
+--------------------------------------------------------------+
```

#### 2. 优化子树选择（ChooseSubtree）
- **内部节点**：选择使得加入条目后**面积增量（Area Enlargement）最小**的子节点；若并列则选择原面积最小的。
- **叶节点的父节点**：直接按**重叠增量（Overlap Enlargement）最小**选择！有效抑制叶子层级的重叠扩散。

#### 3. 强行重新插入（Forced Reinsert）
节点溢出时不立即分裂：
1. 计算溢出节点内所有 $M+1$ 个条目中心与整个 MBR 几何中心之间的距离；
2. 剔除距离中心最远的 $p$ 个条目（通常 $p = 30\% \times M$）；
3. 将剩余条目缩紧 MBR，而被剔除的离群条目重新从树根调用常规插入流程重新路由。

::: theorem 强行重插的死循环规避定理
在单次插入操作触发的向上路径中，**每个树层级至多允许执行一次 Forced Reinsert**。若重插后该层级再次溢出，直接执行常规 Split 分裂。此规则在数学上严格保证算法有限步终止。
:::

::: insight 为什么重新插入具有类似“局部碎片整理”的神奇功效？
早先插入的数据受限于当时局部的狭隘视野，容易被放置在次优分支中。强制重插将边缘条目重新放入具备全局最新视野的树根，往往能将其重新路由到更合适的全新子树中。实验表明这让存储利用率提升了 15%~20%，查询 I/O 下降了近 30%。
:::

#### 4. 基于多轴投影排序的最优分裂（Split）
1. **选择分裂轴**：对每个轴按坐标排序，评估所有满足半满约束的分组切分点，选择**两组 MBR 外框周长和（Margin Sum）最小的坐标轴**（促成正方几何体）；
2. **选择切分点**：在选定轴上，优先选择**两组 MBR 重叠面积（Overlap）最小**的切分点；并列时取面积和最小者。

### 通用搜索树抽象：GiST（Hellerstein et al. 1995）

为终结“每有一种新数据类型就要重写一棵树并重构并发与 WAL”的困局，Hellerstein 等人提出了 **GiST（Generalized Search Tree）**。内核提供通用的多路平衡树拓扑、页面锁管理与崩溃恢复，开发者只需实现 4 个核心方法：
1. `Consistent(entry, query)`：检查条目是否与查询谓词一致；
2. `Union(set_of_entries)`：计算一组条目的最小覆盖超集（在 R 树中即计算 MBR 并集）；
3. `Penalty(entry1, entry2)`：评估将 entry2 插入 entry1 的开销（如面积/重叠增量）；
4. `Compress(entry) / Decompress(entry)`：数据压缩与解包。

GiST 为现代开源地理信息事实标准 **PostGIS** 提供了最核心的底层引擎支撑。

## 现代多样化索引实战（课件 PPT 深度延伸）

对齐 MIT 6.5830 课件 PPT（Access Methods & Indexing, P.53~P.60），现代数据库将索引技术扩展至自动化、全文与语义向量三大领域：

### 自动化索引设计（Automatic Index Design）
在拥有成千上万 SQL 的复杂系统中，如何挑选最优索引组合？
- **数学本质**：在存储预算与写入延迟约束下，寻找最小化整体查询代价的索引子集，属于经典的 **NP-Hard 组合优化问题**；
- **工业方案**：AutoAdmin (MSR 1996)、PostgreSQL `hypopg`。通过向优化器注入**虚拟索引（Hypothetical Indexes）**的元数据，在零磁盘与物理构建开销下模拟代价，由优化器选出最优推荐。

### 倒排索引（Inverted Indexes / Full-Text Search）
针对大段非结构化文本的全文搜索：
- 关系表是 $\text{DocID} \to \text{Text}$；倒排索引建立 $\text{Term} \to \text{Posting List [DocID, Frequency, Offsets]}$；
- 词典（Term Dictionary）常驻内存采用 FST 前缀树维护，倒排链采用 Roaring Bitmap 紧凑压缩，原生支撑 Elasticsearch 与 PostgreSQL GIN 索引。

### 语义相似度与高维向量索引（Vector Indexes）
大模型时代的向量检索（Embeddings）：
- **维数灾难（Curse of Dimensionality）**：当维度 $d \ge 50$ 时，高维空间的测度集中现象导致超球体体积集中在表层外壳，任意两点间距离趋同。所有超矩形 MBR 发生近乎 100% 的重叠，致使 R 树等结构彻底失效，退化为暴力扫描！
- **近似最近邻（ANN: Approximate Nearest Neighbor）破局**：
  - **HNSW（Hierarchical Navigable Small World）**：基于多层跳表思想的多维图网络，实现对数级极速向量路由；
  - **IVF-PQ（倒排量化索引）**：利用聚类与乘积量化压缩内存带宽瓶颈。这一体系将在 **第 17 讲（向量数据库与最终一致性）** 中全景展开。

结合 MIT 课堂交互案例，面对以下四个高频典型 SQL 查询，系统架构师与优化器的决策推演如下：

### 场景 A：单列极值聚合查询
```sql
SELECT MAX(sal) FROM emp;
```
- **物理访问决策**：在 `emp.sal` 列上构建单列 B+ 树索引。
- **底层机制推演**：对于无索引的堆文件，计算最大值必须执行全表扫描并遍历所有元组，复杂度为严格的 $O(N)$。而在单列升序 B+ 树中，整棵树的最右侧叶子节点物理槽位中天然保存着全局最大值。优化器可以直接跳过所有内部中间节点，沿着最右侧路由指针直达目标叶节点，仅需消耗 1~2 次物理页 I/O 即可在 $O(1)$ 常数时间内返回结果，彻底免除了昂贵的聚合算子计算。

### 场景 B：唯一标识符单点等值点查
```sql
SELECT sal FROM emp WHERE id = 1;
```
- **物理访问决策**：若系统仅有严格点查需求且无需范围遍历，首选 `emp.id` 的**哈希索引（Hash Index）**；若业务同时涉及主键范围导出，则选用 B+ 树聚簇主键索引。
- **底层机制推演**：哈希索引通过哈希函数将 `id = 1` 直接映射为外存数据桶地址，理论期望 I/O 仅为 1 次，点查性能达到极致；而 B+ 树树高通常为 3~4 层，点查通常需要 2~3 次 I/O。

### 场景 C：单列范围过滤与非索引列投影
```sql
SELECT name FROM emp WHERE sal > 100k;
```
- **物理访问决策**：在 `(sal, name)` 上构建**覆盖复合索引（Covering Index）**。
- **底层机制推演**：如果仅在 `sal` 上建立普通非聚簇索引，当满足 `sal > 100k` 的员工数量较多时，执行引擎每拿到一个 RID 就必须回表读取堆文件获取 `name` 字段，产生密集的随机 I/O，极易被优化器放弃并退化为全表扫描。而将 `name` 共同打包进索引叶子节点后，范围扫描在索引树内部即可独立闭环提取数据，零回表开销，吞吐量提升显著。

### 场景 D：等值与范围组合多谓词过滤
```sql
SELECT name FROM emp WHERE sal > 100k AND dept = 2;
```
- **物理访问决策**：构建三列联合索引 `CREATE INDEX idx_dept_sal_name ON emp (dept, sal, name)`。
- **底层机制推演**：此处的关键在于**复合索引字段顺序的设计**！若将范围列 `sal` 置于最左端 `(sal, dept, name)`，在定位到 `sal > 100k` 的起点后，后续的 `dept` 字段在全局范围内是无序乱跳的，优化器无法利用树的二分路由对 `dept = 2` 进行剪枝；相反，将等值列 `dept` 置于最左端后，树首先以 $O(\log N)$ 锁定 `dept = 2` 的局部子树范围，随后在该连续区间内部再对 `sal > 100k` 进行连续叶子链表扫描，最后直接提取叶节点内置的 `name` 字段，达成最完美的 Index-Only 访问路径！

## 高维空间索引：从一维退化到 R*-Tree 的几何演进

虽然 B+ 树在一维标量数据（整数、时间戳、单字段字符串）上表现完美，但在地理空间数据（经纬度坐标）、CAD 几何体、多维点集检索中，一维索引彻底失效。

### 5.1 为什么一维 B+ 树在高维/空间多维查询中失效？

考虑一个典型的二维空间范围查询：

```sql
-- 查找位于某矩形区域内的所有商户点
SELECT * FROM Points 
WHERE x BETWEEN 10 AND 20 
  AND y BETWEEN 100 AND 200;
```

假设我们在 `(x, y)` 上建立了一个复合 B+ 树索引（Composite Index）：

1. **字典序排序约束**：B+ 树只能按照单轴字典序排列元组：$(x_1, y_1) < (x_2, y_2) \iff (x_1 < x_2) \lor (x_1 = x_2 \land y_1 < y_2)$。
2. **一维投影撕裂二维局部性**：在物理存储上，只要 $x$ 坐标稍有不同（例如 $x=10$ 与 $x=11$），哪怕两者的 $y$ 坐标非常接近（如 $y=150$），它们在 B+ 树中也会被隔得极远！
3. **退化为海量跳读或全表扫描**：
   - 树只能在 $x \in [10, 20]$ 上进行初步定位；
   - 对于这个范围内的**所有**数据，由于 $y$ 是乱序分布的，执行引擎必须扫描这整个 $x$ 区间的所有叶节点，逐条比对 $y$ 坐标；
   - 如果用户查询变成了 `WHERE y BETWEEN 100 AND 200`（未指定 $x$），由于违背最左前缀匹配，该复合 B+ 树**完全不可用**，不得不降级为全表扫描！

```text
+--------------------------------------------------------------+
|            一维 B+ 树无法保持多维空间邻近性（Locality）      |
|                                                              |
|   二维物理空间:                B+ 树内部存储 (按 x 字典序):  |
|   Y ^                           [ (1, 100), (1, 200) ]        |
|     |  A(1,100)   B(2,100)      [ (2, 100), (2, 200) ]        |
|     |                          ...                           |
|     |  C(1,10)    D(2,10)       [ (99, 100), (99, 200) ]      |
|   --+-------------------> X                                  |
|   空间中 A 与 B 极度相近!       但在 B+ 树中，若数据量极大，  |
|   空间中 C 与 D 极度相近!       A 与 B 可能被间隔数万个节点！ |
+--------------------------------------------------------------+
```

### 5.2 空间划分（Space Partitioning）vs 数据划分（Data Partitioning）

为了对多维数据进行有效索引，学术界与工业界探索出两条截然不同的路线：

```text
+-----------------------------------------------------------------------------------+
|                        高维多维空间索引两大阵营技术对照表                         |
|                                                                                   |
|   对比维度          空间划分 (Space Partitioning)    数据划分 (Data Partitioning) |
|  +----------------+--------------------------------+----------------------------+ |
|  | 代表结构       | KD-Tree、Grid Files、Quad-Tree | R-Tree、R*-Tree、SS-Tree   |
|  | 划分依据       | 固定的空间坐标切割 (轴平行超平面)| 根据数据对象的分布动态聚类 |
|  | 空间重叠       | **零重叠**（空间互斥，每个点唯一）| **允许重叠** (MBR 间可交叠)|
|  | 树平衡性       | 数据倾斜时极易退化，难保证严格平衡| 保持类似 B+ 树的**严格平衡**|
|  | 外存适配性     | 较差（节点大小不规则，分裂难控）| **极佳**（节点严格对齐磁盘页)|
|  | 对象类型支持   | 主要适用于点（Points）         | 天然支持点、多边形与矩形   |
|  +----------------+--------------------------------+----------------------------+ |
+-----------------------------------------------------------------------------------+
```

1. **四叉树（Quad-Tree）与 KD 树（k-d Tree）**：递归地将空间切分为象限或轴对齐超平面。当数据分布均匀时检索迅速，但在现实世界中人口或轨迹极度倾斜（如城市中心 vs 荒漠），会导致树严重偏斜，外存分页与并发锁控极其复杂。
2. **R 树系列（Data Partitioning）**：放弃空间零重叠的严苛约束，采用**最小外接矩形（MBR: Minimum Bounding Rectangle）**包络数据对象。虽然 MBR 之间可能重叠导致查询需要多路分支搜索，但其节点能够严格对齐磁盘页，保持完美的对数树高平衡。

### 5.3 R-Tree（Guttman 1984）基础拓扑与查询剪枝

1984 年，UC Berkeley 的 Antonin Guttman 在 SIGMOD 上发表了开创性论文 *“R-Trees: A Dynamic Index Structure for Spatial Searching”*，首次将 B 树的平衡多路理念推向多维空间。

#### 1. 核心物理结构：

- **叶节点（Leaf Node）**：存储条目格式为 `(MBR, RID)`，其中 MBR 是紧紧包围该空间对象（点、折线或多边形）的 $n$ 维闭区间矩形：
  $$\text{MBR} = [x_{\min}, x_{\max}] \times [y_{\min}, y_{\max}]$$
- **内部节点（Internal Node）**：存储条目格式为 `(MBR, child_ptr)`，其中 MBR 是能够完全覆盖该子节点所包含的所有下层 MBR 的最小超矩形。
- **数学不变量**：每个节点可容纳 $M$ 个条目，除根节点外至少容纳 $m \le \lceil M/2 \rceil$ 个条目（半满约束）。所有叶子节点处于同一物理深度。

```text
+-----------------------------------------------------------------------------+
|                             R 树分层嵌套 MBR 拓扑                           |
|                                                                             |
|      +---------------------------------------------------------------+      |
|      | 根节点 MBR R1: 覆盖全局空间                                    |      |
|      |   +-----------------------+     +-----------------------+     |      |
|      |   | 内部节点 MBR R2       |     | 内部节点 MBR R3       |     |      |
|      |   |  +-----+     +-----+  |     |  +-----+     +-----+  |     |      |
|      |   |  | e1  |     | e2  |  |     |  | e3  |     | e4  |  |     |      |
|      |   |  +-----+     +-----+  |     |  +-----+     +-----+  |     |      |
|      |   +-----------------------+     +-----------------------+     |      |
|      +---------------------------------------------------------------+      |
|                                                                             |
|   树状检索拓扑:                                                             |
|                         [ 根节点: R2, R3 ]                                  |
|                            /          \                                     |
|             [ 内部节点: e1, e2 ]   [ 内部节点: e3, e4 ]                     |
+-----------------------------------------------------------------------------+
```

#### 2. 查询算法：窗口相交判定（Intersection Search）

给定查询矩形 $Q$：

1. 从根节点开始，遍历当前节点的所有条目；
2. 若条目的 $\text{MBR}_i$ 与 $Q$ 相交（$\text{MBR}_i \cap Q \neq \emptyset$），则递归进入对应的子节点；
3. 到达叶节点后，比对实际对象的 MBR 与 $Q$，取出匹配对象的 RID 回表取元组。

::: pitfall 为什么 R 树的查询可能退化？
若数据插入顺序不当，内部节点的 MBR 之间会产生**巨大的重叠区域（Overlap）**。当查询矩形 $Q$ 落在重叠区域时，查询引擎无法像 B+ 树那样精确二分走单条路径，而必须**同时遍历多个子树分支**！在极端情况下，重叠严重会导致查询退化为全树扫描。
:::

### 5.4 经典论文深度精读：R*-Tree（Beckmann et al. 1990）的四大几何优化

针对 Guttman 原版 R 树重叠过大、空间死区（Dead Space）高、查询多分支发散的死穴，1990 年，Norbert Beckmann、Hans-Peter Kriegel、Ralf Schneider 与 Bernhard Seeger 发表了划时代论文：  

> **"The R*-tree: An Efficient and Robust Access Method for Points and Rectangles"** (ACM SIGMOD 1990)

#### 1. 核心理论突破：四大联合优化几何准则

Guttman 的原版 R 树在节点分裂与插入时，仅依赖单一启发式——**最小化 MBR 面积增加量（Area Enlargement）**。Beckmann 等人通过严格数学分析与实验证实，仅优化面积是极其片面的。R*-Tree 提出了四大联合优化目标：

1. **最小化重叠面积（Minimize Overlap Area）**：不同子树 MBR 之间的交集必须最小。重叠越小，查询矩形同时命中多个分支的概率越低，剪枝效率越高；
2. **最小化覆盖总面积（Minimize Area Coverage）**：各个节点的 MBR 越紧致，所包涵的“空白死区”越少，误命中的概率越小；
3. **最小化周长外框（Minimize Margins / Perimeters）**：在面积固定的情况下，**正方形（各维度跨度均匀）的周长远小于狭长的扁平矩形**。正方形在应对各种长宽比的查询窗口时具有更均衡稳定的相交概率；
4. **最大化存储利用率（Maximize Storage Utilization）**：减少空闲槽位，降低树高，削减总磁盘页 I/O 次数。

```text
+--------------------------------------------------------------+
|            R 树（仅面积优化） vs R*-树（综合多维优化）       |
|                                                              |
|   [ Guttman R-Tree: 产生狭长且重叠的 MBR ]                  |
|   +-------------------------+                                |
|   | MBR A                   |                                |
|   |         +---------------+--------------------+           |
|   |         | 重叠区 (Overlap): 触发双倍 I/O 搜索!|           |
|   +---------+---------------+                    |           |
|             | MBR B                              |           |
|             +------------------------------------+           |
|                                                              |
|   [ R*-Tree: 追求正方紧凑、零重叠或极低重叠 ]                |
|   +---------------+      +---------------+                   |
|   | MBR A (正方)  |      | MBR B (正方)  |  (零交集!         |
|   | (低周长/紧致) |      | (低周长/紧致) |   查询精准剪枝!)  |
|   +---------------+      +---------------+                   |
+--------------------------------------------------------------+
```

---

#### 2. R*-Tree 核心算法推演一：优化子树选择（ChooseSubtree）

当插入一个新条目 $E$ 时，R*-Tree 根据节点所处层级采取不同的贪心策略：

- **若是内部节点的子节点（指向包含子树的节点）**：
  选择使得条目 $E$ 加入后**面积增量（Area Enlargement）最小**的子节点；若出现并列，选择原本**面积最小**的子节点（保持紧致）。
- **若是叶节点的父节点（子节点直接存储数据）**：
  直接按**重叠增量（Overlap Enlargement）最小**选择！
  $$\Delta \text{Overlap}(i) = \sum_{j \neq i} \text{Area}((\text{MBR}_i \cup E) \cap \text{MBR}_j) - \sum_{j \neq i} \text{Area}(\text{MBR}_i \cap \text{MBR}_j)$$
  计算条目 $E$ 放入各个候选节点后，导致该节点与其他兄弟节点的 MBR 重叠面积增加了多少。选择 $\Delta \text{Overlap}$ 最小的节点。这一策略从根本上遏制了叶子节点之间的交叠发散！

---

#### 3. R*-Tree 核心算法推演二：强行重新插入（Forced Reinsert）

传统平衡树（如 B+ 树和 R 树）在节点条目数达到 $M+1$ 溢出时，唯一的应对手段是**立即分裂（Split）**。  
但 Beckmann 等人指出：**早先插入的条目受限于当时局部的数据视野，很可能被放置在了一个次优的子树中**。如果盲目分裂，这种历史偏差会被永久凝固在树结构中。

R*-Tree 提出了革命性的**强行重新插入（Forced Reinsert）**机制：

```text
+--------------------------------------------------------------+
|                    强行重新插入 (Forced Reinsert) 流程       |
|                                                              |
|   1. 节点容量溢出 (达到 M + 1 个条目)                        |
|        |                                                     |
|   2. 计算每个条目中心与当前节点 MBR 中心之间的欧氏距离       |
|        |                                                     |
|   3. 降序排序，选出距离中心最远的 p 个条目 (通常 p = 30% * M)|
|        |                                                     |
|   4. 将这 p 个离群条目从当前节点物理移除，更新剩余条目 MBR   |
|        |                                                     |
|   5. 将被移除的 p 个条目重新调用 Insert 从树根重新路由插入!  |
+--------------------------------------------------------------+
```

::: theorem 强行重插的死循环规避定理
在单次用户插入操作所触发的向上遍历路径中，**每个树层级至多允许触发一次 Forced Reinsert**！系统使用一个位图标记数组 `overflow_level` 记录已重插过的层级。若某一层级在重新插入后再次发生溢出，则禁止二次重插，直接强制触发常规 Split 节点分裂。该机制严格保证算法在有限步骤内必定终止，绝不发生递归死循环。
:::

::: insight 为什么重新插入能带来巨大的性能跃迁？
强行重插不仅缓解了分裂压力，而且相当于一次**低成本的动态局部碎片整理（Dynamic Re-clustering）**！那些最靠近边缘的条目被移走后，原节点变得更加紧凑；而离群条目重新从根向下遍历，往往会被路由到后续新建立的、更匹配它们几何方位的兄弟子树中。实验表明，仅此一项机制就让树的整体空间利用率提升了 15%~20%，查询 I/O 下降了近 30%。
:::

---

#### 4. R*-Tree 核心算法推演三：基于轴向排序的最优分裂（Split）

当某层级已经执行过重插且再次溢出时，R*-Tree 执行精心设计的多维分裂算法：

假设每个节点容量上限为 $M$，下限为 $m = 0.4 \times M$。对于一个有 $M+1$ 个条目的溢出节点：

1. **第一阶段：选择分裂轴（Choose Split Axis）**
   - 对每一个坐标轴（X 轴、Y 轴）：
     - 分别按条目的下界坐标和上界坐标对所有条目进行升序排序；
     - 遍历所有可能的分组切分点 $k$（其中 $m \le k \le M - m + 1$，共 $M - 2m + 2$ 种分法）；
     - 计算每种切分方案下，左组 MBR 与右组 MBR 的**外边框周长之和（Margin Sum）**；
     - 将当前轴所有可能切分方案的周长累加，得到当前轴的总评价值。
   - **选择所有轴中总周长和最小的轴作为最终的分裂轴！**（因为周长最小化直接促成正方形几何外框）。
2. **第二阶段：选择最佳切分点（Choose Split Index）**
   - 在选定的最佳分裂轴上：
     - 评估所有合法的切分方案；
     - **优先选择两组 MBR 重叠面积（Overlap）最小的切分点**；
     - 若重叠面积并列相同，则选择**两组 MBR 面积总和（Area Sum）最小**的切分点。

### 5.5 通用搜索树抽象：GiST（Generalized Search Tree，Hellerstein et al. 1995）

在 1990 年代中期，数据库研究界陷入了“树形爆炸”的困境：针对标量有 B+ 树，针对空间有 R 树、R*-树、QuadTree，针对多维向量有 TV-Tree、X-Tree……每一个新数据类型都需要内核工程师花费数年时间从零编写一棵树，并为其重新设计并发加锁（Concurrent Latching）与 ARIES 崩溃恢复（WAL Logging）。

1995 年，Joseph M. Hellerstein、Jeffrey F. Naughton 与 Avi Pfeffer 在 VLDB 上发表了划时代论文 *“Generalized Search Trees for Database Systems” (GiST)*，从根本上终结了这一碎片化困局。

```text
+-----------------------------------------------------------------------------+
|                             GiST 统一可扩展内核架构                         |
|                                                                             |
|   +-----------------------------------------------------------------------+ |
|   |                       DBMS 内核通用引擎 (一次编写，全局复用)           | |
|   |   - 统一多路平衡树拓扑管理与外存分页                                  | |
|   |   - 高性能并发读写加锁协议 (GiST Latching Protocol)                    | |
|   |   - ARIES 崩溃恢复与预写日志 (WAL Logging)                             | |
|   +-----------------------------------------------------------------------+ |
|                                      |                                      |
|            只要注册 4 个核心键方法 (Key Methods)，即刻获得全新索引树!       |
|                                      v                                      |
|   +-------------------+  +--------------------+  +------------------------+ |
|   | 1. Consistent()   |  | 2. Union()         |  | 3. Penalty()           | |
|   | 判断条目是否命中  |  | 合并谓词产生超集   |  | 计算条目插入的增量代价 | |
|   | (相交/包含判定)   |  | (如计算外接 MBR)   |  | (如面积/重叠增量)      | |
|   +-------------------+  +--------------------+  +------------------------+ |
|                                      |                                      |
|   +----------------------------------+------------------------------------+ |
|   | 4. Compress() / Decompress() : 自定义键的物理压缩与反序列化表示       | |
|   +-----------------------------------------------------------------------+ |
+-----------------------------------------------------------------------------+
```

GiST 将平衡搜索树的通用系统逻辑与具体的键谓词逻辑彻底解耦。PostgreSQL 深度集成了 GiST 机制，使其成为世界上对空间几何、IP 地址段、范围类型（Range Types）支持最强大的关系数据库（支撑了现代开源地理信息事实标准——**PostGIS**）。

### 核心研讨思考题

#### 思考题 1：为什么空间多维检索不能简单依赖 B+ 树结合空间填充曲线（如 Z-Order 曲线）？
空间填充曲线通过位交叉将多维坐标映射为一维整数，能够复用现成的 B+ 树。但其核心缺陷在于：二维空间中连续的一个查询矩形，在映射为一维 Z 曲线后会被严重撕裂为大量碎片化的一维不连续区间（Z 曲线的突变跳跃）。范围查询必须向 B+ 树发起数倍乃至数十倍的一维子区间搜索；此外对带面积的多边形几何体支持极度生硬。而 R*-Tree 直接以 MBR 进行物理聚类，范围连续性极佳。

#### 思考题 2：在高维向量检索（如 768 维）中，为什么 R*-Tree 会退化为全表扫描？
根据高维几何测度集中现象，当维度大幅增加时，单位超立方体中几乎所有体积都分布在离中心较远的边界薄壳上。给定一个覆盖全局极小体积比例的超球体查询，其在各个坐标轴上的投影边长都接近于 1。这意味着树中几乎每一个内部节点的 MBR 都与查询窗口发生空间相交，树状剪枝完全失效，算法不得不遍历每一个叶子分支，其开销反而远高于连续内存顺序扫描。因此现代系统必须采用放弃 100% 精确性的近似最近邻（ANN）算法。
