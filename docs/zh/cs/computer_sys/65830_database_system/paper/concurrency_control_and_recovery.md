# Concurrency Control and Recovery：事务并发控制与故障恢复理论基石

> **论文作者**：Michael J. Franklin  
> **发表出处**：*The Computer Science and Engineering Handbook*, CRC Press, 1997  
> **配套讲次**：[Lec 11 事务处理与两阶段锁](../lec11.md) · [Lec 13 故障恢复原理与日志体系](../lec13.md)

## TL;DR

- 体系化梳理了事务 ACID 属性的形式化理论边界，明确了并发控制与故障恢复在数据库内核中的核心职责分工。
- 形式化推导了**冲突可串行化（Conflict Serializability）**判别法，证明了优先图（Precedence Graph）无环性与串行执行的拓扑等价关系。
- 详解了**严格两阶段锁（Strict 2PL）**协议及其级联回滚免疫（Cascadeless Abort）特性，推导了多粒度意向锁（IS/IX/SIX）的层次兼容矩阵。
- 阐明了缓冲池置换四象限策略（Steal/No-Steal vs Force/No-Force）对恢复子系统的根本约束，奠定了预写日志（WAL）的理论基石。

## 1. 论文背景与 ACID 契约的物理分解

在多用户并发与硬件脆弱性的物理现实中，数据库管理系统必须为上层应用维系看似自相矛盾的假象：**每个事务都以为自己独占整台计算机，且外存介质永远不会发生掉电或崩溃。**

Michael J. Franklin 在这篇极具学术与工程影响力的综述中，将事务的四要素（ACID）拆解为两组精密的工程子系统协同保障：

```text
+-----------------------------------------------------------------------------------------+
|                               ACID 契约与底层内核子系统映射                             |
|                                                                                         |
|   ACID 核心特性           业务语义定义                     负责保障的底层内核子系统     |
|  +----------------------+--------------------------------+----------------------------+ |
|  | A - 原子性 (Atomicity)| 事务内所有操作要么全做要么全不做| 恢复子系统 (Undo Logging)   |
|  | C - 一致性 (Consistency)| 满足所有预设完整性约束与业务逻辑| 应用逻辑 + 约束检查机制    |
|  | I - 隔离性 (Isolation)| 并发执行等价于某种串行执行调度  | 并发控制 (2PL / OCC / MVCC)|
|  | D - 持久性 (Durability)| 事务提交后修改绝对不会意外丢失  | 恢复子系统 (Redo Logging)   |
|  +----------------------+--------------------------------+----------------------------+ |
+-----------------------------------------------------------------------------------------+
```

## 2. 冲突可串行化与严格两阶段锁（Strict 2PL）

### 2.1 冲突等价与优先图判定
在并发调度中，若两个来自不同事务的连续操作满足：**作用于同一个物理数据项，且至少有一个是写操作（$W$）**，则这两个操作被称为**冲突操作（Conflicting Operations）**。冲突操作的相对顺序不可调换，否则会改变最终数据库的物理状态。

```mermaid
flowchart LR
    Schedule["并发操作调度序列 (Schedule)"] --> DepGraph["构建优先图 (Precedence Graph / Serialization Graph)"]
    DepGraph --> Judge{"图是否存在有向环？"}
    Judge -- "无环 (Acyclic)" --> Serializable["符合冲突可串行化！<br/>等价于拓扑排序所得的串行调度"]
    Judge -- "存在环 (Cycle)" --> NonSer["不可串行化！<br/>存在脏读、不可重复读或丢失更新异常"]
```

### 2.2 严格两阶段锁（Strict Two-Phase Locking）
基础 2PL 协议仅要求：**事务一旦开始释放任何锁，就绝不能再申请任何新锁**（分为加锁增长期 Growing Phase 与解锁缩减期 Shrinking Phase）。

基础 2PL 虽然保证了可串行化，但存在致命隐患——**级联回滚（Cascading Aborts）**：若事务 $T_1$ 在缩减期释放了某个数据项的独占锁并随后中止（Abort），而在其释放锁后读取了该项的事务 $T_2$ 必须连带被迫回滚，引发系统级雪崩！

**Strict 2PL 的绝对约束**：
- 事务在执行过程中只申请锁；
- **所有获得的排他锁（X Locks）甚至共享锁（S Locks），必须死死保持直到事务完全提交（`COMMIT`）或回滚（`ABORT`）的那一瞬间，才能统一释放！**
- **工程价值**：彻底杜绝脏读与级联回滚，回滚某个事务只需读取其专有 Undo 日志就地恢复，完全不影响其他并发事务。

### 2.3 多粒度意向锁（Multiple Granularity Locking）

为了同时高效支持“对单行数据的频繁点查/点更”与“对整个大表的批量统计”，系统必须支持树状多粒度封锁（数据库 $\to$ 数据表 $\to$ 页面 $\to$ 元组行）：

```text
+-----------------------------------------------------------------------------------------+
|                              多粒度锁与意向锁兼容性矩阵                                 |
|                                                                                         |
|   请求锁模式 \ 现持有模式    IS (意向共享)   IX (意向排他)    S (共享)       X (排他)   |
|  +------------------------+---------------+---------------+---------------+-----------+ |
|  | IS (Intent Shared)     |      兼容     |      兼容     |      兼容     |    冲突   |
|  | IX (Intent Exclusive)  |      兼容     |      兼容     |      冲突     |    冲突   |
|  | S  (Shared)            |      兼容     |      冲突     |      兼容     |    冲突   |
|  | SIX (Shared + IX)      |      兼容     |      冲突     |      冲突     |    冲突   |
|  | X  (Exclusive)         |      冲突     |      冲突     |      冲突     |    冲突   |
|  +------------------------+---------------+---------------+---------------+-----------+ |
+-----------------------------------------------------------------------------------------+
```

- **协议规则**：要在底层节点（如行）申请 $S$ 锁，必须先在所有祖先节点（表、页）成功加上 $IS$ 锁；要在底层申请 $X$ 锁，必须先在所有祖先加上 $IX$ 锁。
- **价值**：当某个事务企图修改整张表并申请表级 $X$ 锁时，只需检查表上的意向锁状态，而**无需深层遍历表中数百万行去逐一检查行锁**。

## 3. 缓冲池置换四象限与预写日志（WAL）

数据库对内存页与外存数据页的交互管理，在理论上可以划分为四大正交策略：

```text
+-----------------------------------------------------------------------------------------+
|                               缓冲池置换策略与恢复负担四象限                            |
|                                                                                         |
|                      【NO-STEAL】 (未提交脏页绝不允许刷盘)   【STEAL】 (允许淘汰未提交脏页)  |
|  +-----------------+--------------------------------------+---------------------------+ |
|  | 【FORCE】       | 不需要 Undo, 不需要 Redo             | 需要 Undo, 不需要 Redo    |
|  | (提交时强制刷盘)| 性能极差（单次提交产生大量随机写）   | 极少有工业系统采用        |
|  +-----------------+--------------------------------------+---------------------------+ |
|  | 【NO-FORCE】    | 不需要 Undo, 需要 Redo               | 【最强性能工业标准：ARIES】|
|  | (提交时不强刷盘)| 内存容量极其受限                     | 需要 Undo (处理未完成事务) |
|  |                 |                                      | 需要 Redo (重放已提交数据)|
|  +-----------------+--------------------------------------+---------------------------+ |
+-----------------------------------------------------------------------------------------+
```

1. **STEAL 策略**：当缓冲池内存不足时，允许系统将**包含未提交事务修改的脏页**写出到磁盘腾挪空间。这意味着外存磁盘可能出现脏数据，崩溃恢复时必须具备 **Undo（回滚撤销）**能力。
2. **NO-FORCE 策略**：当事务声明 `COMMIT` 时，系统**绝不强制**将该事务修改的所有物理数据页同步刷盘，只要日志持久化即可返回成功。这意味着已提交的数据可能仍在内存中并未落盘，断电崩溃后必须具备 **Redo（重做重放）**能力。

**预写日志（Write-Ahead Logging, WAL）核心铁律**：
- 在任何内存脏页被刷出到外存磁盘之前，该页修改所对应的所有日志记录必须首先落盘（保证 STEAL 安全）；
- 在事务向客户端宣告提交成功前，该事务所有的提交日志必须刷入磁盘（保证 NO-FORCE 持久性）。

## 4. 架构师深度洞察

::: insight 锁开销、死锁预防与无锁并发的抉择
Franklin 详尽阐述的 Strict 2PL 架构是教科书中最严密的并发安全范式，但它在现代高并发多核体系下存在天然瓶颈：
1. **死锁风险无法规避**：资源交叉竞争必然导致环路等待。在高负载下，维护等待图（Wait-For Graph）并在数百个并发事务中进行拓扑环路检测，CPU 消耗陡增；
2. **读写互相阻塞**：只读的长事务（如报表统计）会阻塞所有短更新事务，导致 OLTP 系统吞吐瞬间腰斩。

这催生了后来两大重要技术分支：
- **快照隔离（Snapshot Isolation / MVCC）**：通过维护元组的多版本历史，让“读写不冲突，读永远不加锁”，仅在写-写竞争时利用锁或 OCC 仲裁；
- **确定性事务调度（Deterministic DB / H-Store / Calvin）**：在事务执行前预先按全局排序规划加锁顺序，从根本上在数学上杜绝死锁。

理解 Franklin 的传统 2PL 边界，是理解所有新一代无锁与多版本并发机制的必经之路。
:::
