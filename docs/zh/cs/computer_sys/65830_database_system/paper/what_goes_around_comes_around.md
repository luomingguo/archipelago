# What Goes Around Comes Around：数据模型半个世纪的技术轮回

> **论文作者**：Michael Stonebraker, Joseph M. Hellerstein  
> **发表出处**：*Readings in Database Systems* (Red Book 4th/5th Edition), 2005  
> **配套讲次**：[Lec 2 现代 SQL 与高级查询](../lec2.md) · [Lec 1 关系模型与 SQL 基础](../lec1.md)

## TL;DR

- 梳理了数据模型从 1960 年代到 2000 年代长达 35 年的演进史：层次模型（IMS）、网状模型（CODASYL）、关系模型、实体关系（ER）、面向对象（OODBMS）与 XML。
- 确立了数据系统设计最核心的分水岭——**物理数据独立性（Physical Data Independence）**与**声明式查询（Declarative Query）**。
- 历史证明：任何迫使程序员用代码硬编码物理存储指针与访问路径的数据模型，都必然因维护成本爆炸而走向消亡。
- 现代 NoSQL 与半结构化文档存储并未颠覆这一规律，而是在特定场景下向灵活性妥协，最终仍需向类 SQL 声明式接口收敛。

---

## 1. 论文研究背景与核心主张

在计算机系统演进中，每隔十年就会涌现出一套“声称能够彻底淘汰关系数据库”的新数据模型或范式。然而，历史的车轮不断转动，新方案往往重复犯下几十年前早被验证过的错误。

图灵奖得主 Michael Stonebraker 与 Joseph Hellerstein 在这篇经典文献中系统回顾了 1970 至 2005 年间数据库数据模型的兴衰史，提出了著名论断：**“技术潮流总是循环往复（What goes around comes around）”**。无论是面向对象数据库、XML 还是后来的键值/文档型存储，一旦应用规模扩大、数据关系变复杂，系统最终都必须重新发明关系模型的两大基石：
1. **物理与逻辑数据独立性**：应用代码不得依赖磁盘物理布局或存储指针；
2. **高级声明式查询语言与基于代数重写的优化器**：由系统而非程序员决定最高效的数据访问路径。

## 2. 数据模型的历史演进与致命缺陷

### 2.1 层次模型（Hierarchical Model: IBM IMS）
- **核心机制**：数据被组织为严格的“段树（Segment Tree）”。每个子段只能拥有一个父段，记录之间使用物理磁盘地址或内存指针直接相连。
- **致命缺陷**：
  1. **无法直接表达多对多（$M:N$）关系**：例如“学生”与“课程”、“动物”与“饲养员”。若想表达多对多，必须在多个父节点下重复拷贝相同的子记录，导致严重的数据冗余与更新异常；
  2. **根路径依赖**：对子记录的任何查询都必须从树根依次向下穿透，无法从叶子节点独立切入检索。

### 2.2 网状模型（Network Model: CODASYL DBTG）
- **核心机制**：引入“系（Set）”的概念，记录可以作为多个系的主记录（Owner）或从属记录（Member），从而支持任意有向图结构。
- **致命缺陷（导航式编程）**：
  - CODASYL 是一种完全**过程式（Imperative）**的访问模型。程序员必须编写诸如 `FIND FIRST <Record> WITHIN <Set>`、`FIND NEXT` 等游标跳转指令，手动在磁盘物理链表中“航行（Navigate）”。
  - **丧失物理独立性**：一旦数据库管理员为了加速某一类查询而添加或删除了某个物理链表指针，全公司数万行既有业务代码就会发生编译错误或逻辑静默崩溃。

### 2.3 关系模型的革命（Ted Codd 1970）
Edgar F. Codd 提出了划时代的三大原则：
1. **数据表示极致纯粹**：所有数据均表示为数学集合论中的二维关系（表），每条记录为无序元组，属性值为原子标量；
2. **彻底切断物理指针**：实体之间的关联只能通过数据值（Value-based，如外键键值匹配）在运行时关联，严禁在记录中暴露存储指针；
3. **声明式查询与一阶谓词逻辑**：用户使用非过程化语言（如 SQL / 关系演算）描述“想要什么数据”，底层内核查询优化器利用关系代数等价变换，在千百种物理执行路径中自主选择代价最小的方案。

## 3. 为什么后来的“挑战者”大多功败垂成？

### 3.1 面向对象数据库（OODBMS，1980年代末 - 1990年代）
- **动机**：为了解决面向对象编程语言（C++ / Smalltalk）与关系表之间的“阻抗失配（Impedance Mismatch）”，试图直接将内存对象图持久化到磁盘。
- **失败根因**：
  - 倒退回了指针遍历（Object Identity & Pointer Dereferencing）。OODBMS 本质上是用 C++ 重新包装了 CODASYL 网状模型！
  - 缺乏标准化的声明式查询语言。若要查询“薪资大于 10000 的员工”，程序员必须写 `for` 循环遍历整个对象集合，丧失了优化器做全表过滤与索引加速的可能。

### 3.2 XML 与半结构化模型（2000 年代初）
- **动机**：支持 Schema 灵活演变与嵌套半结构化文本交换。
- **失败根因**：
  - XML 本质上是层次模型的重演。XQuery 和 XPath 的深层路径遍历让查询优化器的代价评估变得极度困难，存储膨胀率高，性能在复杂聚合场景下遭遇断崖。

## 4. 官方课前思考题深度解答

### Q1: 哪些类型的程序容易用 SQL 表达？哪些类型难以表达？你觉得声明式还是过程式更简单？
- **易于表达**：集合过滤、投影、多表等值连接（Hash/Merge Join）、分组聚合、窗口统计与集合代数操作。这类数据处理逻辑只需一条简洁的 SQL 语句即可描述完备。
- **难以表达**：图遍历（深度优先/广度优先搜索）、递归路径规划、状态机流转、复杂矩阵线性代数运算。虽然现代 SQL 支持递归 CTE，但在表达复杂迭代循环与动态规划算法时依然笨重。
- **认知权衡**：对于初学者，过程式（按部就班的循环与指针跳转）符合人类直觉思维；但当数据量达到亿级、并发量达到数千时，声明式编程将执行策略完全解耦，交由内核利用 SIMD、并行线程、多路归并自动优化，生产力与运行效率远超手工过程式代码。

### Q2: 什么是数据独立性（Data Independence）？为什么它至关重要？
- **逻辑数据独立性**：底层物理表结构发生扩展（如增加属性列、通过视图 View 拆分表）时，上层应用程序的逻辑代码无需修改；
- **物理数据独立性**：数据在磁盘上的存储格式（堆文件、聚簇索引、列式压缩、B+ 树、哈希桶）发生任何调整，上层 SQL 查询语句一字不改，结果语义完全不变。
- **商业与工程价值**：将企业软件的生命周期从“与底层硬件和存储格式死死捆绑”中彻底解耦，使得硬件升级、索引调优、存储引擎重构不会引发毁灭性的应用重写。

### Q3: 关系模型的核心思想是什么？相比前代模型有哪些本质飞跃？在哪些方面存在局限？
- **核心思想**：基于数学集合论，以值（Value）而非指针（Pointer）关联数据，采用关系代数与一阶谓词逻辑作为严密数学地基。
- **本质飞跃**：消除了网状/层次模型中的死板指针链接与数据冗余，将优化权力上收至内核优化器，建立了标准化声明式查询规范。
- **内在局限**：关系第一范式（1NF）要求属性原子性，对嵌套层次对象（如 JSON 数组、图拓扑网络、高维向量嵌入）的表达不够自然，容易在复杂领域驱动设计中引发“对象-关系阻抗失配”。

### Q4: 层次模型（IMS）与关系模型（Codd）最关键的技术区别是什么？
- **寻址方式**：层次模型是**指针寻址与路径寻址**（必须沿着预定树状分支游标下潜）；关系模型是**内容寻址与值寻址**（基于列值的布尔谓词匹配）；
- **拓扑约束**：层次模型强制一父多子（树拓扑），多对多关系必须依赖数据复制；关系模型无拓扑偏见，任何两张表只要存在共同语义列即可在运行时动态自然连接。

## 5. 架构师深度洞察

::: insight 历史的技术回声与现代 NoSQL 的演进收敛
Stonebraker 在 2005 年写下这篇论文时，正值 XML 喧嚣渐退；然而几年后，MongoDB、Cassandra、Dynamo 等 NoSQL 浪潮席卷重来，许多人一度再次宣称“SQL 已死”。

但观察这十余年的演化轨迹：
1. MongoDB 最终被迫补齐了 ACID 多文档事务与基于 Pipeline 的聚合操作框架；
2. Cassandra 引入了 CQL；Presto / Trino / Spark SQL 成为连接所有大数据湖仓的事实标准；
3. 云原生时代的最终形态不是抛弃关系模型，而是**多模态融合（Multi-Model DBMS）**——关系型内核内置 JSONB 字段与向量（pgvector）类型，外层仍然使用成熟的声明式 SQL 配合优化器。

技术螺旋上升，物理独立性与声明式查询永远是数据库系统不可动摇的物理定律。
:::
