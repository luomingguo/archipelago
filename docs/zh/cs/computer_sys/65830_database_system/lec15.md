# Lec 15 并行与分布式数据库架构

## TL;DR

- 现代大规模数据库系统从单机纵向扩展走向无共享架构（Shared-Nothing）与云原生存算分离架构。
- 数据分区策略（轮转分区、范围分区、哈希分区）权衡了负载均衡度、写入倾斜风险与谓词下推剪枝能力。
- 查询并行化涵盖算子间流水线并行与算子内数据分区并行，Volcano Exchange 算子实现了网络通信的无缝封装。
- 分布式连接策略（同构共区连接、小表广播连接、全网重分区连接、半连接优化）决定了集群跨机网络 I/O 开销与吞吐上限。

## 架构演进与核心洞察

::: insight Exchange 算子的优雅解耦
Volcano 论文中由 Goetz Graefe 提出的 Exchange 算子是并行查询处理的基石。在没有 Exchange 之前，算子必须关心自己是在本地线程还是跨网络节点运行。Exchange 算子伪装成普通迭代器，内部封装了网络缓冲区、线程池与哈希重分布逻辑。上下游算子无需更改一行代码，即可无缝从单机执行平滑升级为数百台机器协同的分布式并行查询。
:::

## 1. 并行处理与分布式扩展的核心评估指标

并行数据库与分布式数据库的设计目标存在本质区分：
- **并行数据库（Parallel DBMS）**：利用多处理器、多核心或多节点硬件资源，协同加速单个复杂 SQL 查询的执行速度，核心关注**响应延迟（Latency）**；
- **分布式数据库（Distributed DBMS）**：节点在地理或机架上物理隔离并具有独立故障域，核心关注**高可用性（Availability）、容灾容错与海量并发事务吞吐量（Throughput）**。

### 1.1 加速比（Speedup）与扩展比（Scaleup）

衡量分布式并行数据库性能扩展能力的两大核心物理指标：

1. **加速比（Speedup）**：固定任务规模（工作量不变），增加硬件资源（节点数从 $1$ 增加到 $N$）带来的执行时间缩短倍数：
   $$\text{Speedup} = \frac{\text{单机执行耗时 } T_1}{\text{N 机并行执行耗时 } T_N}$$
   - **线性加速比（Linear Speedup）**：$\text{Speedup} = N$（理想状态，如 10 台机器获得 10 倍速度）；
   - **超线性加速（Super-linear Speedup）**：由于节点增加使得工作集完整装入各节点的 CPU L3 缓存，偶发产生 $\text{Speedup} > N$。

2. **扩展比（Scaleup）**：任务规模与硬件资源按同等比例同步扩大（$N$ 倍数据由 $N$ 台机器处理）：
   $$\text{Scaleup} = \frac{\text{单机处理基准数据量耗时 } T_1}{\text{N 机处理 N 倍数据量耗时 } T_N}$$
   - **线性扩展比（Linear Scaleup）**：$\text{Scaleup} = 1$（机器翻倍的同时数据翻倍，耗时依然保持恒定）。

![并行数据库加速比指标曲线：线性加速与非线性加速比在不同并行度下的性能表现对比](https://tc-1258979383.cos.ap-guangzhou.myqcloud.com/660a5d7b9ae57.png)

### 1.2 阻碍线性扩展的物理天花板
在实际工程部署中，系统很难长期维持纯线性加速，主要受制于三大开销：
1. **启动开销（Startup Cost）**：主节点分发查询计划、初始化数百个工作进程与分配远程资源的固定时延；
2. **干扰与通信争用（Interference & Contention）**：节点并发请求网络交换机带宽、争用分布式元数据目录以及锁管理器时的排队延迟；
3. **倾斜效应（Skew / Amdahl 瓶颈）**：由于数据分布不均或计算热点，最慢的长尾节点（Straggler）决定了整个分布式算子的总耗时。

## 2. 分布式系统四大硬件拓扑架构

分布式与并行数据库系统的核心分水岭在于 CPU、内存与磁盘等硬件资源在网络中的共享边界。

```text
1. 共享一切 (Shared-Everything)       2. 共享磁盘 (Shared-Disk)             3. 无共享架构 (Shared-Nothing)
  [CPU1] [CPU2] [CPU3]                 [Node 1]   [Node 2]   [Node 3]       [Node 1]     [Node 2]     [Node 3]
    \      |      /                     (CPU+RAM)  (CPU+RAM)  (CPU+RAM)     [CPU+RAM]    [CPU+RAM]    [CPU+RAM]
   +---------------+                        \          |          /             |            |            |
   | 全局共享内存  |                         \         |         /          [本地磁盘]   [本地磁盘]   [本地磁盘]
   +---------------+                     +-------------------------+            \            |            /
           |                             | 高速网络 / 存储区域网络 |             +-----------+-----------+
   +---------------+                     +-------------------------+             |   标准以太网络 (Network)   |
   |  全局共享磁盘 |                                  |                          +-----------------------+
   +---------------+                         +-----------------+
                                             |  全局共享外存池 |
                                             +-----------------+
```

### 2.1 共享一切架构（Shared-Everything / Shared-Memory）
- **拓扑特征**：所有 CPU 核心通过高速系统总线统一访问全局内存地址空间与本地外存磁盘。
- **优点**：编程模型与单机完全一致，数据共享零网络开销，各线程间通信延迟在纳秒级。
- **缺陷**：受限于单机主板物理插槽与非一致内存访问（NUMA）总线仲裁限制，CPU 超过数十核后总线争用急剧恶化，无法横向扩展。

![共享一切与共享内存架构示意图：多核 CPU 共享物理内存与统一总线互联](https://tc-1258979383.cos.ap-guangzhou.myqcloud.com/660a6222ed112.png)

### 2.2 共享磁盘架构（Shared-Disk）
- **拓扑特征**：每个节点拥有独立的 CPU 与物理内存，运行独立的数据库实例；所有节点通过高速存储区域网络（SAN / NAS 或光纤通道）挂载同一套底层共享存储池（典型代表如 Oracle RAC）。
- **优点**：计算节点无状态化，单个计算节点宕机后，其他节点可直接接管外存数据，容灾切换极快；
- **缺陷**：
  1. 共享外存网络带宽成为全集群并发 I/O 的单点瓶颈；
  2. 多节点在私有缓冲池中修改同一物理页时，必须运行极其昂贵复杂的**分布式锁管理器（Distributed Lock Manager, DLM）**以防缓存不一致，网络锁心跳开销巨大。

![共享磁盘架构示意图：独立计算节点通过高速网络互联访问统一逻辑外存存储池](https://tc-1258979383.cos.ap-guangzhou.myqcloud.com/660a6231ed2ca.png)

### 2.3 无共享架构（Shared-Nothing / 图灵奖设计）
- **提出背景**：Michael Stonebraker 于 1986 年发表奠基性论文 *`The Case for Shared Nothing`*，彻底奠定了现代大规模并行分析数据库（如 Teradata、Greenplum、ClickHouse、TiDB）的基石。
- **拓扑特征**：每个节点独占本地 CPU、本地内存与本地磁盘，节点之间**绝不共享任何物理硬件**，仅通过普通 TCP/IP 局域网传递数据消息。
- **核心优势**：硬件无单点瓶颈，具备近乎无限的线性横向扩展能力（Scale-Out）。

![无共享架构示意图：独立计算节点独占本地 CPU、内存与磁盘并通过网络协作](https://tc-1258979383.cos.ap-guangzhou.myqcloud.com/660a66cd1a84b.png)

### 2.4 云原生存算分离架构（Cloud-Native Disaggregated Storage）
- **演进趋势**：现代云原生数据库（如 Snowflake、Amazon Redshift、Google BigQuery）结合了 Shared-Disk 与 Shared-Nothing 的双重优势：
  - **计算层（Compute Layer）**：由数百台无共享虚拟机组成弹性算力池，算子间通过局域网高速 Shuffle 交换中间数据；
  - **存储层（Storage Layer）**：数据持久化下沉至分布式云对象存储（如 AWS S3、腾讯云 COS），实现存储容量无限扩展与按需秒级弹性扩缩容。

![存算分离架构演进示意图：无共享计算集群挂载分布式对象存储与中心化元数据服务](https://tc-1258979383.cos.ap-guangzhou.myqcloud.com/660b840b21d99.png)

## 3. 并行查询处理技术与火山 Exchange 算子

并行查询处理在系统执行层划分为多个正交维度：
- **查询间并行（Inter-Query Parallelism）**：多个独立用户的查询在集群的不同节点或核心上并发执行，由多版本并发控制或锁管理器协调隔离性；
- **查询内并行（Intra-Query Parallelism）**：单个耗时较长的重型分析 SQL 被切分为多个子任务，在多台节点上并发加速。

### 3.1 算子间流水线并行（Inter-Operator / Pipeline Parallelism）
将查询计划树中的上下游算子分配给不同的计算线程或节点，上游算子源源不断生产元组，下游算子以流水线方式重叠执行。
- **局限性**：受制于阻塞算子（Pipeline Breakers，如排序 `Sort` 或哈希构建 `Hash Build`）的阻断，且流水线阶段受最慢木桶算子制约，并行度上限往往只有数个阶段，无法扩展到数百节点。

![算子间流水线并行执行示意图：流水线阶段重叠与数据流流式传递过程](https://tc-1258979383.cos.ap-guangzhou.myqcloud.com/660b8b2020798.png)

### 3.2 算子内数据分区并行（Intra-Operator Parallelism）
将单个逻辑算子（如扫描 `SeqScan`、过滤 `Filter` 或连接 `Join`）拆解为 $N$ 个对等的无状态并行实例（Worker Instances），每个实例负责处理输入数据集的一个独立分片。这是现代 MPP 系统的绝对核心主力。

![算子内分区并行执行架构：数据分片与独立算子实例的水平并发执行](https://tc-1258979383.cos.ap-guangzhou.myqcloud.com/66c3fccf6e60b.png)

### 3.3 划时代的火山 Exchange 算子架构

Goetz Graefe 于 1990 年提出的 **Exchange 算子**彻底解决了网络通信与单机迭代模型的融合难题：
- **上层接口**：暴露标准的 `open()`、`next()`、`close()` 火山模型拉取接口，消费者算子无法分辨数据究竟来自本地内存还是远端集群；
- **内部双端机制**：
  - **Producer 线程**：在发送端主动循环调用子算子的 `next()`，将生成的元组批量序列化进网络缓冲区；
  - **Consumer 线程**：在接收端异步从 TCP 套接字读取数据块，填充本地线程安全队列，供上层算子平滑消费。

```text
协调者节点 (Coordinator Node):
                [ Merge / Gather Exchange ]  <-- 汇聚所有远端流
                            ^
                            | (网络传输 TCP/IP)
     +----------------------+----------------------+
     |                                             |
工作节点 1 (Worker Node 1):                  工作节点 2 (Worker Node 2):
     [ Hash-Partitioned Exchange ]                [ Hash-Partitioned Exchange ]
                  |                                            |
            [ Filter (σ) ]                               [ Filter (σ) ]
                  |                                            |
         [ Local SeqScan(R1) ]                        [ Local SeqScan(R2) ]
```

#### Exchange 算子的三大经典变体
1. **Gather Exchange（汇聚）**：将多个分布式 Worker 的数据流汇聚合并为一个单点输出流，常用于最终结果输出或聚合后汇总；
2. **Repartition / Shuffle Exchange（哈希重洗）**：按照目标属性对元组计算哈希值，通过交叉网络将数据精准分发给对应的下游处理节点；
3. **Distribute / Split Exchange（分发）**：将单输入流按照轮转或广播规则拆分成多个输出分支。

## 4. 数据水平分片策略（Horizontal Partitioning）

在无共享架构中，表数据的物理分布方式直接决定了查询下推（Predicate Pushdown）能力与网络传输开销。

```text
+-----------------------+------------------------------------------+------------------------------------+
| 分片策略              | 映射规则                                 | 核心优缺点对比                     |
+-----------------------+------------------------------------------+------------------------------------+
| 1. 轮转 / 随机分区    | 元组第 i 条映射至节点 (i mod N)          | 优点: 负载绝对均匀，无数据倾斜     |
| (Round-Robin)         |                                          | 缺点: 无法进行谓词剪枝下推         |
+-----------------------+------------------------------------------+------------------------------------+
| 2. 范围分区           | 按照分片键连续区间划分:                  | 优点: 范围扫描直接剪枝，局部性好   |
| (Range Partitioning)  | [1, 100] -> N1, [101, 200] -> N2         | 缺点: 单调写入产生写热点，数据倾斜 |
+-----------------------+------------------------------------------+------------------------------------+
| 3. 哈希分区           | 按照分片键哈希散列:                      | 优点: 散列均匀，彻底消除写热点     |
| (Hash Partitioning)   | Node = hash(key) mod N                   | 缺点: 范围查询必须全节点广播打散   |
+-----------------------+------------------------------------------+------------------------------------+
```

### 4.1 轮转与随机分区（Round-Robin Partitioning）
- **机制**：元组依次循环插入各节点，每个节点分片大小严格相等。
- **代价**：数据库无法预知任何特定值落在哪个节点上。任何点查或范围查询都必须全量扫描所有节点（Scatter-Gather 广播开销）。

![轮转与随机数据分区示意图：元组均匀离散分布与全扫描负载均衡](https://tc-1258979383.cos.ap-guangzhou.myqcloud.com/66c407a5ce19d.png)

### 4.2 范围分区（Range Partitioning）
- **机制**：依据分片键的大小区间（如按创建时间或地理区域）划分物理节点。
- **收益**：执行带有范围谓词的查询（如 `WHERE date >= '2026-01-01'`）时，优化器可实现确定性的**分区剪枝（Partition Pruning）**，仅激活包含数据的目标节点。
- **隐患**：单调递增键（自增主键、实时时间戳）会导致最新插入流量全部集中冲击某一个单一节点，造成灾难性的**写入热点（Hotspotting）**与存储空间倾斜。

![范围数据分区示意图：按键值区间划分数据子集与点查谓词下推剪枝](https://tc-1258979383.cos.ap-guangzhou.myqcloud.com/66c407c17544f.png)

### 4.3 哈希分区（Hash Partitioning）
- **机制**：通过哈希函数对分片键求哈希值并模节点数 $N$。
- **收益**：自增数据被无序均匀打散至全集群，彻底消除写热点与空间倾斜；等值点查可直接路由到目标节点。
- **代价**：打破了数据的大小顺序，范围查询无法剪枝，必须向所有节点广播。

![哈希数据分区示意图：通过哈希函数将数据均匀映射至固定分区节点](https://tc-1258979383.cos.ap-guangzhou.myqcloud.com/66c409ea2954c.png)

## 5. 分布式连接算法深度矩阵（Distributed Joins）

在无共享集群中，连接两张大表 $R$ 与 $S$（条件为 $R.A = S.B$）的最高代价是**跨机房或机架的网络传输 I/O**。优化器根据表的数据量级与初始分片键，挑选最优物理连接路径：

### 5.1 场景一：同构共区连接（Colocated / Pre-Partitioned Join）
若两张表 $R$ 与 $S$ 初始时就已经按照各自的连接键（$A$ 与 $B$）采用了相同的哈希函数与相同的节点分片数进行分布，则相匹配的键值天然位于同一物理节点上。
- **网络开销**：**零网络数据传输（0 Network I/O）**！各节点只需在本地执行单机 Hash Join 或 Merge Join，性能最高。

![同构共区连接示意图：表 A 与表 B 按相同连接键预分区实现的零网络本地连接](https://tc-1258979383.cos.ap-guangzhou.myqcloud.com/66c41ab2a5fcf.png)

### 5.2 场景二：广播连接（Broadcast Join / Replicated Join）
适用于极度不对称的“大表连接小表”场景（例如数据仓库中数亿条记录的事实表 $Sales$ 连接数千条记录的维度表 $Store$）。
- **执行过程**：将小表 $S$ 的全量数据广播发送到集群中存放大表 $R$ 分片的每一个计算节点；
- **本地计算**：每个节点将小表 $S$ 载入本地内存构建哈希表，直接流式扫描本节点的大表 $R$ 分片完成探测；
- **网络开销**：设节点数为 $n$，网络总传输量为 $|S| \cdot (n - 1)$，远小于全网重分布大表的开销。

![广播复制连接示意图：小表全量复制广播至大表各分区节点执行本地连接](https://tc-1258979383.cos.ap-guangzhou.myqcloud.com/66c422afa3ddb.png)

### 5.3 场景三：全网重分区连接（Shuffle Join / Repartition Join）
适用于两张海量大表（$|R|$ 与 $|S|$ 均无法全量载入单机内存），且初始分片键与连接键均不吻合的场景。
- **执行过程**：两张表各自通过 Exchange 算子，按连接键重新计算哈希值，将元组通过网络交叉 Shuffle 发送给对应的目标节点；
- **网络传输量精确推导**：
  设表 $B$ 均匀分布在 $n$ 个节点上，每个节点原本持有 $\frac{|B|}{n}$ 个元组。
  重分区时，节点本地处理的元组只有 $\frac{1}{n}$ 命中自己，其余 $\frac{n-1}{n}$ 必须通过网络跨机发送。
  单个节点向外发送的数据量为：
  $$\text{TxPerNode} = \frac{|B|}{n} \cdot \frac{n - 1}{n}$$
  全集群 $n$ 个节点产生的全网总跨机网络流量为：
  $$\text{TotalNetworkTraffic} = (|R| + |S|) \cdot \frac{n - 1}{n}$$
  当节点数 $n$ 较大时，几乎整个数据集（约 $100\%$ 数据量）都需要通过物理网卡与网络交换机传输一次，网络带宽成为核心性能瓶颈。

![分布式重分区连接示意图：通过哈希重洗将两表元组跨网络重分布至目标节点](https://tc-1258979383.cos.ap-guangzhou.myqcloud.com/660baaa60715c.png)

![重分区网络传输开销计算图例：每节点收发数据量与网络带宽负载分析](https://tc-1258979383.cos.ap-guangzhou.myqcloud.com/66c41b589ac75.png)

### 5.4 场景四：半连接优化（Semi-Join Reduction）
若两张大表 $R$ 与 $S$ 跨节点连接，但由于外层带有高度选择性的过滤谓词，实际参与连接的元组只占极小比例：
1. 节点 1 仅提取表 $R$ 的连接键投影 $\pi_{A}(R)$，将其压缩发送给远端节点 2；
2. 节点 2 使用该投影键集合过滤表 $S$，产出半连接结果 $S \ltimes R = \{s \in S \mid s.B \in \pi_A(R)\}$；
3. 节点 2 仅将高度精简后的匹配元组发回节点 1 完成最终连接；
- **工业界进阶（布隆过滤器 Bloom Filter Join）**：在现代分布式系统（如 Presto、Spark SQL）中，系统往往将连接键映射为紧凑的位图过滤器（Bloom Filter）进行广播过滤，以极低的网络开销消除 $90\%$ 以上的无用数据传输。

## 6. 分布式两阶段聚合计算（Distributed Aggregation）

聚合操作（`SUM`、`COUNT`、`AVG`、`MAX`、`MIN` 以及 `GROUP BY`）在分布式环境下同样通过两阶段（Two-Phase）模式执行：

![两阶段分布式聚合计算示意图：节点本地局部预聚合与全局 Exchange 汇聚合并](https://tc-1258979383.cos.ap-guangzhou.myqcloud.com/66c43a690a2aa.png)

1. **第一阶段：节点本地预聚合（Local Aggregation）**  
   每个节点独立扫描自身本地的数据分片，针对本地元组执行 `GROUP BY` 局部汇总。对于可拆解的代数聚合函数（如 `AVG`），系统将其转化为包含 `SUM` 与 `COUNT` 的复合中间状态元组 $(sum_{local}, count_{local})$；
2. **第二阶段：全局汇总合并（Global Aggregation via Exchange）**  
   本地预聚合的结果数据量已被压缩数个数量级。各节点通过 Gather Exchange 将中间状态发送至协调节点（或通过 Hash Partitioned Exchange 分流至各聚集汇总节点），执行全局归并计算：
   $$\text{Global AVG} = \frac{\sum sum_{local}}{\sum count_{local}}$$
- **收益**：网络传输的数据量从海量的原始明细行锐减为极小规模的分组汇总统计量。

## 7. 高可用副本体系与 Quorum 强一致模型

分布式集群必须假设物理机器、网卡和磁盘随时可能发生永久性损坏。为了保证数据永不丢失，数据库引入多副本复制机制。

### 7.1 复制模式与拓扑决策
1. **主从复制（Primary-Replica / Master-Slave）**：
   - 所有的写操作统一路由至指定的主副本（Primary），主副本将修改日志持久化后同步或异步传播至只读从副本（Replicas）；
   - 从副本对外承接报表分析等只读查询，分担主库读压力；
2. **多主复制（Multi-Primary / Active-Active）**：
   - 多个节点均可并发接收写操作，但必须配备跨节点分布式冲突仲裁或分布式事务两阶段提交。

### 7.2 K-Safety 容灾阈值
- **定义**：数据库在任意时刻即使突发损坏 $K$ 个节点，系统整体依然能够继续对外提供正常服务且数据零丢失；
- **要求**：为了达成 $K$-Safety，集群中每一个数据分片的物理副本总数必须至少为 $K + 1$。

### 7.3 日志传播与更新时序
- **同步复制（Synchronous）**：主节点收到写入请求后，必须等待至少指定数量的副本确认持久化，才向客户端返回提交成功；安全性极高，但写延迟受限于最慢的网络链路；
- **异步复制（Asynchronous）**：主节点本地落盘后立即向客户端返回成功，后台异步发送日志。延迟极低，但主节点若突发物理烧毁，未复制的更新面临数据丢失风险；
- **实时连续传播（Continuous）**：事务每生成一条 WAL 记录立即通过流式套接字推向从节点（如 PostgreSQL Streaming Replication）；
- **批处理周期传播（Periodic）**：定时按检查点或批次集中打包同步日志。

### 7.4 Quorum 法定人数共识机制

为了在容忍单点网络卡顿与机器延迟的同时保障强一致性，现代分布式存储普遍采用**法定人数模型（Quorum Consensus）**：
- 设某分片的总副本数为 $N$；
- 每次写操作必须收到至少 $W$ 个副本的持久化确认才算成功；
- 每次读操作必须并发查询至少 $R$ 个副本，并选取其中版本号（Version / Timestamp）最新的结果。

::: theorem Quorum 鸽巢原理强一致判定定理
系统能够保证强一致性（客户端发起的读操作必定能读到最近一次已提交写操作的结果）的充分必要条件是：
$$R + W > N$$
**数学证明**：
设系统共有 $N$ 个物理副本。某次写操作成功覆盖的副本集合记为 $\mathcal{W}$（$|\mathcal{W}| = W$）；随后客户端发起的读操作采样的副本集合记为 $\mathcal{R}$（$|\mathcal{R}| = R$）。
根据集合论与鸽巢原理：
$$|\mathcal{W} \cap \mathcal{R}| = |\mathcal{W}| + |\mathcal{R}| - |\mathcal{W} \cup \mathcal{R}| \ge W + R - N$$
由于 $R + W > N$，必然有 $|\mathcal{W} \cap \mathcal{R}| \ge 1$！
这证明读操作采样的副本集合与写操作覆盖的副本集合**必然存在至少一个重叠的物理节点**。客户端通过比对重叠节点返回的数据版本戳，即可百分之百识别出最新提交的有效数据。
:::

## 8. 经典文献研读与学术思辨（Literature Review）

### 8.1 必读奠基论文

1. **Michael Stonebraker (1986)**  
   *`The Case for Shared Nothing`*. IEEE Database Engineering Bulletin, Vol. 9, No. 1.  
   **核心贡献**：首次全面对比了 Shared-Memory、Shared-Disk 与 Shared-Nothing 三种体系，推导了无共享架构在避免集中式硬件总线瓶颈上的压倒性优势，奠定了现代横向扩展分布式数据库的理论基石。
2. **Goetz Graefe (1990)**  
   *`Encapsulation of Parallelism in the Volcano Query Processing System`*. ACM SIGMOD Record.  
   **核心贡献**：提出了划时代的 Exchange 算子，展示了如何通过将多线程通信、数据分区与缓存队列封装为标准迭代器接口，使得单机查询执行器无需修改即可透明升级为大规模并行处理（MPP）引擎。
3. **David DeWitt & Jim Gray (1992)**  
   *`Parallel Database Systems: The Future of High Performance Database Systems`*. Communications of the ACM (CACM).  
   **核心贡献**：系统阐述了并行数据库的设计哲学，严格定义了加速比（Speedup）与扩展比（Scaleup）的评测体系，分析了数据倾斜与管道瓶颈对大规模并行的实际约束。

### 8.2 学术深度思辨题

::: insight 研读思考题 1：Amdahl 定律与分布式数据倾斜对线性加速比的破坏机制
**问题**：根据 Amdahl 定律，系统整体的理论加速比受限于必须串行执行的部分比例。在无共享架构的 MPP 查询执行中，除了固定的串行开销外，数据倾斜（Data Skew）是如何在微观物理层瓦解大规模并行加速效果的？  
**深度解答**：  
设一个查询被划分为 $N$ 个 Worker 并行执行。若数据完全均匀分布，每个节点处理 $\frac{1}{N}$ 的数据量，理想耗时降为 $T/N$。但在真实业务中，数据的属性值往往呈现严重的 Zipf 幂律分布（例如热门品牌或高频用户 ID 集中）。当系统执行哈希重分区（Shuffle）时，数千万条具有相同热点键的元组全部被散列路由至同一个节点 $W_k$。  
此时，其余 $N-1$ 个节点在毫秒级内完成本地计算后全部进入空闲等待状态，而受害者节点 $W_k$ 承受了数十倍的数据量与内存争用，频繁触发外部溢出写盘（Spill to Disk）。根据木桶定律，整个并行算子的完成时间由最慢的长尾节点（Straggler）决定。这导致无论集群横向增加多少节点，查询总耗时几乎不再下降，线性加速比彻底崩溃。工业级系统必须通过倾斜检测、广播倾斜键或盐化（Salting）打散策略进行缓解。
:::

::: insight 研读思考题 2：半连接（Semi-Join）与布隆过滤器在星型模型分析中的网络节约推导
**问题**：在星型模型数据仓库查询中，为什么现代 MPP 执行器普遍采用 Bloom Filter Pushdown 替代原始的 Semi-Join 实体传输？请从网络传输带宽与内存开销角度定量对比两者的权衡。  
**深度解答**：  
传统的 Semi-Join 需要维度表节点提取其连接键投影集合 $\pi_{\text{key}}(D)$，并跨网络传输实体值列表给事实表节点。设维度表过滤后的唯一键数量为 $K$ 个，每个键占用 8 字节，则需要传输 $8K$ 字节的精确键集合，接收端还需构建临时的哈希集合进行查找。  
而布隆过滤器（Bloom Filter）利用多哈希映射将键集合编码为一个紧凑的固定大小位图（Bit Array）。对于误判率（False Positive Rate）为 $p = 1\%$ 的情况，每个键平均仅需约 9.6 比特（约 1.2 字节）的存储空间。维度表节点只需广播一个数十 KB 的微型二进制位图，事实表扫描算子在读取底层数据页的同时即可利用 CPU SIMD 指令进行单周期极速位运算过滤。尽管布隆过滤器存在极小的假阳性误判（极少量不匹配的行未被过滤，最终由下游 Hash Join 精确剔除），但它以不到实体传输 $15\%$ 的网络带宽与更低的计算开销，达成了几乎等效的剪枝收益。
:::

::: insight 研读思考题 3：云原生存算分离架构对经典无共享（Shared-Nothing）架构的颠覆与重构
**问题**：Snowflake 等现代云数据仓库将存储完全下沉至云对象存储，这一架构是否违背了 Stonebraker 提出的“无共享（Shared-Nothing）”原则？它是如何在物理上克服经典 Shared-Disk 架构的缺陷的？  
**深度解答**：  
云原生存算分离架构并未违背无共享原则的本质精神，而是对其进行了现代硬件演进下的层次重构：  
1. **执行层依然是纯粹的 Shared-Nothing**：在计算节点集群内部，每个虚拟计算节点拥有独占的 CPU 与本地 NVMe 缓存，查询执行期间节点间依然采用 Shuffle 和本地内存交换，完全没有单机层面的全局硬件锁总线争用；  
2. **重构经典 Shared-Disk 的致命缺陷**：经典 Shared-Disk 失败的核心原因在于光纤存储网络成为单点 I/O 瓶颈，以及多机修改同一数据块必须运行分布式锁管理器（DLM）。而现代云对象存储（如 AWS S3）底层本身就是一个具备百万级 IOPS 线性扩展的分布式海量存储集群，消除了集中式存储瓶颈；更关键的是，现代云数仓的数据文件采用不可变列式格式（如 Parquet / ORC），写操作生成新版本文件而非原位修改，彻底消除了写写数据块争用与 DLM 开销。因此，存算分离架构兼具了 Shared-Nothing 的强悍并行算力与 Shared-Disk 的计算弹性解耦，达成了现代数据库工程的巅峰演进。
:::

在现代主流工业级数据库产品中，本讲推演的理论体系有如下直接对应：

## 并行处理数据库

- **目标**：在多个处理器上加快 SQL 的查询
- **怎么判断是否执行更快？ 或者说评价指标是什么**：

  - **加速比** 在同个问题上的 speed up(加速比) = 原耗时时间/新耗时时间
  - **放大比** scale up(放大) = 在一倍机器上的一倍的问题 / N 倍的机器上的 N 倍问题
  - 两者不一定相同，小问题的可能意味着很难并行化
- **数据库特别指标**
  - 事务加速比（Transaction speedup）： 固定的一组事务，用 1 vs N 个机器做比较

  - 批量加速比（Batch speedup）： 固定大小 DB，用 1 vs N 个机器

  - 事务放大比（Transaction scaleup）： 用 N 个机器来执行 N 倍的事务来与单个机器和单个事务做比较
  - 批量放大比（Batch scaleup）： 用 N 个机器来执行用 N 倍的一个事务来与单个机器和单个事务做比较
- 加速比目标

  - 线性增长的阻碍
    - 启动时间。启动并行执行器需要花费一点时间
    - 干扰竞争（interference contention）: 受限于一些共享资源；比如输入输出队列，等等
    - 工作倾斜： 每个处理器分配的工作量并不相同

### 并行架构

有几种方法来并行化数据库

- Shared Everything——共享所有

  - ![截屏 2024-04-01 15.28.27](https://tc-1258979383.cos.ap-guangzhou.myqcloud.com/660a6222ed112.png)
  - 优点
    - 容易构建多核计算机就是如此，易于编程
    - 多线程执行
    - 每个核都能访问任何记录
  - 缺点
    - 没有容错；如果内存/甚至一个处理器崩了，那么这个模型也就崩了
    - 难以在一些核上扩展

- Shared-Disk——共享磁盘

  - ![截屏 2024-04-01 15.28.43](https://tc-1258979383.cos.ap-guangzhou.myqcloud.com/660a6231ed2ca.png)
  - 多机器；每个机器都能访问磁盘的任何记录
  - 需要协调机制保证写入磁盘是安全的（缓存一致性）
  - 磁盘会抽象成服务
  - 容错机制取决于可靠磁盘阵列，成本较高
  - Oracle 用的很多

- Shared-Nothing——分布式

  - ![截屏 2024-04-01 15.48.22](https://tc-1258979383.cos.ap-guangzhou.myqcloud.com/660a66cd1a84b.png)
  - 多机器
  - 数据分区；每个机器各自负责处理&修改其负责的数据；意味着需要新的并发控制/恢复机制
  - 扩展性非常好： 添加机器或者分区都非常容易
  - 通过复制技术来容错

- Shared-Nothing——基于分布式文件系统的分布式

  ![截屏 2024-04-02 12.05.23](https://tc-1258979383.cos.ap-guangzhou.myqcloud.com/660b840b21d99.png)

  - 将存储扩展与计算扩展分离
  - 存储层实现了容错机制
  - 数据进行了逻辑分区且被不同的处理器操作
  - 在云计算已经很普遍了，比如 SnowFlake、MapReduce

##### **重新分区操作**

1. 重新分区：
   - 表 B 的每个分区被分割成 n 个新分区（每个节点一个新分区）
   - 每个节点会把它持有的分区数据按照分区规则分配到所有 n 个节点中，包括自身。这意味着每个节点都会把原分区分割成 n 份，发送到 n 个不同节点
2. 数据传输：
   - 假设表 B 的分区大小是|B|/n 字节，因此每一份大小就是|B|/n / n 字节
   - 因为每个节点上都有一个新的分区，所以每个节点需要把`n-1`份数据发送到其他节点，每份数据大小为$|B|/n^2$

> 每台机器需要接受和发送多少字节的数据？

![截屏 2024-08-20 12.27.59](https://tc-1258979383.cos.ap-guangzhou.myqcloud.com/66c41b589ac75.png)

- 每个分区有 |B| / n 个记录， 重分区将它水平拆分成 n 个 chunk，每个节点发送 n-1
- 每个节点: 发送 = 接受 =$ (n-1) * |B| / n^2$ bytes

> 假如表 A，B 都需要重新分区，每台机器需要接受和发送多少字节的数据？

每个节点： $(|A| / n^2)* (n-1) + (|B|/n^2) * (n-1) $​bytes

#### 复制的例子

- 假设我们需要将 B 复制到所有节点
- 在复制策略中，较小的表需要被复制到所有其他节点上。每个节点发送的字节数计算公式为 $|B| / n * (n-1)$
- ![截屏 2024-08-20 12.59.16](https://tc-1258979383.cos.ap-guangzhou.myqcloud.com/66c422afa3ddb.png)

#### 复制 vs. 分区

- 复制需要每个节点将较小的表发送给所有其他节点
  - 每个节点发送 `(|T| / n) * (n-1)` 字节
  - 而重分区一个表的情况下，每个节点发送 `((|T| / n) / n) * (n-1)` 字节
- 在什么情况下，复制会优于重分区来执行连接操作？
  - 如果较小表的大小 **小于** 需要重分区一个或两个表时发送的数据量。
  - 还需考虑连接操作的成本：使用复制的表时成本会更高。

>  例子：假设 `|B| = 1 MB`，`|A| = 100 MB`，`n = 3`

- 需要对 A 进行重分区（B 按连接属性分布）。

  - 重分区策略：重分区 A 的每个节点数据量为 `|A| / 3 / 3 * 2 = 22.2 MB`
    - 这个数据量明显大于 B 表大小，所以重分区 A 表开销较高
    - 连接操作将 .33 MB 的数据与 33 MB 的数据进行连接。

  - 复制策略：广播 B 的数据量为 `|B| = 1 MB`，即 `1 / 3 * 2 = 0.66 MB`。
    - 连接 1 MB 数据与 33 MB 数据进行连接。

结论： 分布式数据库执行连接操作时

- 当较小表的大小小于重分区时所需传输的数据量时，复制会是更好的选择。复制可以避免复杂的重分区操作，尤其是当**较小表的大小相对较小时**
- 如果需要进行连接的表大小较大

> 假设我们有两个表 A 和 B，它们分布在 3 个节点上。
>
> A 的大小为 9 MB。
>
> B 的大小为 90 MB。
>
> 连接条件是 `A.a = B.b`。
>
> - B 表根据 b 属性进行了哈希分区，而 A 表没有根据 a 属性分区。
>
> 如果我们执行以下操作，每个节点需要发送多少数据：
>
> 1. 重分区 A 表。
> 2. 复制 A 表。

Solution： 1. (9 / 3) / 3 * 2 = 2MB  ; 2. 9 / 3 * 2 = 6MB

#### 其他选择

- 预先复制小表
  - 如果空间允许，是一个不错的选择
- ”半连接“
  -  首先，将 B 表的连接属性值（例如 `B.b`）的列表发送给 A 表所在的节点。
  -  然后，A 表仅选择那些与 B 表中的值匹配的记录，并将这些匹配记录发送回 B 表所在的节点
  -  最后，B 表使用从 A 表接收到的匹配记录列表来完成最终的连接计算
  -  适合处理宽表（列数多的表），因为宽表的数据量较大，直接传输会很耗费资源。通过预过滤，只传输在 B 表中实际存在的值，避免了不必要的数据传输，提高了效率

  - 缺点：

##### **重新分区操作**

1. 重新分区：
   - 表B的每个分区被分割成n个新分区（每个节点一个新分区）
   - 每个节点会把它持有的分区数据按照分区规则分配到所有n个节点中，包括自身。这意味着每个节点都会把原分区分割成n份，发送到n个不同节点
2. 数据传输：
   - 假设表B的分区大小是|B|/n 字节，因此每一份大小就是|B|/n / n字节
   - 因为每个节点上都有一个新的分区，所以每个节点需要把`n-1`份数据发送到其他节点，每份数据大小为$|B|/n^2$

> 每台机器需要接受和发送多少字节的数据？

![截屏2024-08-20 12.27.59](https://tc-1258979383.cos.ap-guangzhou.myqcloud.com/66c41b589ac75.png)

- 每个分区有 |B| / n个记录， 重分区将它水平拆分成n个chunk，每个节点发送n-1
- 每个节点: 发送 = 接受 =$ (n-1) * |B| / n^2$ bytes

> 假如表A，B都需要重新分区，每台机器需要接受和发送多少字节的数据？

每个节点： $(|A| / n^2)* (n-1) + (|B|/n^2) * (n-1) $​bytes

#### 复制的例子

- 假设我们需要将B复制到所有节点
- 在复制策略中，较小的表需要被复制到所有其他节点上。每个节点发送的字节数计算公式为 $|B| / n * (n-1)$
- ![截屏2024-08-20 12.59.16](https://tc-1258979383.cos.ap-guangzhou.myqcloud.com/66c422afa3ddb.png)

#### 复制 vs. 分区

- 复制需要每个节点将较小的表发送给所有其他节点
  - 每个节点发送 `(|T| / n) * (n-1)` 字节
  - 而重分区一个表的情况下，每个节点发送 `((|T| / n) / n) * (n-1)` 字节
- 在什么情况下，复制会优于重分区来执行连接操作？
  - 如果较小表的大小 **小于** 需要重分区一个或两个表时发送的数据量。
  - 还需考虑连接操作的成本：使用复制的表时成本会更高。

>  例子：假设 `|B| = 1 MB`，`|A| = 100 MB`，`n = 3`

- 需要对 A 进行重分区（B 按连接属性分布）。

  - 重分区策略：重分区 A 的每个节点数据量为 `|A| / 3 / 3 * 2 = 22.2 MB` 
    - 这个数据量明显大于B表大小，所以重分区A表开销较高
    - 连接操作将 .33 MB 的数据与 33 MB 的数据进行连接。

  - 复制策略：广播 B 的数据量为 `|B| = 1 MB`，即 `1 / 3 * 2 = 0.66 MB`。
    - 连接 1 MB 数据与 33 MB 数据进行连接。

结论： 分布式数据库执行连接操作时

- 当较小表的大小小于重分区时所需传输的数据量时，复制会是更好的选择。复制可以避免复杂的重分区操作，尤其是当**较小表的大小相对较小时**
- 如果需要进行连接的表大小较大

> 假设我们有两个表 A 和 B，它们分布在 3 个节点上。
>
> A 的大小为 9 MB。
>
> B 的大小为 90 MB。
>
> 连接条件是 `A.a = B.b`。
>
> - B 表根据 b 属性进行了哈希分区，而 A 表没有根据 a 属性分区。
>
> 如果我们执行以下操作，每个节点需要发送多少数据：
>
> 1. 重分区 A 表。
> 2. 复制 A 表。

Solution： 1. (9 / 3) / 3 * 2 = 2MB  ; 2. 9 / 3 * 2 = 6MB

#### 其他选择

- 预先复制小表
  - 如果空间允许，是一个不错的选择
- ”半连接“
  -  首先，将 B 表的连接属性值（例如 `B.b`）的列表发送给 A 表所在的节点。
  -  然后，A 表仅选择那些与 B 表中的值匹配的记录，并将这些匹配记录发送回 B 表所在的节点
  -  最后，B 表使用从 A 表接收到的匹配记录列表来完成最终的连接计算
  -  适合处理宽表（列数多的表），因为宽表的数据量较大，直接传输会很耗费资源。通过预过滤，只传输在 B 表中实际存在的值，避免了不必要的数据传输，提高了效率
